性能调优：并发、批处理与显存优化

跑通是一回事，跑得爽是另一回事。当你从「好奇」进入「日常使用」，总会遇到这些场景：

  • 聊天到一半，模型突然「卡住不吐字」；
  • 打开长文档让它总结，直接报显存不足；
  • 多个请求同时进来，前面的把后面的堵死了。

这一篇，把影响本地模型性能的几个核心变量讲透：显存、上下文、并发、批处理、关键参数，并给你两张「排查清单」，让问题对号入座。

1. 先建立一个直觉：推理像「厨师同时炒几道菜」

把大模型推理想象成厨师炒菜：

  • 显存（操作台）：台面越大，能摊开的菜和配料越多；
  • 上下文（一桌的菜）：聊得越长，需要摆在台面上的「所有菜」越多；
  • 并发（同时来的客人）：几桌客人同时点单，厨师要么一桌一桌来（排队），要么一次炒好几桌的份（批处理）；
  • 批处理（一次炒多份）：同一时间把类似需求合并起来一起做，效率反而更高。

性能调优，本质上就是：在台面（显存）有限的前提下，让厨师（GPU）忙而不乱。

2. 第一课：显存都去哪了？

你可能会以为「显存 = 模型体积」。其实推理时的显存由三块组成：

推理占用的显存 ≈ 模型权重 + 上下文（KV cache）+ 计算中间缓冲
  • 模型权重：模型本身，体积 = 参数 × 精度（第 2 篇 content/硬件怎么选：显存、内存与 CPU 的账.md 讲过）；
  • KV cache（上下文缓存）：为了记住对话历史，模型要把每轮「见过」的词都缓存一份。上下文越长，这个缓存越大；
  • 中间缓冲：计算过程中的临时数据。

新手最容易忽略的就是 KV cache——这也是「模型明明很小，却还是爆显存」的头号原因。上下文从 4K 加到 32K，KV cache 可能吃掉好几个 GB。

术语解释：K 和 V 是 Transformer 注意力机制里的两个关键向量，KV cache 就是给它们做的「草稿纸」。普通人只需要记住：上下文越长，显存越紧张。

3. 第二课：控制上下文长度的两个参数

在 Ollama 里，和你日常最相关的是这两个参数（可通过 ollama run 时的环境变量或 API 请求参数设置）：

参数 作用 建议
num_ctx 模型能「记住」的最大 Token 数（上下文窗口） 日常聊天 4096～8192 就够；长文档才需要 16384+
num_predict 一次最多生成多少个 Token（回答最长长度） 默认 -1（不限制）；短问答可以设 512

设置方式（API 请求时）：

from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
resp = client.chat.completions.create(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "写一篇 800 字的小作文"}],
    max_tokens=1200,       # 对应 num_predict：限制输出长度
    # 其他选项见下方第 5 节
)

为什么默认值往往很大？ 厂商为了「看起来能力强」，默认上下文给得很长。但你如果只是聊天，8K 就绰绰有余——把上下文改小，立竿见影地省显存、提速度。

4. 第三课：并发与批处理——人多不一定慢

4.1 排队（串行）vs 并行

Ollama 默认是一个模型实例服务所有请求。当多个请求同时到达，有两种处理方式：

  • 串行排队：一个一个来，每个请求独占全部 GPU——每个人等待时间变长，但单次回答不降速；
  • 并行/批处理：把多个请求打包成一批同时算——单位时间完成的请求总数（吞吐量）大幅上升，但每个请求的速度略有下降。

对「一个人用」来说，串行就行；对「团队用/批量任务」来说，批处理才是正道。

4.2 Ollama 的并发设置

Ollama 用环境变量控制同时加载的模型数量：

# 最多同时加载 2 个模型（默认即可）
set OLLAMA_MAX_LOADED_MODELS=2

# 每个模型最多并行处理 4 个并发请求（默认 4）
set OLLAMA_NUM_PARALLEL=4

Windows 用 set，macOS/Linux 用 export，设置后重启 Ollama 生效。

补充一个实用细节：这些环境变量设置后重启 Ollama 才生效。如果你不想每次开终端都敲一遍 set/export，可以把它「永久化」：

  • Windows：右键「此电脑」→ 属性 → 高级系统设置 → 环境变量 → 新建，把 OLLAMA_NUM_PARALLEL 等变量永久写进去；
  • macOS / Linux：把 export 那几行写进 shell 配置文件（~/.zshrc 或 ~/.bashrc），下次开终端自动生效。

注意权衡：并行数调高 → 吞吐上升，但显存占用也上升（每个并发都要一份 KV cache）。显存不够时并行反而导致反复换出模型，拖垮整体速度。

4.3 vLLM 与批处理的关系

如果你对「高并发、大批处理」有真实需求（比如要同时服务 30 个人），第 6 篇 content/推理引擎对比：llama.cpp、vLLM 与 Ollama.md 提过的 vLLM 才是专业选手——它的核心优化就是把批处理做到了极致（分页注意力、连续批处理）。个人电脑上用 Ollama 调好并行数就够了，不必上 vLLM。

5. 第四课：三个「说话风格」参数

除了性能，还有几个控制「输出行为」的参数，顺手讲清楚（它们影响质量，间接影响重试次数和耗时）：

参数 作用 取值建议
temperature 随机性：越高越天马行空，越低越稳定保守 写文案 0.7～1.0；总结/代码 0.1～0.3
top_p 采样的候选范围（配合 temperature 用） 默认 0.9 左右即可
num_predict 回答最大长度 见第 3 节

典型用法：让模型做「事实类」任务（总结、翻译、代码）就把 temperature 调低——减少胡说八道（幻觉），也减少「答完再重试」的浪费。

一句话理解三个参数的关系：temperature 决定「敢不敢冒险」，top_p 决定「在多大范围内冒险」，num_predict 决定「最多走多远」。日常使用中，只调 temperature 和 num_predict 就够覆盖九成场景，别被参数数量吓到。

6. 第五课：让 GPU 多干活，CPU 少干活

前面讲过（第 2 篇、第 6 篇），模型会被拆成「层」，一部分放 GPU、一部分放 CPU：

  • 放 GPU 的层越多 → 速度越快；
  • 放不下的部分落到 CPU → 明显变慢，但能「跑起来」。

Ollama 的参数是 num_gpu：

  • 默认：Ollama 自动判断，能放多少放多少（新手就用默认）；
  • 手动指定：比如显存和模型僵持时，强制只放 40 层到 GPU：
OLLAMA_NUM_GPU=40 ollama run qwen2.5:7b

显存不足时怎么办？ 两个思路：

  1. 降低量化：Q8 → Q6 → Q4（第 4 篇 content/模型格式与量化：GGUF 与 Q4/Q8.md），权重小了，占用直降；
  2. 减少 GPU 层数：让一部分层跑 CPU，虽然慢，但至少能跑完不崩。

7. 场景排查清单（直接抄作业）

7.1 场景一：「显存不够 / 报错 OOM」

按顺序排查，命中即解决：

  • [ ] 换了更小的量化版本（Q4）？
  • [ ] 缩小了上下文长度（num_ctx 调到 4096）？
  • [ ] 降低了并行数（OLLAMA_NUM_PARALLEL=1）？
  • [ ] 关了占显存的其他程序（浏览器几十个标签页会吃共享显存）？
  • [ ] 降低了 OLLAMA_MAX_LOADED_MODELS，避免同时装多个模型？
  • [ ] 最后手段：降模型规模（7B → 3B），或启用 CPU 混合推理。

7.2 场景二：「回答一个字一个字蹦，太慢了」

  • [ ] 模型是否大部分层在跑 CPU？用 ollama ps 看 GPU/CPU 占比；
  • [ ] 上下文是否太长？长对话用 /clear 或新开会话；
  • [ ] temperature 是否过高导致模型「想太多」？事实类任务调低；
  • [ ] 是否开着多个大模型？ollama ps 看内存占用；
  • [ ] 电脑是否同时开着大量软件？给模型让路。

7.3 场景三：「多个人一起用就卡死」

  • [ ] 显存够不够并行？不够就 OLLAMA_NUM_PARALLEL 调低到 2 或 1；
  • [ ] 大家是不是都用同一个大模型？分流到不同模型（如小号 3B 处理轻量请求）；
  • [ ] 长期多用户场景，认真考虑 vLLM（见第 6 篇）。

8. 性能体检：怎么量化「快不快」？

调优前后要有数据对比，两个指标够用：

  • 首 Token 延迟：发出请求到输出第一个字的等待时间，越短越「跟手」；
  • 吞吐量：每秒生成的 Token 数（tokens/s），越高越「流畅」。

在 Ollama 对话里看右下角的 eval rate 就能看到实时速度（约等于每秒生成 Token 数）。调优后对比一下，成就感拉满。

8.1 怎么判断瓶颈在「显存」还是「算力」？

一个简单的观察法：

  • 显存满了，但 GPU 利用率不高 → 瓶颈在「装不下」或「搬运数据」，解法是降量化、缩上下文；
  • 显存没满，GPU 利用率 90% 以上 → 瓶颈在「算力」，调参基本无用，换更好的硬件才有效。

Windows 用户用「任务管理器 → 性能 → GPU」看利用率；Linux 用户执行 nvidia-smi 即可实时观察。

8.2 最简单的压测脚本

想客观衡量调优效果？写个循环，连续发 10 次请求，记录每次耗时：

import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
for i in range(10):
    t0 = time.time()
    client.chat.completions.create(
        model="qwen2.5:7b",
        messages=[{"role": "user", "content": "说一句话"}],
        max_tokens=50,
    )
    print(f"第 {i+1} 次耗时：{time.time() - t0:.1f} 秒")

如果每次耗时稳定，说明性能稳定；如果越来越慢，多半是上下文被撑大或缓存累积——新开会话即可缓解。

9. 常见问题

9.1 「调了半天还是慢，是不是模型有问题？」

大多数情况不是模型问题，而是硬件天花板。7B 模型在纯 CPU 上大约每秒 1～4 个词、在中端显卡上大约每秒 20～40 个词——这是物理规律，调参改变不了量级。先接受「这台电脑的极限在哪」，再决定要不要升级硬件，别在参数上无限死磕。

9.2 「为什么换了更大的模型，反而明显变慢？」

意料之中。大模型权重更多，每一步计算的规模是指数级上升的。从 7B 换到 32B，速度掉一半甚至更多都很正常。如果你「既要质量又要速度」，正确姿势是保持模型规模不变、把量化等级提高（Q4 → Q6/Q8），而不是盲目上更大的模型。

9.3 「多个并发请求会不会把系统搞崩？」

不会。Ollama 自带排队机制，请求多了只是排队等待，不会「搞崩」。真正的风险是另一种：显存不够时，Ollama 会反复把模型换进换出，表现为「突然变得极慢」。遇到这种抖动，调低并行数（OLLAMA_NUM_PARALLEL）往往比调高更有效。

10. 本章小结

一张「性能调优地图」收尾：

现象 核心变量 手段
爆显存 权重 + KV cache 降量化、缩上下文、降并行
太慢 GPU/CPU 比例 提高 num_gpu、缩小模型、缩短上下文
多请求排队 并行数 调 OLLAMA_NUM_PARALLEL；长期上 vLLM
输出不稳定 temperature 事实类任务调低至 0.1～0.3
  1. 显存 = 权重 + KV cache + 缓冲，上下文是隐形杀手；
  2. 并发与批处理：单人串行、团队并行，吞吐与延迟要取舍；
  3. num_ctx/num_predict/temperature 是最常用的三个旋钮；
  4. 两个典型场景（OOM、卡顿）各有 6 步排查清单，按序执行。

性能调优是个「体力活」，但回报是实打实的：同样的电脑，能跑更大的模型、答得更快。
