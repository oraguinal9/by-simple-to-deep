API 服务化：把本地模型变成接口

到这一篇为止，你的模型已经能「命令行对话」和「网页对话」了。但你可能还有一个念头：能不能让别的程序也用上它？ 比如自己写的小工具、公司的现有系统、甚至一个手机 App。

答案是：能。办法就是——把本地模型变成 API（接口）。

这一篇讲三件事：什么是 API、Ollama 怎么把模型变成 API、以及你怎么用代码调用它。

1. 先建立一个直觉：API 像「餐厅的外卖窗口」

想象你的模型是一家餐厅：

  • 直接在店里吃（命令行/网页对话）——方便，但只有食客本人能用；
  • 开一个外卖窗口（API）——任何「带单子来」的人（其他程序）都能下单，窗口按标准格式接单、出餐。

这个「标准格式」就是关键。本地模型要变成 API，就得让任何程序都能用一套统一的规则来下单。

好消息是：业界已经有一套「事实标准」——OpenAI 的 API 格式。无数软件（聊天机器人、办公工具、翻译插件……）都按这套格式开发。Ollama 提供了一个 /v1 端点，用 OpenAI 兼容的格式接受请求。这意味着：

任何原本用 ChatGPT 接口写的程序，只要把请求地址改成本地地址，就能无缝改用你本地跑的免费模型。 一个字都不用改逻辑。

这就是「API 服务化」最大的价值。

补充一句实用背景：API 全称是「应用程序接口」。不用背这个词，把它理解成「程序之间沟通的固定暗号」即可。暗号定好了，任何程序（无论用什么语言写的）都能来敲门。这也是「标准化」如此重要的原因——OpenAI 定下暗号，全世界程序都照它开发；现在你把服务换成本地的，程序们照样听得懂，只是服务端从「千里之外」换成了「你家楼下」。

2. 先确认你的模型「API 窗口」开着

Ollama 安装后默认就开着一个本地服务，监听 http://localhost:11434。先验证一下：

curl http://localhost:11434/api/tags

如果返回一段 JSON（包含你已安装的模型列表），说明服务正常。这个地址就是你的「AI 服务器」大本营。请记住 11434 这个端口号——后续所有对接（Open WebUI、你自己的程序）都会用到它。

Ollama 提供了两套接口：

端点 说明
/api/... Ollama 原生接口（简单直接）
/v1/... OpenAI 兼容接口（推荐给开发者）

给没写过代码的读者补一句 JSON 是什么。 看到请求里一堆 {"字段名": 值}，你可能会懵。简单说，JSON 就是「给程序看的表格」——用一对花括号把信息组织起来。上面那段请求翻译成人话是：「我要点一道菜（model 是 qwen2.5:7b），点单内容（messages）是——先设定餐厅规范（system：你是一位友好的助手），再问一个问题（user：用一句话介绍你自己）。」并不神秘。

重点说 /v1。它的地址长这样：

http://localhost:11434/v1/chat/completions

这就是「兼容 ChatGPT 的聊天接口」，下面我们分三步调用它。

3. 三步调用本地模型：curl 版

第一步：准备模型

确保 Ollama 里有一个模型在运行（没有就下载）：

ollama run qwen2.5:7b

注意：run 之后对话窗口会占着。可以敲 /bye 退出，但不要退出服务——Ollama 的服务是独立常驻的，退出对话窗口不影响 API 可用。确认服务在跑：curl http://localhost:11434/api/tags。

第二步：发送第一条 API 请求

打开另一个终端窗口，执行：

curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5:7b",
    "messages": [
      {"role": "system", "content": "你是一位友好的助手"},
      {"role": "user", "content": "用一句话介绍你自己"}
    ]
  }'

你会在屏幕上看到一长串 JSON，其中最关键的是 choices[0].message.content 里的内容——那就是模型的回答。

第三步：看懂请求的四个核心字段

字段 作用 类比
model 用哪个模型 点的是哪个菜
messages 对话内容（含角色和消息） 你说了什么、上下文是什么
role: system 给模型设定的「人设/规则」 餐厅的服务规范
role: user 你（用户）说的话 你的点单

多轮对话怎么实现？很简单——把历史消息全部放进 messages 数组：

{
  "model": "qwen2.5:7b",
  "messages": [
    {"role": "system", "content": "你是一个耐心的中文老师"},
    {"role": "user", "content": "什么是梯度下降？"},
    {"role": "assistant", "content": "梯度下降是一种……"},
    {"role": "user", "content": "那学习率呢？"}
  ]
}

原理与成本提醒：每轮对话都会把全部历史再发给模型一次，这既是它能「记得」上下文的原因，也是越聊越慢、越占显存的原因（第 9 篇 content/性能调优：并发、批处理与显存优化.md 会讲怎么控制）。

4. 用 Python 调用：老代码一行不改

现在到了最激动人心的一步。OpenAI 官方 Python 库可以直接指向本地模型：

pip install openai

然后写一个 Python 脚本 chat.py：

from openai import OpenAI

# 关键：把 base_url 指向本地 Ollama，api_key 随便填一个占位
client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",  # 本地服务不校验 key，随便写
)

# 调用方式与调用 ChatGPT 完全一致
resp = client.chat.completions.create(
    model="qwen2.5:7b",
    messages=[
        {"role": "system", "content": "你是我的中文写作助手"},
        {"role": "user", "content": "帮我写一段欢迎新同事的开场白"},
    ],
)

print(resp.choices[0].message.content)

运行：

python chat.py

你会看到模型生成的文字打印出来。

关键点再强调一遍：这段代码和调用 ChatGPT 的唯一区别，就是 base_url 换成了本地地址、api_key 随便填。任何用 openai 库写的现成代码，都可以通过改这一行，无缝切换到本地模型。

如果你不想用 openai 这个库，用 Python 自带的 requests 也能实现同样效果——本质都是「发一个 HTTP POST 请求、解析 JSON 返回」，openai 库只是把这些过程封装得更友好。理解「调用 API 本质上就是发请求、收响应」，能帮你摆脱对任何单一库的依赖。

5. 兼容层原理：Ollama 的 /v1 是怎么回事？

你可能会好奇：Ollama 内部是 llama.cpp（见第 6 篇 content/推理引擎对比：llama.cpp、vLLM 与 Ollama.md），它凭什么能听懂 OpenAI 的格式？

原理并不神秘——翻译层：

外部请求（OpenAI 格式 JSON）
        ↓  Ollama 收到后解析
翻译成内部调用（调用 llama.cpp 跑 GGUF 模型）
        ↓  模型生成结果
翻译回 OpenAI 格式 JSON 返回

Ollama 在 :11434 端口开了一个 HTTP 服务器，/v1/* 路径下的请求会被专门处理：解析 OpenAI 风格的 messages，翻译成内部任务，再把结果包装成 OpenAI 风格的响应。

这就解释了为什么它可以「以假乱真」——它在协议层做了兼容，而不是让 llama.cpp 本身认识 OpenAI。

对开发者而言：你根本不需要关心这个翻译过程，只需要记得一个地址、一套格式。

顺带一提，URL 里的 /v1 表示「第一版接口」。OpenAI 的接口从第一版至今没有大的变动，所以 /v1 成了行业惯例。你会发现 DeepSeek、智谱等国内服务的 API 地址也都带 /v1——原因就是大家都兼容同一套协议，方便程序「一次开发、到处切换」。

6. 除了 model 和 messages，常用参数还有这些

前面用的请求只包含了 model 和 messages 两个字段。实际开发中，还有几个高频参数你应该认识：

参数 作用 建议
temperature 随机性（取值 0~2），越高越发散 创意写作 0.7+，事实类 0.1~0.3
max_tokens 回答的最大长度 默认不限制；需要控时设置
stream 是否流式返回 false 一次性返回；true 逐字返回
top_p 采样候选范围 通常和 temperature 二选一来调
seed 随机种子，固定后可复现结果 测试/对比时用

6.1 流式输出（stream）怎么取舍？

stream: true 时，回答像打字一样逐字推送（适合做「打字机效果」），但代码要处理多次返回；stream: false 一次性拿到完整结果，代码最简单。个人项目建议先 false 跑通，再考虑升级流式——少踩很多坑。

6.2 一次带参数的真实请求

resp = client.chat.completions.create(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "写一首关于春天的五言绝句"}],
    temperature=0.9,   # 创作场景，适度发散
    max_tokens=200,    # 控制在 200 个 token 以内
)
print(resp.choices[0].message.content)

7. 实战场景：本地 API 能干什么？

有了这个接口，你的想象力可以打开了：

场景一：给现有应用换引擎

公司内部的小工具、个人脚本，原本调 OpenAI，把 base_url 改成 http://localhost:11434/v1，API 费归零，数据留在本地。

场景二：批量处理文档

写一个 Python 脚本，把几百个文本文件逐个发给本地模型做摘要：

import os
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

for name in os.listdir("documents"):
    if not name.endswith(".txt"):
        continue
    with open(f"documents/{name}", encoding="utf-8") as f:
        text = f.read()
    resp = client.chat.completions.create(
        model="qwen2.5:7b",
        messages=[
            {"role": "user", "content": f"请用三句话概括下面内容：\n{text}"}
        ],
        temperature=0.3,  # 低温度，输出更稳定
    )
    print(f"{name}: {resp.choices[0].message.content}\n")

场景三：接入自动化工具链

本地模型 + 定时脚本 = 自动写日报、自动翻译、自动归类邮件。数据全程不出本机。

场景四：做「本地优先、云端兜底」的双引擎

把云端的 base_url 和本地的 base_url 同时准备好，用一行配置切换：

# 想用本地：改成这一行
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

# 想用云端：换成云端地址和真实密钥
# client = OpenAI(base_url="https://api.deepseek.com/v1", api_key="你的密钥")

思路很简单：常规任务走本地（免费、私密），复杂任务切云端（更强）。两个引擎共存，各取所长。

8. 常见问题

8.1 「请求报 404 / 连接被拒绝」

  • 检查 Ollama 服务是否在跑：curl http://localhost:11434/api/tags；
  • 确认地址拼写：/v1/chat/completions（注意是 chat 不是 chatbot）；
  • Windows 防火墙可能拦截，首次启动时允许即可。

8.2 「返回的内容是乱码 / 空白」

  • 确认请求头带了 Content-Type: application/json；
  • 中文乱码通常是终端编码问题（Windows 设 chcp 65001），数据本身没问题；
  • 给请求加参数 "stream": false，避免流式输出把输出格式搞乱。

8.3 「api_key 填什么？」

本地 Ollama 不校验密钥，填任意字符串（如 "ollama"、"local"）都能通过。别把云端的密钥写进这个脚本——本地根本用不上。

8.4 「响应慢怎么办？」

本地模型慢是硬件决定的。优化方向见第 9 篇：降低并发、缩短上下文、选更小的量化版本、把 GPU 用足。

8.5 「能同时调用多个模型吗？」

可以。请求里的 model 字段可以随意切换你已安装的任意模型，Ollama 会自动加载对应模型。但注意：同时加载多个大模型会占满显存/内存（第 9 篇 content/性能调优：并发、批处理与显存优化.md 会讲并行数控制）。建议按需切换，而不是把几个大模型全部常驻内存。

8.6 「能在浏览器里直接调用本地 API 吗？」

可以，但要注意「跨域」问题：浏览器出于安全策略，会限制网页向本地端口发请求。最简单的做法是把调用放到后端服务里（比如用 Python/Node 写一个小接口），或者直接用第 7 篇的 Open WebUI 这类现成界面。别在纯前端页面里直接调本地 API，会踩 CORS 的坑，而且没必要自己造轮子。

9. 本章小结

  1. API 化价值：让任何程序都能调用本地模型，数据不出本机，费用为零；
  2. 一键兼容：Ollama 的 http://localhost:11434/v1 是 OpenAI 兼容接口，改 base_url 就能换引擎；
  3. 调用方式：curl 一条命令验证，openai Python 库一行配置接入；
  4. 原理：Ollama 做了一层「协议翻译」，让你在本地享受云端的开发体验。
