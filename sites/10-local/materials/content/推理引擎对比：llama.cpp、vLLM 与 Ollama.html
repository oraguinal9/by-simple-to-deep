推理引擎对比：llama.cpp、vLLM 与 Ollama

你可能已经用 Ollama 跑起了模型，也听说过 llama.cpp、vLLM、LM Studio 这些名字。它们之间是什么关系？哪个适合我？

这一篇，把本地部署的「引擎」世界讲清楚。先给一个核心结论：Ollama 只是方便的外壳，真正干重活的是底层的推理引擎。 理解了这层关系，你就明白了整个本地部署技术栈的地图。

1. 先建立一个直觉：引擎像「发动机」，工具像「整车」

  • 推理引擎是发动机：负责把模型「算」起来，是核心技术，但不友好——发动机没法直接开着上路；
  • 工具/壳是整车：把发动机装进车架，配上方向盘、座椅、仪表盘，你只管开。

所以：

  • llama.cpp / vLLM 是「发动机厂」；
  • Ollama、LM Studio 是「整车厂」——它们内部用的就是 llama.cpp 这类发动机。

打开 Ollama 跑 ollama run 时，实际发生的是：

你输入文字
   ↓
Ollama（整车：负责下载模型、管理会话、提供命令和 API）
   ↓
llama.cpp（发动机：负责把模型加载进显存/内存，逐字生成回答）
   ↓
回答输出给你

这就是第 3 篇里说的「Ollama 底层就是 llama.cpp」的完整含义。了解这一点，你就能理解：Ollama 能跑什么模型，基本取决于 llama.cpp 支持什么格式（GGUF，见第 4 篇 content/模型格式与量化：GGUF 与 Q4/Q8.md）。

2. 逐个认识四位主角

2.1 llama.cpp：最底层的「发动机」

  • 是什么：一个用 C/C++ 写的开源推理引擎，最初专为在 CPU 上跑模型而设计，后来也支持 GPU。它是整个本地开源推理生态的基石。
  • 特点：
  • CPU 友好：没有好显卡也能跑（这一点决定了它的江湖地位）；
  • 支持 GGUF：本地格式的「普通话」（见第 4 篇）；
  • 轻量：可以打包成极小的程序，嵌入各种设备（路由器、手机、树莓派……）；
  • 可移植：一个可执行文件 + 一个模型文件就能跑，无任何 Python 依赖。
  • 适合谁：想完全掌控、研究原理、在特殊设备上部署的进阶玩家。
  • 怎么用（命令行）：
# 下载 llama.cpp 编译版后
./llama-cli -m ./models/qwen2.5-7b-instruct-q4_k_m.gguf -p "你好，请介绍一下自己"

顺带解答一个新手常问的问题：为什么 llama.cpp 用 C++ 写，而不是更流行的 Python？

因为 C++ 程序编译后直接运行，没有解释器那层开销——启动更快、内存占用更低、性能更稳，还能打包成单个可执行文件随处拷贝。相比之下，Python 方案（比如 vLLM 那套）要装一堆依赖，启动更重。在「老电脑跑得动」「嵌进小程序」这类场景，C++ 的优势无可替代。

2.2 Ollama：给发动机装上车壳

  • 是什么：基于 llama.cpp 的「整车」。它在发动机外做了四件事：
  • 模型管理：一行命令下载、删除、查看模型（第 3 篇讲过）；
  • 会话封装：ollama run 直接进入聊天；
  • API 服务：内置 OpenAI 兼容接口（第 8 篇 content/API 服务化：把本地模型变成接口.md）；
  • 硬件自动调度：自动把层分配到 GPU/CPU。
  • 特点：简单到极致，新手十分钟上手；跨平台（Win/Mac/Linux）；社区活跃。
  • 适合谁：绝大多数本地部署用户——先上 Ollama 绝对没错。
  • 怎么用：
ollama run qwen2.5:7b

2.3 vLLM：为「并发服务」而生的高性能引擎

  • 是什么：一个用 Python 编写的高性能推理引擎，核心卖点是高吞吐、高并发。
  • 特点：
  • 用了「分页注意力」（PagedAttention）等黑科技，同时服务几十上百个请求时，速度几乎不衰减；
  • 支持业界标准的 OpenAI 兼容 API，是很多公司做「模型即服务」的首选；
  • 依赖 GPU 和较完整的 Python 环境，对纯 CPU 用户不友好；
  • 主要面向服务端部署，不是个人桌面工具。
  • 适合谁：要搭一个多人可用的 AI 服务、研究生产级部署的进阶玩家。
  • 怎么用（示意，实际需先安装）：
# 启动 vLLM 服务，暴露 OpenAI 兼容接口
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8000

一句话对比：llama.cpp 和 vLLM 都能跑模型，但 llama.cpp 主打「少资源、可移植」，vLLM 主打「多并发、高吞吐」。个人电脑用前者，多用户服务用后者。

2.4 LM Studio：图形界面版的「整车」

  • 是什么：一个带图形界面的本地模型运行工具，底层同样用 llama.cpp。
  • 特点：全图形化——点鼠标就能下载模型、切换模型、调参数、聊天，完全不用碰命令行；自带模型浏览与搜索。
  • 适合谁：完全不想看命令行、只想有个「本地 ChatGPT」的纯新手。
  • 怎么用：安装 → 搜索模型 → 下载 → 点「聊天」，全程鼠标操作。
  • 注意：它和 Ollama 是竞品，二选一即可（本系列以 Ollama 为主线）。

2.5 顺带一提：还有哪些「角色」？

为了让你以后在社区里看到这些名字不慌，再快速盘点几个相关角色：

  • llama-server：llama.cpp 自带的 HTTP 服务端，相当于「不带壳的 API」。进阶玩家会直接用它在本地起一个标准接口（和 Ollama 的 API 类似）；
  • GPT4All：另一个图形化工具，主打离线小模型、界面友好，与 LM Studio 同类；
  • SGLang：新兴的高性能推理引擎，面向服务端，性能和 vLLM 同级，是后起之秀；
  • Transformers + Hugging Face：Python 生态的「正统」推理/训练框架，适合做研究和实验，纯本地部署偏重。

一句话记住：个人本地部署的主力就是 llama.cpp 及其外壳（Ollama / LM Studio），其余引擎多面向服务端或研究。 了解存在即可，不必都上手。

  • 想要在旧电脑/嵌入式设备跑 → llama.cpp；
  • 普通个人用户请直接拥抱 Ollama，其他了解即可。

4. 深入一点：Ollama 是怎么「调用」llama.cpp 的？

作为一个「由简入深」的系列，这一节讲一点点原理，但会用大白话。

llama.cpp 把「跑模型」这件事抽象成了几个步骤：

  1. 加载 GGUF 文件：把权重和分词器读进内存；
  2. 分配层：决定哪些层放 GPU、哪些层放 CPU（-ngl 参数控制，Ollama 里叫 num_gpu）；
  3. Token 化：把你的输入文字拆成 Token；
  4. 前向计算：模型逐 Token 预测下一个 Token，直到生成完整回答。

Ollama 做的事情，就是替你把第 1、2 步的配置都自动化了——根据你的显存自动决定放多少层到 GPU，然后把第 3、4 步的执行结果用友好的方式呈现给你。

在第 9 篇 content/性能调优：并发、批处理与显存优化.md，我们会回到这些底层参数，教你手动优化。

5. 常见问题

5.1 「我用 Ollama，还需要学 llama.cpp 吗？」

不需要。把 Ollama 当成你的日常工具，llama.cpp 的存在是为了让你理解「Ollama 的边界在哪」。只有当你需要精细控制（比如只跑 CPU、嵌入某个小程序）时，才需要直接接触 llama.cpp。

5.2 「vLLM 一定比 Ollama 快吗？」

分场景。单用户交互（你自己聊天），两者差别很小，Ollama 甚至更省心；几十个用户并发请求，vLLM 的吞吐优势才体现出来。别为了「听起来高级」就上 vLLM——先问自己有多少并发需求。

5.3 「能在 Windows 上用 vLLM 吗？」

可以但比较折腾（vLLM 官方主力支持 Linux + NVIDIA GPU）。Windows 玩家想体验服务化，直接用 Ollama 的 API 即可，效果对个人用户完全够用。

5.4 「Ollama 会取代 llama.cpp 吗？」

不会。Ollama 是「壳」，llama.cpp 是「芯」，壳依赖芯。而且 llama.cpp 自身也在持续进化（支持更多新模型、新量化），两者是共生关系。

5.5 「CPU 推理和 GPU 推理，速度差多少？」

以 7B 的 Q4 量化模型为例，一个粗略的经验值：

  • 中端显卡（8GB 左右）：约每秒 20～40 个词，接近人正常阅读速度；
  • 纯 CPU（8 核主流笔记本）：约每秒 1～4 个词，能明显感到「一字一字往外蹦」。

差距大约一个数量级，所以「加显卡带来质变」这句话是真的。但换个角度：如果只是偶尔用用、不赶时间，CPU 的慢速也并非不能忍——先跑通流程再升级硬件，是更稳妥的路线。

5.6 「Ollama 下载的模型，vLLM 能直接用吗？」

不能直接共用。Ollama 用的是 GGUF 格式，vLLM 主要用 Hugging Face 的 safetensors 格式，两者是「两套打包方式」。好在有官方转换脚本可以互转。对普通用户来说，你选了哪个引擎，就按哪个生态下载模型，不必纠结转换问题。

5.7 决策清单：我该留在 Ollama 还是上 vLLM？

我的情况 选择
就我一个人用，偶尔聊天 留在 Ollama，别折腾
几个人共用（5 人以内） Ollama + Open WebUI 足够
几十人同时用，要求高吞吐 考虑 vLLM + 一台好 GPU 的服务器
要在树莓派、路由器这类小设备上跑 用 llama.cpp 裸跑

这张表的逻辑很简单：并发需求决定引擎选择。个人和小组场景，Ollama 的并发能力已经够用；只有「规模化服务」才需要 vLLM 这种专业引擎。别被「性能焦虑」绑架——用最简单的方式解决你的问题，就是最好的方案。

5.8 「LM Studio 和 Ollama 能同时装吗？」

可以，两者互不冲突（它们各自管理自己的模型目录）。但没必要同时用——选一个顺手的主力即可。更常见的玩法是：用 Ollama 当「引擎底座」（命令行和 API 好用），再让其他界面（比如第 7 篇的 Open WebUI）连上它。这种「引擎归引擎、界面归界面」的架构，正是整个本地部署生态最优雅的地方。

6. 本章小结

一张地图帮你收尾：

推理引擎层（发动机）：llama.cpp（CPU友好、可移植） | vLLM（高并发、服务端）
      ↑ 封装 ↑
工具层（整车）：Ollama（命令行友好） | LM Studio（图形界面友好）
      ↑ 统一接口 ↑
你的使用层：个人聊天 / 网页界面 / API 服务
  1. Ollama 底层是 llama.cpp，这是理解整个生态的关键；
  2. 普通用户选 Ollama，无脑正确；
  3. 进阶方向：vLLM 用于高并发服务，llama.cpp 用于底层控制；
  4. 选型口诀：要简单用 Ollama，要并发用 vLLM，要全鼠标用 LM Studio。
