第六章 PPO 训练循环：RLHF 是怎么一步步炼成的

第五章讲了 PPO 的「零件」，这一章我们把它组装成一条流水线，看看一次完整的 RLHF 训练到底在跑什么。理解了这条流水线，你就看懂了 InstructGPT、ChatGPT 背后的那台「对齐发动机」。

一、四个同框的模型（角色扮演）

RLHF 的 PPO 阶段，同时活在显存里的通常有四个模型：

角色 代号 干什么 是否更新参数
策略模型 Actor (π) 真正生成回答的模型，也是我们要训练的 ✅ 不断变好
参考模型 Reference (π_ref) SFT 后的初始模型，作为「别跑太远」的锚 ❌ 冻结
奖励模型 Reward (RM) 给生成的回答打分 ❌ 冻结
价值模型 Critic (V) 估算「当前状态往后的预期总奖励」，用来算优势 ✅ 和 Actor 一起训练

为什么这么「重」？因为 on-policy（第四章）要求现采现学，而打分、算优势、防塌陷都需要专门的模型。显存占用≈4 个模型，这就是 RLHF 贵的根源。

二、一次迭代的七步

把一次 PPO 更新（一个 mini-batch）拆开看：

第 1 步：采样（Rollout） 用当前 Actor 对一批问题 x，逐词生成回答 y。这一步产生轨迹：x → y₁ → … → y_T。

第 2 步：打分（Reward） 把 (x, y) 送进冻结的 RM，得到整段回答的分数 r。有时还会在每步叠加一个 KL 惩罚项（来自 Reference），奖励变成 r − β·KL，越早偏离参考模型，奖励越低。

第 3 步：算优势（Advantage） 用 Critic 估计每一步的 V(s)，结合结尾的 r，算出每个 token 位置的优势 A_t（第四章）。一句话：这一步选得好不好、比平均好多少。

第 4 步：构造损失 对 Actor，用第五章的裁剪目标 L_PPO（优势×比值，clip 住）；对 Critic，用「它估的 V 与真实回报的误差」做回归损失。两者合在一起反向传播。

第 5 步：小步更新 执行几次（比如 1~4 次）梯度更新，只动 Actor 和 Critic，且受 clip 限制，每次只挪一点点。

第 6 步：同步 Reference / RM Reference 和 RM 全程不动。它们像「评委席」，只打分、不改分。

第 7 步：回到第 1 步 因为 on-policy，更新后的 Actor 已经变了，旧样本失效，必须重新采样再训。如此循环成千上万次。

三、一张「信息流」图（文字版）

问题 x ──▶ Actor 生成 y ──▶ RM 打总分 r │ ▼ Critic 算 V，结合 r 得优势 A │ ▼ Actor/Critic 用 (A, clip, KL) 更新参数 │ KL 项来自 Reference（始终冻结，当尺子） │ 循环，直到收敛

你可以把 Reference 想成「出厂设置相册」，Actor 每动一步都要回头看看：「我离出厂设置是不是太远了？」RM 是「客户满意度评分」，Critic 是「自身对成败的预判」。

四、工程上的真实痛点

  • 显存爆炸：4 个模型同框。常用招数：用 LoRA（只训低秩适配，见 L5）挂在 Actor 上、用 ZeRO/张量并行切分、把 Reference 和 RM 用「参数卸载 / 共享」省显存。
  • 奖励尺度漂移：RM 的分数范围可能不均匀，导致训练信号忽大忽小，需要归一化（如奖励减均值除标准差）。
  • 采样慢：rollout 是逐词生成，是整条流水线最耗时的环节，往往靠大 batch、多卡推理加速。
  • 不稳定：学习率、KL 系数 β、clip 范围 ε 都要精调，否则容易「训崩」或「训不动」。

五、一个常被问的问题：为什么不直接用 RM 监督 fine-tune？

既然 RM 能给分数，能不能像 SFT 那样「让模型直接模仿高分回答」？不行，因为 RM 只给一个总分，它并不告诉你「哪个词、哪句话好」，也没法生成「标准高分回答」给你模仿。RL 的价值，正是通过「试错 + 优势分配」让模型自己摸索出如何持续产出高分回答的策略。

本章小结

  • RLHF 的 PPO 阶段同框 4 个模型：Actor（训）、Critic（训）、Reference（冻）、Reward（冻）。
  • 一次迭代七步：采样 → RM 打分(+KL) → Critic 算优势 → 构造裁剪损失 → 小步更新 → 参考/奖励冻结 → 循环重采样（on-policy）。
  • 信息流：问题→Actor 生成→RM/Critic 评分→Actor/Critic 更新→受 Reference 约束。
  • 工程痛点：显存（4 模型）、奖励漂移、采样慢、超参敏感；常用 LoRA + 并行 + 奖励归一化缓解。
