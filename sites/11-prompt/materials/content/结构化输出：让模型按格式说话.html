结构化输出：让模型按格式说话

为什么需要「按格式说话」

先回忆一下前几章的成果：你已经学会了把话说清楚、给模型设定角色、用例子教它、让它先想再说。现在模型输出的内容质量不错了——但有个新问题：它说话太「随性」了。

你让它提取三条信息，它给你写成一段散文；你让它列个表格，它给你加一堆客套话；你让它输出五个要点，它有时候给你四个、有时候给你六个。作为人，这种小瑕疵忍忍就过去了；但如果你是让程序来读模型的输出（比如自动把模型的结果存进 Excel、发给后台系统、拼进网页），格式一乱，程序就「崩」了。

结构化输出（Structured Output），解决的就是这个问题：在提示词里明确要求模型按指定的格式回答——JSON、表格、固定模板、固定字段——让输出规规整整，可直接被程序解析，也方便人阅读。

一句话概括：普通输出是「让模型自由说话」，结构化输出是「给模型一张有格子的表格，让它一格一格填」。

这一章我们会讲：结构化输出到底是什么、为什么对程序特别重要、怎么用「输出格式字段 + 示例」约束它，以及最常见的 JSON 输出有哪些坑、怎么避。

三种常见的结构化输出形式

先直观感受一下「自由输出」和「结构化输出」的区别。

自由输出（不约束格式）

请总结这份产品评测，提取出产品名、评分、优点、缺点。

模型的回答大概是：

这篇评测讲的是某品牌的降噪耳机，整体评分还行，4 分左右吧。优点是降噪效果不错、佩戴舒服，缺点是续航一般，还有就是价格偏贵。另外还提到了 APP 有点难用……

信息其实都有，但散在一段话里。人要读没问题，程序要「把评分存进数据库」就麻烦了——它不知道该从哪截取。

结构化输出（用表格约束）

请总结这份产品评测，提取出产品名、评分、优点、缺点，用表格输出：
| 项目 | 内容 |

模型的回答就会是：

| 项目 | 内容 |
| --- | --- |
| 产品名 | 某品牌降噪耳机 |
| 评分 | 4 分 |
| 优点 | 降噪效果好；佩戴舒适 |
| 缺点 | 续航一般；价格偏贵；APP 难用 |

一眼看过去清清楚楚，也容易复制到 Excel。这算是「轻量结构化」。

结构化输出（用 JSON 约束）

JSON 是另一种更「硬」的格式。先别被这个词吓到，JSON 就是一段有固定语法规则的文本，长得像「名字: 值」的一串列表，它的好处是电脑程序读取起来非常方便。用 JSON 约束：

请提取下面的信息，输出 JSON 格式，不要输出任何其他内容：
{"产品名": "...", "评分": ..., "优点": ["..."], "缺点": ["..."]}

模型输出：

{
  "产品名": "某品牌降噪耳机",
  "评分": 4,
  "优点": ["降噪效果好", "佩戴舒适"],
  "缺点": ["续航一般", "价格偏贵", "APP 难用"]
}

这种输出可以直接被程序读取，比如存进数据库、渲染成网页、喂给下一个流程。JSON 是「程序眼中的表格」。 常见结构有数组（用方括号 [ ] 括起来的一串值）和对象（用花括号 { } 括起来的「键: 值」集合），后面讲坑的时候会再提。

为什么要结构化：程序解析与二次处理

结构化输出最大的价值，是让模型的输出可以被程序自动消费。举两个真实场景你就明白了。

场景一：批量录入

你经营着一家小店，每天要把几十条顾客留言分类、提取要点。如果让模型一条条自由输出，你得每条手工「翻译」成表格。但如果你让模型按固定格式输出，程序就可以自动把几十条结果合并成一张表，一键导出。

场景二：流水线作业

你搭了一个「AI 工作流」：第一步让模型读合同，第二步把提取的条款喂给另一个程序做风险判断，第三步生成提醒邮件。每一步之间要传递数据，数据格式必须是程序认识的——这时候 JSON 就成了「接口语言」。自由文本在流水线里是没法传的，结构化输出是流水线的「接插件」。

对普通用户而言，结构化输出还有两个顺手的好处：一是可读性——表格比一大段话好看；二是可复现性——要求固定格式，模型每次输出的「骨架」一致，你对比两次结果也更容易。

怎么让模型输出 JSON：格式字段 + 示例双保险

让模型输出 JSON，光靠说一句「输出 JSON」往往不够——它可能给你加一句「好的，以下是 JSON：」之类的废话，或者格式略偏。最稳的做法是「格式字段」和「示例」双管齐下。

第一步：在提示词里写明「输出格式」字段

明确告诉它要输出什么字段、字段叫什么名、什么类型：

请从下面的订单邮件中提取信息，按如下 JSON 格式输出：
{
  "订单号": "字符串",
  "下单日期": "字符串（YYYY-MM-DD）",
  "商品清单": ["字符串"],
  "总金额": "数字（元）",
  "客户姓名": "字符串"
}

把字段名、类型、格式都写死，模型就有了「填表模板」。

第二步：加一条「只输出 JSON」的硬约束

模型最大的坏习惯是「答完还想再寒暄两句」。所以在格式要求后面，加上严格约束：

要求：只输出 JSON，不要输出任何解释、注释、前后缀文字。如果某字段信息不存在，填写 null。

注意「如果某字段信息不存在，填写 null」——这条很关键，它规定了「缺数据时怎么办」，避免模型自作主张编一个假数据填进去。

第三步（可选，更稳）：给一个完整示例

如果要更高的一致性，就示范一条。用 few-shot 的思路给一个「输入→输出」对：

示例：
邮件内容：张伟先生您好，您于 2026-07-01 订购的商品已发货，订单号 A10086，含保温杯 2 个、充电宝 1 个，实付 256 元。
输出：
{"订单号": "A10086", "下单日期": "2026-07-01", "商品清单": ["保温杯", "充电宝"], "总金额": 256, "客户姓名": "张伟"}

模型看到完整范例，格式几乎不会跑偏。这一招的原理，就是上一章 few-shot 示例：用例子教会模型 里讲的「照葫芦画瓢」。

JSON 输出的四个常见坑（以及怎么绕开）

即使写了格式要求，JSON 输出仍然有几个高频翻车点。逐个认识它们，你就能提前避开。

坑一：多余的「前后缀文字」

模型偶尔会在 JSON 前后加「好的，我提取如下：」或「希望对你有所帮助！」。程序读取时，这些前缀会造成解析失败。

  • 绕法：在提示词里明确写「只输出 JSON 本身，禁止任何多余文字」，必要时多强调一遍。

坑二：引号与转义错误

JSON 对引号非常严格：键和字符串值必须用英文双引号 " 包起来，字符串内部再出现引号，要用反斜杠转义（写成 \"）。如果模型输出的字符串里直接带了没转义的引号，比如 "备注": "他说"今天到""，整段 JSON 就坏了。

  • 绕法：遇到「文本里可能带引号、换行、特殊符号」的字段，在提示词里提醒「文本中的引号请用转义字符表示」；更省事的办法是让这类字段尽量短，或干脆不让它输出自由长文本。

坑三：字段缺失或字段名被改

模型可能偷偷改字段名，比如你把 订单号 写死，它输出成 订单ID。程序按原字段名取值，就取不到了。

  • 绕法：格式字段写死 + 给示例；并且要求「字段名必须与要求完全一致，不能增删改」。

坑四：把数字当字符串、或反过来

你要求 "评分": 4（数字），它输出 "评分": "4"（字符串）；或者金额要求字符串它给你数字。类型不对，程序运算时会报错。

  • 绕法：在格式字段里注明类型（数字 / 字符串 / 数组），并在示例里展示正确的类型。

给你一个把这些坑都堵上的「抗坑版」JSON 提示词：

请从下面的文字中提取信息，输出一个 JSON 对象，必须遵守：
1. 字段名严格使用下面的名称，不允许改名、增删字段；
2. 只输出 JSON 本身，禁止任何解释、前缀、后缀文字；
3. 字符串中的引号必须使用转义字符；
4. 缺失的信息填 null，不要编造；
5. 数字字段必须是数字，不要加引号。

格式：
{"项目名称": "字符串", "数量": 数字, "单价(元)": 数字, "备注": "字符串或null"}

文字如下：
【粘贴待提取的文本】

非 JSON 的结构化：表格、清单与固定模板

不是所有场景都需要 JSON。根据「谁来读」决定格式：程序读 → JSON；人读 → 表格或清单。

表格输出模板

请把下面的内容整理成 Markdown 表格，列名为：姓名、部门、入职年份、一句话评价。
要求：不要输出表头以外的任何文字；没有信息的单元格写「未知」。

清单输出模板

请输出 5 条建议，每条占一行，格式为「第 N 条：建议内容」。不要输出序号以外的多余文字。

固定模板输出

请按下面的模板回答，模板外的内容一律不输出：
问题：【我的问题】
我的回答：【一句话结论】
原因：【不超过三句话的理由】
一个反例：如果我的回答是错的，可能是【哪种情况】

「固定模板」的好处是：即便内容质量有波动，骨架永远是同一副，方便你逐项对比和复用。

补充一个实用技巧：固定模板里可以留一个「追问位」，让结构化输出变成「可对话的表单」。比如上面模板的「一个反例」那一栏，如果模型填得模棱两可，你可以接着追问「请把『一个反例』这一栏展开成完整的推导：什么条件下我的结论会失效」。模板负责「骨架统一」，追问负责「细节深挖」，两者配合，既保持了输出结构，又不牺牲内容深度。很多办公场景（比如让 AI 每篇输出「背景—判断—证据—风险」四段）都适合这种「模板 + 追问」的组合拳。

结构化输出的四条经验法则

  • 先想清楚「给谁读」：给人读用表格/清单，给程序读用 JSON。别在给人看的场景里硬塞 JSON，也别把表格喂给程序。
  • 格式要写进提示词，不是靠碰运气：把字段、类型、示例都写清楚，再辅以「只输出格式内容」的硬约束。
  • 给示例永远比纯描述稳：一个完整示例顶得上十句解释，这是 few-shot 在格式任务上的又一次胜利。
  • 留好后路：万一模型格式真的坏了，别慌——你可以把「让它按刚才的格式重新输出一遍」也写成一句提示词（比如「请把上面输出重写成标准 JSON，其他不要」），往往能救回来。

本章小结

  • 结构化输出 = 明确要求模型按固定格式（JSON / 表格 / 清单 / 模板）回答。
  • 核心价值是「可被程序解析」，适合批量录入、流水线作业等场景；对人来说也更好读、更可复现。
  • 让它输出 JSON 的套路：写明格式字段 + 类型 + 只输出 JSON 的硬约束 + 一个完整示例。
  • 四个高频坑：多余前后缀文字、引号转义错误、字段名被改、类型错乱——各有对应绕法。
  • 选格式的口诀：程序读用 JSON，人读用表格/清单。

模型终于「规规矩矩说话」了。但你可能已经想到一个问题：如果输入给模型的内容本身很长很长，比如一整本书、一份几十页的合同，该怎么办？下一章，我们处理「上下文与长文本」。请阅读 上下文与长文本：摘要、切片与分步处理。
