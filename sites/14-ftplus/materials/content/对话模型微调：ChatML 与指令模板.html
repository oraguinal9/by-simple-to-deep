对话模型微调：ChatML 与指令模板

你前面准备的数据是「问题 + 答案」，但训练框架不会直接把两段文字丢给模型。它需要把对话包成模型认识的模板，模型才能学会「谁是用户、谁是助手、从哪开始回答」。这一章把模板这件事讲透。

为什么需要模板

大模型本质是「下一个 token 预测器」。它训练时看到的输入是一长串 token。要让它在推理时表现出「对话能力」，训练数据里就必须明确区分对话的角色边界：

  • 哪部分是用户说的；
  • 哪部分是助手说的；
  • 哪部分是系统提示（可选）；
  • 模型应该从哪个位置开始生成回答。

模板就是干这个的——用特殊标记符把这些边界标出来。

ChatML：最流行的对话模板

ChatML 是 OpenAI 提出的一种模板格式，后被开源社区广泛采用。它的核心是几个特殊 token：

<|im_start|>role
内容<|im_end|>

其中 role 可以是 system（系统）、user（用户）、assistant（助手）。

一个完整的对话长这样：

<|im_start|>system
你是一个乐于助人的中文助手。<|im_end|>
<|im_start|>user
请用一句话解释什么是微调。<|im_end|>
<|im_start|>assistant
微调是指……<|im_end|>

训练时，损失只算 assistant 那一段。模型看到前面的 system + user，要学着续写出正确的 assistant 回答。它不会真的「学会对话」——它学会的是「看到这个模式的输入，接着写下一段」。

关键理解：loss 只算助手回答

这一点极其重要，很多初学者搞错。

如果损失把整段（包括 user 问题）都算进去，模型就只会「复读输入」，失去意义。正确做法是：屏蔽掉 user 和 system 部分的 loss，只让模型预测 assistant 部分。

这对应到训练里就是一个「mask（掩码）」机制。你的训练数据如果已经是完整模板文本，框架通常会自动按模板识别 assistant 段做 mask；如果用原始格式（如 ShareGPT），框架会先把对话转成模板，再 mask。

不同模型的模板不一样

这是最容易踩的坑：每个模型的「官方模板」可能不同。Qwen 有 Qwen 的模板，Llama 有 Llama 的模板，ChatML 只是其中一种。

例如 Llama 系常用：

<|begin_of_text|><|start_header_id|>user<|end_header_id|>

你好<|eot_id|><|start_header_id|>assistant<|end_header_id|>

你好！<|eot_id|>

如果训练用的模板和推理时用的不一致，模型会「乱说话」甚至报错。

铁律：训练模板必须和该模型的 tokenizer 默认模板一致。用 HF 的 tokenizer 加载模型时，tokenizer.chat_template 就是它该用的模板，别自己瞎造。

实操：用 tokenizer 把对话变成训练文本

正确做法是不要手动拼字符串，而是让 tokenizer 帮你转。HF 的 apply_chat_template 就是干这个的：

messages = [
    {"role": "system", "content": "你是一个财务助手。"},
    {"role": "user", "content": "报销截止日期是什么时候？"},
]
text = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False
)

得到的 text 就是符合该模型模板的完整训练样本，你再把它喂给训练器即可。这样模板永远和模型匹配，不踩坑。

系统提示要不要写进训练数据

取决于你的目标：

  • 你的助手始终扮演固定角色（如财务专家）→ 把系统提示写进每条训练数据，让模型稳定记住这个角色；
  • 你的助手要灵活处理各种对话 → 系统提示可以留空，或只加通用的「乐于助人」描述。

经验：训练数据里的 system 越稳定，推理时越可靠。如果你想让它固定当某类专家，就每条都带上那段 system。

模板不对会发生什么：看两个翻车现场

理解「模板必须匹配」最有效的方式，是看模板错了的实际症状：

翻车 1：训练模板和推理模板不一致。 你训练时用 ChatML 把数据包成 <|im_start|>...，但推理时用的基座模型默认模板是 Llama 风格。模型推理时看到的输入和训练时完全不同，回答会：乱码、重复、前言不搭后语，甚至把特殊标记原样吐出来。症状是「训练时 loss 正常，推理时模型像坏了一样」——这时优先怀疑模板。

翻车 2：模板里少了结尾标记。 ChatML 的 <|im_end|> 如果漏了，模型就不知道「这句话说完了」，会一直续写下去，把下一段 user 的内容也当回答生成。症状是「回答停不下来、把问题也复述了」。

排查口诀：先打印 tokenizer.chat_template 和 apply_chat_template 的产物，肉眼确认「和训练数据一致」再开训。

mask 机制：为什么「只算 assistant」如此关键

再深入一点理解 mask。训练时，一个 batch 里的每个位置都有一个「是否参与损失计算」的标记。实现上常见两种：

  1. 数据层面：把 user/system 部分的 label 设成 -100（HF 约定，-100 不参与 loss）；
  2. 模板层面：训练框架解析出 assistant 段，自动屏蔽其他段。

如果你手动拼文本训练，忘了 mask，模型会学到「把用户问题也背下来」，效果会变得很怪（复读机）。所以：

能用框架的自动模板转换，就别手拼；手拼就一定要做 mask。

特殊 token：背后的「哑巴符号」

<|im_start|>、<|im_end|> 这些看着像文本，其实是被 tokenizer 当作特殊 token 处理的——它们有独立 token id，不会被拆成普通字，因此能安全地当「角色分隔符」用，不会和正文混淆。

这也是为什么「自己发明一套分隔符」很危险：如果 tokenizer 不认识你的符号，它会被拆成普通 token，训练时模型学到的边界就乱了。始终用该模型官方定义的特殊 token。

多轮对话：让助手记住上下文

指令微调不止单轮。多轮对话数据的价值是让模型学会「带着历史上下文回答」：

<|im_start|>user
报销怎么申请？<|im_end|>
<|im_start|>assistant
第一步……第二步……<|im_end|>
<|im_start|>user
那需要什么材料？<|im_end|>
<|im_start|>assistant
需要……<|im_end|>

第二问「那需要什么材料？」单独看是残缺的，但模型结合上文知道是在问报销。训练数据里带几轮这样的历史，推理时模型的上下文能力会明显更好。

准备多轮数据的建议： - 每条对话从 2~6 轮不等，别全是单轮； - 多轮里「用户追问」「用户换话题」「用户确认」等真实交互形态都要有； - 推理时的 messages 列表要和训练时的轮数习惯一致。

指令模板 vs 对话模板

还有一类叫「指令微调（instruction tuning）」的数据，有时只有一轮 user/assistant，没有多轮对话。它和对话模板不冲突——指令样本本质就是单轮的对话，用同样的模板包起来即可。

多轮对话数据（多轮 user/assistant 交替）则让模型学会「追着上下文走」，这对客服、助手类应用很有价值。准备数据时如果能带几轮历史，效果往往更好。

小练习

  1. 用 tokenizer.apply_chat_template 把下面这段对话转成文本，观察输出的特殊标记是什么：[{"role":"user","content":"你好"}]。
  2. 为什么「损失只算 assistant 部分」？如果全算会怎样？
  3. 换一个模型（比如 Llama），看看它的模板和 ChatML 有什么不同——用 tokenizer.chat_template 打印出来对比。
  4. 进阶：故意把模板拼错（比如用错结尾标记）训练一个小模型，观察推理时的症状，验证「模板不匹配」的后果。
