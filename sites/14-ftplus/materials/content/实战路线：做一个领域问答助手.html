实战路线：做一个领域问答助手

最后一章，我们把前面 9 章的知识串成一条完整的流水线，亲手做一个「领域问答助手」。我们用「公司财务政策问答助手」作为贯穿例子——你可以换成任何你感兴趣的领域。

目标定义

我们的目标是：让一个开源模型学会用「公司财务政策」的话术和口径回答员工的财务问题，并且答得比通用模型更准、更贴公司规则。

先明确边界（回顾第 1 章的决策表）：

  • 公司财务政策这类私有/最新知识 → 其实更适合 RAG（可检索、可更新）；
  • 固定的话术、口径、输出格式 → 微调更能保证稳定性。

所以一个成熟的方案往往是 RAG + 微调结合：RAG 负责「喂知识」，微调负责「学会话术与格式」。这一章我们重点做「微调」那一半，并说明如何与 RAG 配合。

完整流水线总览

第2章 数据准备      → 整理财务问答对
第5章 指令模板      → 转成 ChatML 格式
第3章 训练          → Unsloth QLoRA 微调
第8章 合并导出      → 合并回基座，导出模型
第9章 评测          → 对比基座 vs 微调
（配合 RAG）       → 让知识实时、可更新
第10章 部署         → 起一个能问答的服务

第一步：构造财务问答数据

从公司的财务 FAQ、员工手册、报销制度里，整理出问答对。示例：

用户：差旅费报销需要什么发票？
助手：差旅费报销需提供合法有效的增值税发票，并附差旅审批单。
     高铁票、住宿发票需为抬头为公司名称的电子发票。具体以最新
     报销制度为准。

用户：报销一般多久到账？
助手：财务部在收到完整单据后 5 个工作日内完成审核，审核通过后
     3 个工作日内打款到工资卡。

要点：答案要准、口径要统一（这是微调要「学会」的）。数量不用多，几百到几千条高质量的即可，再按第 2 章的配比混入少量通用对话防遗忘。

第二步：转成模板文本

用 tokenizer 的 apply_chat_template 把每条问答转成符合你基座模型模板的文本（见第 5 章），存成 JSON，每条的 text 字段就是完整模板文本。这是训练数据。

第三步：用 Unsloth 微调

直接复用第 3 章的最小代码，换上你的财务数据。基座选一个中文表现好的（如 Qwen2.5 系列），用 QLoRA + r=16，先跑小步数验证 loss 下降，再逐步到收敛。

第四步：合并导出

训练完，merge_and_unload() 合并回基座，导出完整模型（第 8 章）。此时你有一个「会用财务话术说话」的模型。

第五步：评测

用训练数据之外的 50 条财务问题评测（第 9 章）：

  • 对比基座 vs 微调的回答，看微调是否真的「更贴财务口径、更少泛泛而谈」；
  • 重点盯忠实度：财务领域答错会误导员工，务必检查有没有编造。

第六步：与 RAG 配合（进阶）

纯微调有个死穴：模型记不住经常更新的政策。政策一改，你就要重新微调。

成熟的落地是「RAG + 微调」双轨：

用户提问
  ├─ RAG 检索：从最新政策文档库检索相关段落（知识实时）
  └─ 微调模型：用学到的「财务话术」组织回答（风格稳定）
  • RAG 负责「知道最新政策」（改文档即可，不用重训）；
  • 微调负责「怎么说话」（话术、口径、格式固定）。

两者配合，既快又准又可维护。这也正是前面 L4/L13 讲 RAG、这一阶段讲微调的意义——它们不是二选一，而是互补。

第七步：部署上线

合并后的模型起一个推理服务（vLLM 或本地 Ollama，见 L10），前端接一个问答界面，一个能用的领域助手就诞生了。

FAQ：领域助手项目最常见的问题

Q1：我该先做 RAG 还是先做微调？ 答：先做 RAG。它不用训练、见效快、可追溯，能先解决「知识准确」这一半问题。如果用了 RAG 之后，发现回答「话术不像公司的人、格式不固定」，再上微调解决「风格」这一半。别一上来就微调——很多项目根本不需要微调。

Q2：微调后回答变笨了（通用能力退化）？ 答：八成是数据配比问题。回第 2 章，把通用对话数据比例提上去（比如 40%+），重新微调。

Q3：微调后还是答错政策问题？ 答：先确认这是「知识问题」还是「表达问题」。政策细节答错 → 是知识问题，应该靠 RAG 喂最新资料，别指望微调记知识；同样的知识、换个说法就答对 → 才是微调该解决的表达问题。

Q4：要不要用更大的基座模型？ 答：如果你的任务在 7B 上已经达到 90 分，换 14B 可能只到 92 分，但成本和延迟翻倍。先在小模型上把数据和流程磨到极限，再决定要不要升。

Q5：多久重训一次？ 答：取决于知识变化频率。政策经常变 → 靠 RAG 更新，不重训；话术口径变了 → 才重训。把「重训」当低频事件，把「RAG 更新」当高频事件。

项目排期模板（给真实项目用）

如果你要在公司里做这个项目，一份务实的时间分配参考（以 2 周为例）：

阶段 时间 产出
需求定义与边界 0.5 天 「哪些靠 RAG、哪些靠微调」决策表
数据收集与清洗 3~4 天 干净的数据集 + 评测集
基线验证（RAG 先行） 1~2 天 RAG 版助手，发现问题清单
微调训练与调参 2~3 天 LoRA 模型 + 多版本对比
评测与迭代 2~3 天 评测报告 + 数据修订
部署与上线 1~2 天 推理服务 + 前端 + 监控

注意：数据 + 评测占了一半以上时间，这是常态，别压缩——压缩它们的项目最后都回来补课。

一次完整的「微调项目复盘」

做完整个实战，你应该对一次微调项目有完整感知：

  1. 先定义边界：哪些靠 RAG，哪些靠微调；
  2. 数据是灵魂：质量 > 数量，口径要统一；
  3. 模板要跟模型：用 apply_chat_template，别手拼；
  4. QLoRA 起步：省显存，效果不差，先跑通再优化；
  5. 合并才能部署：别拿 adapter 直接上线；
  6. 评测定乾坤：拿数据和基座对比，别凭感觉。

从这里再往哪走

微调学到这里，你已经具备独立完成一个微调项目的完整能力。如果想继续深入，几个方向：

  • RLHF / DPO：让模型「更讨人喜欢」——这正是 L6 讲过的内容，微调 + RLHF 是一对组合拳；
  • 多模态微调：给视觉/音频模型做适配；
  • 更长上下文的训练：学会处理超长序列；
  • 更高效的数据工程：数据合成、主动学习。

上线后的监控：别「训完就完事」

模型上线只是开始，还要持续盯三件事：

  1. 效果监控：收集真实用户提问，定期抽样评测回答质量，形成周报；
  2. 知识时效：政策/文档变化时，及时更新 RAG 知识库（不用重训模型）；
  3. 翻车预警：记录「用户明显不满/投诉」的对话，定期复盘是知识问题还是表达问题。

上线 ≠ 结束。一个健康的领域助手是「数据 → 训练 → 评测 → 监控 → 再迭代」的持续循环，微调只是其中的一环。

结语

恭喜你完成「微调实战进阶」全部 10 章。你现在不仅知道怎么调库，更理解了微调的本质是改行为、数据是灵魂、评测是真相。把一个开源模型训练成自己的专属助手，对你来说已经不再是黑盒。

去动手做一个真正属于你的领域助手吧——从你最熟悉、最想解决的领域开始。
