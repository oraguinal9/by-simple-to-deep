评测你的微调模型

「我微调好了，但它到底好不好？」这是最关键也最容易被糊弄的问题。这一章给你一套科学的评测方法：从「拍脑袋看几个例子」升级到「用指标和对照实验说话」。

为什么必须评测

微调的效果不能靠「感觉」。因为：

  • loss 降了 ≠ 模型变好了：loss 是在训练集上的，可能过拟合；
  • 看几个例子有幸存者偏差：你容易挑「表现好」的例子给自己看；
  • 没有对照就没意义：不跟微调前的基座比，你不知道到底改进了什么。

所以评测的核心是：同一套问题，分别问基座模型和微调模型，量化对比。

评测的两大流派

1. 客观指标（能自动化打分）

适合有「标准答案」的任务：

  • 分类/选择题准确率：模型答对了多少；
  • BLEU / ROUGE：生成文本和参考答案的重合度（适合翻译、摘要、抽取类）；
  • F1：信息抽取等任务；
  • 困惑度（perplexity）：模型对数据「有多意外」，越低越好，但仅作参考。

优点：可批量、可复现。缺点：对「开放性对话」评价不全面（一个意思有多种说法，BLEU 会误判）。

2. 主观评测（人工/模型打分）

适合开放性对话、风格、有用性：

  • 人工打分：让人按「有用性、忠实度、流畅度」打分（最可靠但慢）；
  • LLM 打分：用一个强模型（如 GPT / Qwen 大杯）当「裁判」给回答打分（快，但裁判也有偏见）；
  • A/B 对比：把基座和微调的回答匿名放一起，让人/裁判选更好的（最直观）。

一个实用的评测流程

不追求完美，先搭一套「够用」的流程：

1. 准备一个固定的评测集（50~100 条典型问题，覆盖你的场景）
2. 记录基准：用未微调的基座模型跑一遍，得到 baseline
3. 微调模型跑同一份评测集
4. 对比：自动指标（如有）+ 人工/LLM 抽查打分
5. 反复迭代：发现问题 → 修数据 → 重训 → 再评测

关键：评测集必须是训练时没见过的（不能和训练数据重叠），否则测的是「背题」而非「学会」。

评测集从哪来

  • 从你的真实业务问题里抽取（最贴近实际）；
  • 找一部分数据留出来（比如 10%），专门当评测集，不参与训练；
  • 如果担心泄露，可以从公开测试集（如 C-Eval、CMMLU 中文评测）里抽题。

三个一定要盯的维度

不管用什么方法，评测时至少看这三件事：

  1. 有用性（helpful）：回答有没有真的帮到用户，是不是答非所问；
  2. 忠实度（faithful）：有没有编造（幻觉）。微调不是塞知识，若它开始一本正经胡说，要警惕；
  3. 稳定性（consistent）：同一类问题是不是每次都答得差不多，有没有随机抽风。

过拟合怎么在评测中暴露

过拟合的典型信号：训练 loss 一直降、但评测集上指标变差。或者：模型能完美复述训练数据里的答案，但换一种问法就答错。

对策： - 增加通用数据配比（防「背题」）； - 减少训练步数 / 降低学习率； - 检查数据是否在评测集里「穿帮」。

写一个最小的评测脚本

给你一个极简的可扩展框架（用 LLM 裁判示意，可换成人工）：

EVAL_QS = ["你的产品怎么退货？", "解释一下什么是 LoRA。", ...]

def ask(model, q):
    # 用你的推理接口让模型回答
    return ...

base_answers = [ask(base_model, q) for q in EVAL_QS]
ft_answers   = [ask(ft_model,   q) for q in EVAL_QS]

# 用裁判模型打分，或人工逐个比较
for q, ba, fa in zip(EVAL_QS, base_answers, ft_answers):
    better = judge(q, ba, fa)   # 返回 "base" 或 "ft" 或 "tie"
    print(q, "→", better)

统计「微调赢的比例」，就能量化微调的净收益。

客观指标详解：什么时候信、什么时候不信

很多初学者拿到 BLEU/ROUGE 就当「真理」，其实要看清它们的能力边界：

BLEU / ROUGE（文本重合度）： - 可靠场景：翻译、摘要、信息抽取等「有明确标准答案」的任务； - 坑：开放性问答没有唯一答案，一个意思两种说法 BLEU 就很低，会冤枉好模型。比如模型答「报销 5 个工作日内到账」，参考答案写「5 个工作日到账」，措辞略不同就被扣分。

准确率 / F1： - 适合分类、抽取类任务，客观直接； - 需要先定义「什么叫答对」——是包含关键词？还是语义等价？

困惑度（perplexity）： - 模型对「见过的数据」的意外程度，越低越好； - 但困惑度低 ≠ 回答好（模型可能只学会了「说得很顺」而内容空洞），只作参考。

给新手的建议：客观指标能自动化跑，但要搭配「人工抽查」一起看，两者互补。

LLM 裁判：怎么写一个好 prompt

用强模型当裁判，prompt 写得好不好直接影响结果。一个合格的裁判 prompt 至少包含：

  1. 任务定义：你要它比较什么；
  2. 评分维度：有用性、忠实度、流畅度等；
  3. 评分规则：几分制、怎么算赢；
  4. 输出格式：结构化输出（如 JSON），方便统计；
  5. 去偏要求：不知道哪个是微调模型，避免「位置偏好」。

示例裁判 prompt：

你是一个公正的模型评测员。给定用户问题和两个回答，
请从【有用性、忠实度、流畅度】三个维度分别打分（1-5分），
并说明哪个回答更好。不要因为某个回答更长而偏袒它。

用户问题：{question}
回答A：{answer_a}
回答B：{answer_b}

请以 JSON 输出：{"A": 总分, "B": 总分, "winner": "A"或"B"或"tie", "reason": 一句话理由}

注意： - 打乱 A/B 顺序跑两遍，取稳定结果，消除位置偏好； - 裁判模型最好比被评模型强（不然裁判被「震住」）。

人工评测：效率与可靠性的平衡

人工评测最可靠但也最贵。几个实用技巧：

  • 抽样：不用评全部，抽 20~30 条典型问题即可；
  • 匿名双盲：评的人不知道哪个是基座、哪个是微调，避免心理偏见；
  • 多人交叉：两个人评，分歧大的样本单独讨论；
  • 固定标准：先写清楚「3 分 = 什么水平」，避免评分尺度漂移。

一个折中方案：自动指标批量跑 + 人工抽查 20 条 + LLM 裁判跑全部，三层结合，又快又稳。

评测的「黄金三件套」：基线、对照、回归

专业团队做评测会维护三样东西，你也可以从小做起：

  1. 固定评测集：一份不随训练变化的题库，反复使用，用来横向对比不同版本；
  2. 基线记录：每次训练的评测分数都记录在案，形成「版本 → 分数」表；
  3. 回归测试：每次改数据/参数后重跑评测集，防止「修了 A 坏了 B」。

这套「工程化评测」思维，是把微调从「玩票」升级到「产品」的分水岭。

小练习

  1. 准备 20 条评测问题（训练数据之外），分别问基座和微调模型，记录你觉得微调赢了几条。
  2. 设计一个 LLM 裁判的 prompt，让它比较两个回答哪个更好，并测试它是否稳定。
  3. 微调后若发现「学新忘旧」，你回第 2 章找配比问题，还是这里找评测问题？
  4. 进阶：用同一份评测集，分别测「训练前基座」「训练 200 步」「训练 1000 步」三个版本，画出「训练量—分数」曲线，找出过拟合拐点。

评测是微调的「体检」。做完它，你的微调才算真正闭环。最后一章，我们把所有能力串成一个能落地的领域问答助手。
