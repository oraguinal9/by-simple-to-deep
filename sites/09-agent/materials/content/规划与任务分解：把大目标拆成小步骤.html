规划与任务分解：把大目标拆成小步骤

让大模型直接回答「怎么做一个完整的市场调研报告」，它会给你一箩筐正确的废话。但让它真的去做一份报告，它需要先把这件事拆成一步步可执行的动作——这就是规划（Planning）。规划能力，是 Agent 从「玩具」走向「生产力」的分水岭。

为什么必须拆任务

大模型的强项是「一段一段地想」，弱项是「一口吃成胖子」。任务太大时，它会：

  • 目标漂移：做着做着忘了原始需求。
  • 上下文爆炸：所有内容都堆在窗口里，很快超限。
  • 出错难修：一步错，后面全错，找不到病根。

而拆成小任务之后，每一小步都在上下文窗口内、可单独验证、可单独重试——复杂度从「一次想清」降级为「一步步走」。

两种主流规划范式

1. ReAct：走一步看一步（隐式规划）

前面第 3 章讲过，ReAct 不显式列计划，而是每次根据观察结果决定下一步。适合：任务不重、路径不复杂、需要灵活应变。

2. Plan-and-Execute：先计划，后执行（显式规划）

遇到大任务，先让模型生成一份完整计划，再逐步执行，每步可以回头看计划、必要时修订计划：

用户：帮我写一份「新能源汽车市场调研报告」。

计划生成：
  1. 调研市场规模与增长数据（查资料）
  2. 调研主要玩家与竞争格局（查资料）
  3. 调研政策与消费者趋势（查资料）
  4. 整理数据、生成图表
  5. 撰写报告结构并输出全文

执行：
  第 1 步 → 调用 web_search / browse 收集数据
  第 2 步 → ……（发现某数据过时，修订计划，补充查 2026 年最新数据）
  ……
  最后：输出完整报告

对比一下：

维度 ReAct（隐式） Plan-and-Execute（显式）
先有完整计划？ 否，边做边想 是，先列计划
适合任务 简单、路径多变 复杂、多步骤、可预测
长任务稳定性 易漂移 稳定，计划是「锚」
资源消耗 每步都重新想，token 多 计划一次，执行更省
可解释性 看思考记录 直接看计划清单

实战中两者常混合：先 Plan 列大步骤，每步内部再用 ReAct 灵活执行。

拆任务的方法论

自顶向下拆解（Top-Down）

大目标 → 中任务 → 小动作，层层分解。比如「订杭州两日游」：

订杭州两日游
├── 行：查高铁票 → 订票
├── 住：查酒店 → 比价 → 订酒店
├── 玩：查天气 → 排景点（室内/室外）→ 排时间线
└── 汇总：生成行程单 → 发给用户确认

反思与修订（Reflection）

计划不是一成不变的。执行中发现新情况（下雨了、没票了、超预算了），Agent 要能更新计划。这一步通常靠「再问一次模型」：

System: 你的执行遇到了新情况，请重新评估计划，需要修改吗？
Observation: 原计划第 2 步的酒店已满房。
Thought: 换同价位备选酒店，或建议用户调整预算。
Action: search_hotel[备选条件] → 修订计划第 2 步。

状态管理（State）

每完成一步，把结果写进「工作记忆」——一个结构化的状态对象（JSON），让计划、已完成步骤、待办一目了然：

{
  "goal": "订杭州两日游",
  "plan": ["查票","订酒店","排景点","汇总"],
  "done": ["查票"],
  "current": "订酒店",
  "notes": { "天气": "周六小雨" }
}

有了状态，Agent 中途被打断也能接着干，不会「忘事」。

几个工程小技巧

  1. 计划要可验证：每步目标写得「能判断完成没完成」，比如「收集 5 条 2026 年销量数据」而不是「收集数据」。
  2. 限制步骤数：超过 N 步就停下来问用户，避免死循环烧钱。
  3. 超时与重试：一步失败重试 1~2 次，还失败就跳过或上报。
  4. 大任务先「侦察」：先快速查一遍资料再定计划，比空想计划靠谱。

本章小结

  • 任务太大必须拆，拆解让复杂度可控、可验证、可重试。
  • 两种范式：ReAct（隐式，边做边想）vs Plan-and-Execute（显式，先计划后执行），复杂任务常两者混合。
  • 拆解三件套：自顶向下分解、反思修订计划、状态管理（JSON 记录进度）。
  • 工程技巧：计划可验证、限步数、超时重试、先侦察后规划。
