大模型如何调用工具：Function Calling 原理

上一章说，Agent 的「手脚」是工具。但这里有个看似矛盾的问题：大模型本质上是一个预测下一个词的程序，它连 2 加 3 都算不对（不信你直接问它复杂一点的四则运算），怎么可能真的去查天气、发邮件、访问数据库？

答案是：大模型并不真的执行工具，它只是「说出」自己想调用哪个工具、传什么参数，真正动手的是外部程序。

这个过程，业界叫 Function Calling（函数调用），也叫 Tool Use（工具使用）。

三步走：描述 → 选择 → 执行

第 1 步：把工具「描述」给模型

模型怎么知道有哪些工具可用？因为我们在发给它的请求里，附上了每个工具的结构化说明书（JSON Schema）：

{
  "name": "get_weather",
  "description": "查询指定城市的实时天气，返回温度、天气状况",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名，如 北京" }
    },
    "required": ["city"]
  }
}

注意 description 要写得清清楚楚——模型就靠这句话判断「什么时候该用我」。写得好，选得准；写得含糊，模型就瞎选。

第 2 步：模型输出「调用意图」，而不是真去执行

你问「北京今天冷不冷？」，模型不会真的联网，它只是返回一段结构化指令：

{
  "tool_calls": [
    {
      "name": "get_weather",
      "arguments": { "city": "北京" }
    }
  ]
}

关键理解：模型输出的是「意图」，不是「结果」。 它说「我想调用 get_weather(北京)」，然后停住，等你把结果喂给它。

第 3 步：外部程序执行，结果喂回模型

你的程序收到上面的 tool_calls，自己去调用天气 API，拿到真实结果：

{ "city": "北京", "temperature": 12, "condition": "多云" }

再把结果作为一条新消息发给模型：

用户：北京今天冷不冷？
助手：我想调用 get_weather 查一下。（tool_calls）
工具结果：北京 12°C，多云。
助手：北京今天 12°C，多云，体感偏凉，建议穿件外套出门。

模型看到工具返回的真实数据后，才给出最终回答。整个过程就像：顾问（模型）开药方，护士（你的程序）抓药，抓完把药拿回来给顾问确认。

一个完整的时序图

你 (用户)                    大模型                     你的程序               天气 API
  │  提问「北京冷不冷」          │                          │                    │
  │ ─────────────────────────>  │                          │                    │
  │                             │ 返回 tool_calls           │                    │
  │                             │ ─────────────────────────>│                    │
  │                             │                          │ 请求天气            │
  │                             │                          │ ──────────────────>│
  │                             │                          │ <── 真实数据 ───────│
  │                             │ <── 工具结果（工具消息） ──│                    │
  │                             │ 结合结果生成最终回答        │                    │
  │ <── 最终回答 ─────────────────│                          │                    │

为什么不能直接让模型联网

有人会问：那为什么不直接给模型联网权限？原因有三：

  1. 安全：如果模型能自己访问任意网站、执行任意代码，它就失控了——万一它执行了 rm -rf？把「决策权」和「执行权」分开，工具由你控制，风险就可控。
  2. 可控性：每个工具都是你精心封装的接口，模型只能按你定义的参数调，不能乱来。
  3. 可审计：模型调用了什么工具、传了什么参数、工具返回了什么，全部有记录，出了问题能追责。

多工具 + 循环调用

真实 Agent 通常不止一个工具。比如一个「订票助手」可能有 5 个工具：查航班、查酒店、下单、查余额、发邮件。模型会根据问题选最合适的，而且常常要连续调多次：

问：帮我把下周三北京到上海的高铁订了，再订个虹桥附近的酒店。
→ 调用 search_train(北京→上海, 下周三)     // 第 1 次调用
→ 拿到车次列表，选出 9:00 那班
→ 调用 book_train(车次 G123)               // 第 2 次调用
→ 调用 search_hotel(虹桥附近)               // 第 3 次调用
→ 调用 book_hotel(酒店 A)                  // 第 4 次调用
→ 汇总行程单发给用户

每一次「调用 → 拿到结果 → 再决定」，就是 Agent 工作循环的一拍。这个「想一步、做一步、看一步」的循环，正是下一章的主角——ReAct 框架。

本章小结

  • 大模型不真执行工具，它只输出「调用意图」（tool_calls）。
  • 工具要先用 JSON Schema 描述清楚，description 是模型选工具的依据。
  • 执行权在外部程序手里，结果作为「工具消息」喂回模型，模型再给最终回答。
  • 多工具 + 连续调用，构成了 Agent 干活的基本节拍。
