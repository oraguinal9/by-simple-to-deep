ReAct 框架：思考-行动-观察的循环

上一章我们看到，Agent 干活的节拍是「调用工具 → 拿结果 → 再决定」。这个节拍的规范化版本，就是 2022 年由谷歌研究者提出的 ReAct 框架——这个名字是 Reasoning（推理）和 Action（行动）的组合。

ReAct 的核心思想只有一句话：让模型一边想、一边做、看着结果继续想，像人解决问题一样。

ReAct 的三种动作

在 ReAct 里，模型每一步都输出三样东西之一：

动作 含义 例子
Thought（思考） 分析现状，决定下一步 「用户想去杭州，先查天气决定行程」
Action（行动） 调用某个工具 「Action: get_weather[杭州]」
Observation（观察） 看到工具返回的结果 「Observation: 周六小雨 18°C」

循环就是：Thought → Action → Observation → 新的 Thought → …… → 直到得出结论（Final Answer）。

一个完整的 ReAct 例子

我们用「北京的天气适合穿什么」走一遍：

Question: 北京明天适合穿什么？

Thought 1: 我需要知道北京明天的天气，才能给出穿衣建议。
Action 1: get_weather[北京]
Observation 1: 明天多云，最高 10°C，最低 2°C，北风 4 级

Thought 2: 10°C 且风大，体感会很冷，建议穿厚外套。
Action 2: 不需要再查了，直接回答。
Final Answer: 北京明天 2~10°C、北风 4 级，体感偏冷，建议穿羽绒服或厚大衣，注意防风。

注意第 2 步的 Thought：模型看了结果之后改变了思路——它发现温度低，于是得出「穿厚」的结论。如果没有 Observation 这一步，它就只能瞎猜。

为什么 ReAct 有效

1. 减少幻觉（一本正经地胡说八道）

模型参数里存的知识可能过时、可能记错。ReAct 逼它先查证再回答：关键事实从工具的真实返回里来，而不是凭记忆编。

2. 可追踪、可解释

每一步的 Thought / Action / Observation 都记录在案。出了错，你能回放 Agent 的「心路历程」，知道它哪一步想岔了。

3. 能自我纠错

工具返回「查询失败」或「数据不对」，模型看到 Observation 后可以换一种方式重试，而不是硬着头皮往下编。

用代码感受一下

下面是最简版本的 ReAct 循环（伪代码），逻辑极其朴素，但已经具备了 Agent 的灵魂：

while True:
    # 1. 让模型基于当前对话历史，输出下一步（Thought/Action 或最终答案）
    step = llm.generate(prompt + "\n".join(history))

    if step 是 Final Answer:
        print(step)          # 收工
        break

    if step 是 Action:        # 例如 Action: get_weather[北京]
        tool_name, args = parse_action(step)
        result = call_tool(tool_name, args)   # 真·执行工具
        history.append("Observation: " + str(result))   # 观察结果

就这么简单——一个 while 循环，就是 Agent 的心脏。真正工程化的 ReAct 无非是在这个循环外面加上安全、记忆、错误处理、多工具注册等包装。

ReAct 的局限

ReAct 不是银弹，主要有三个短板：

  1. 慢：一步一停，来回折腾，复杂任务可能要几十次调用，成本高、延迟大。
  2. 规划能力有限：遇到特别复杂的任务，ReAct 这种「走一步看一步」的方式容易走岔路，需要更强的规划机制（后面第 6 章会讲 Plan-and-Execute）。
  3. 上下文膨胀：思考记录会越来越多，挤占上下文窗口（第 5 章「记忆与上下文管理」专门讲这个问题）。

本章小结

  • ReAct = 思考（Thought）+ 行动（Action）+ 观察（Observation）的循环，直到给出最终答案。
  • 核心价值：先查证再回答（减少幻觉）、全程可追踪、能自我纠错。
  • 一个 while 循环就是 Agent 的骨架，工程化只是在它外面加包装。
  • 局限：慢、长任务规划弱、上下文会膨胀。
