记忆与上下文管理：让 Agent 记住过去

一个没有记忆的 Agent 是什么样？你昨天让它记住「我的预算上限 3000 元」，今天它订机票时照样给你订 5000 的头等舱——因为它「失忆」了。

记忆（Memory）是 Agent 四大件之一，也是工程上最容易出问题的一环。这一章我们把记忆拆开讲清楚。

两种记忆：短期与长期

像人一样，Agent 也有两套记忆系统：

维度 短期记忆（上下文窗口） 长期记忆（外部存储）
存在哪 当前发给模型的那一堆 token 向量数据库 / 普通数据库 / 文件
时长 一次任务内（几秒到几小时） 跨任务、跨天、跨月
容量 有限（上下文窗口，几千到几百万 token） 几乎无限
丢失成本 一结束任务就丢 精心维护，长期保留
例子 这次对话的问答、工具调用记录 「用户预算 3000」「用户常去杭州」

上下文溢出的问题

短期记忆就是上下文窗口——模型一次能「看到」的文字上限。Agent 跑长任务时，思考记录、工具返回、多轮对话会越来越多，最终挤爆窗口。挤爆之后怎么办？常见的粗暴做法：

  1. 截断：把最旧的历史砍掉 → 模型忘了开头，行为漂移。
  2. 压缩：用另一个模型把历史「摘要」成几句话 → 细节丢失。
  3. 滑动窗口：只保留最近 N 轮 → 长任务前后脱节。

这些都是「兜底方案」。聪明的 Agent 用长期记忆来补：重要信息落盘，需要时再取回，而不是把一切堆在窗口里。

长期记忆的经典做法：向量库 + 检索

「记住用户预算 3000」这样的信息，放进普通数据库用 SQL 查也行。但 Agent 的记忆更多是自然语言的、模糊的、需要「凭印象召回」的，于是业界主流做法是：

向量数据库 + 语义检索，流程四步：

  1. 写入（Embedding）：把一条记忆文本转成一组数字向量。语义相近的文本，向量也相近。
  2. 存储：向量连同原文一起存进向量库（Chroma、Milvus、Qdrant、pgvector 等）。
  3. 检索（Recall）：把当前问题也转成向量，在库里找「最相似」的若干条记忆。
  4. 注入：把命中的记忆文本拼进上下文，让模型「想起来」。
# 示意：写一条记忆
memory.add("用户喜欢住高铁站附近的酒店，预算 3000 以内")

# 示意：用户问「订个杭州的酒店」，先召回相关记忆
hits = memory.search("杭州 酒店 预算")
# 命中: ["用户喜欢住高铁站附近的酒店，预算 3000 以内"]
# 再把 hits 拼进系统提示或上下文

直观理解：向量库就像你脑中的「联想索引」——想起「订酒店」时，自动连带想起「预算 3000」「爱住高铁站附近」。

记忆的类型：不止「记住事实」

工程上记忆还分得更细：

  • 短期记忆：本次任务的对话历史（就在上下文里）。
  • 工作记忆：任务进行中的中间结果、待办清单（常结构化存储，比如一个 JSON 状态）。
  • 长期记忆：用户画像、偏好、历史任务结果（向量库/数据库）。
  • 情景记忆：每次任务的完整记录（日志，用于回放和审计）。
  • 程序性记忆：Agent「会做的技能」——比如你教会它「订票前先确认预算」，可复用的流程。

一个成熟的 Agent 框架（LangGraph、Mem0 等）会把这些记忆分层管理。理解分层，你就能设计自己的记忆方案。

记忆管理的三个工程原则

  1. 重要信息主动落盘：不要等上下文爆了才想起来存。关键事实（用户偏好、任务结论）在发生时就写入长期记忆。
  2. 检索结果要「新鲜」：记忆会过期（预算可能变、口味可能改）。写入时记时间戳，检索时优先近期内容，并允许用户主动纠正。
  3. 记忆要可控可删：用户有权查看、修改、删除 Agent 记下的关于自己的信息（隐私合规要求，也是信任基础）。

本章小结

  • 短期记忆 = 上下文窗口，有限且会溢出；长期记忆 = 外部存储，靠向量库 + 语义检索。
  • 上下文溢出有三招兜底：截断、压缩、滑动窗口——但都不如「重要信息落盘」实在。
  • 向量库四步：Embedding → 存储 → 语义检索 → 注入上下文。
  • 记忆分类型：短期/工作/长期/情景/程序性，框架帮你分层管理。
  • 三条原则：主动落盘、检索要新鲜、记忆可删可控。
