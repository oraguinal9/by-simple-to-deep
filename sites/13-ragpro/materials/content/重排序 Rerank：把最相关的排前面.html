重排序 Rerank：把最相关的排前面

上一篇我们把混合检索跑通了，用户问"年假几天"，系统召回 50 个块，其中确实有正确的那块——但它排在第 17 位。如果直接把这 50 块都塞给大模型，模型会迷失；如果只取前 5 块，正确的可能被漏掉。怎么把"对的"从第 17 位挪到第 1 位？这就是重排序（Rerank）要解决的问题。

6.1 一个直觉：初筛要宽，精排要严

想象你在参加一个海选面试。海选（初筛）阶段，评委（便宜的快速模型）在 1000 个人里快速挑出 50 个"看着有潜力"的，标准宽松、速度飞快——宁可多放进几个，也别漏掉一个。到了复试（精排）阶段，评委换成最严格的专家（更贵但更准的模型），对着这 50 个人仔细考察，挑出最终要录取的 5 个。

RAG 的检索流程完全复刻了这个逻辑：

第一阶段（召回）         第二阶段（精排）
全库 10 万块                 候选 50 块
   │                          │
   ▼                          ▼
粗筛出 Top-50               精排出 Top-5
工具：向量检索/BM25         工具：Rerank 模型
特点：快，宁多勿漏         特点：准，逐对细比

这就是两阶段检索（Two-stage Retrieval）。它解决的核心矛盾是：又快又准不可兼得。召回阶段的模型为了速度，只能做"粗糙的近似匹配"；而精排阶段只处理 50 个候选，可以用更精细的模型慢慢比。

6.2 为什么召回模型做不了精排的活？

很多人会问：向量检索不是已经能算相似度了吗？让它精排不行吗？答案是：召回模型和重排模型，天生分工不同。

召回模型（Embedding 模型）的工作方式：把查询和文档各自压缩成一个向量，再算两个向量的相似度。问题在于——"各自压缩"这一步会丢信息。想象两个人分别把各自的高中生活浓缩成一段自我介绍，再对比两段介绍判断"他们是不是校友"，你大概率判不准。真正的校友判断，需要把两份材料放一起逐条比对。

重排模型（Cross-encoder 交叉编码器）就是这么干的：把查询和文档拼接成一个整体，一起送进模型，让模型"对着看"到底相不相关。信息不丢，但代价是慢——所以它只能处理少量候选。

一句话记住分工：Embedding 是"分别编码再比方向"，快但粗；Rerank 是"放在一起细细看"，准但慢。 一个负责海选，一个负责终审。

6.3 Rerank 模型原理：一句话版本

以开源社区最常用的 BGE-reranker（如 BAAI/bge-reranker-v2-m3）为例，它的原理可以浓缩成一句话：

把查询和候选文档拼成一个句子对，作为一个整体喂进一个能输出"相关程度分数"的模型，模型直接给出 0–1 的相关分。

和 Embedding 模型最大的区别就一个：查询和文档永远"同框出现"。正因为同框，模型能捕捉到"这个词在查询里是重点、在文档里恰好也重"这类精细关系，精度自然高出一截。

使用示例（sentence-transformers 一行代码能跑）：

from sentence_transformers import CrossEncoder

# 加载中文 rerank 模型
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

# 候选：混合检索召回的前 50 个块
candidates = ["员工每年可休 5-15 天年假……", "员工福利包括体检、班车……", ...]
query = "年假有几天？"

# 逐对打分：模型对每个 (查询, 文档) 对输出一个相关分
pairs = [[query, doc] for doc in candidates]
scores = reranker.predict(pairs)

# 按分数从高到低排序
ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
for i, (doc, score) in enumerate(ranked[:5], start=1):
    print(f"第 {i} 名 分数 {score:.3f}：{doc[:30]}...")

注意：rerank 的输入是查询和每个候选块的"配对"，所以 50 个候选就要做 50 次配对打分。这就是它"慢"的原因——也解释了为什么它只能处理小候选集。

6.4 完整的两阶段流程

把前几篇串起来，一个标准的"先召回后重排"流程长这样：

① 用户问题："年假有几天？"
② 召回：混合检索（向量 + BM25）从 10 万块里捞出 50 个候选块
③ 精排：bge-reranker 对 50 个 (问题, 块) 对打分
④ 截断：保留 Top-5（得分高于阈值的那几个）
⑤ 使用：把 Top-5 拼进上下文，交给大模型生成答案

第 ④ 步有两个工程细节值得展开：

细节一：为什么是 50 → 5？ 50 是"宁多勿漏"的召回量，5 是"足够回答问题"的上下文量。数字可以调，但逻辑要守住：召回的候选数应远大于最终使用的块数。如果召回 5 个直接就用，等于没给精排留机会。

细节二：要不要设分数阈值？ 如果某个问题检索质量很差，50 个候选的 rerank 分数普遍低于 0.2，说明库里可能根本没有答案。这时应该启动"承认不知道"机制，而不是硬塞一个最差的块给模型编。这个机制的具体实现，第 7 篇会讲。

细节三：rerank 分数的解读。 要注意，不同 rerank 模型的分数分布不一样：有的集中在 0.5–0.9，有的偏紧、普遍只有 0.1–0.3。所以阈值不能照抄网上的数值，要先跑一批已知好坏的问题，看分数分布再定阈值。比如跑 20 个问题，发现"正确答案"最低也有 0.45，而"错误候选"最高到 0.3，那阈值设在 0.35–0.4 之间比较合理。阈值是测出来的，不是猜出来的。

细节四：候选块的"新鲜度"问题。 rerank 打分只看文本本身，不知道文档的新旧。如果库里同时有 2021 版和 2024 版制度，rerank 可能把旧版排在前面。解决思路：在元数据里带上"版本号/生效日期"，在合并阶段做加权偏置（旧版块分数 × 0.9，新版 × 1.1），或直接过滤掉已废止版本。别指望 rerank 自己知道哪个版本有效。

6.5 一个示例：重排前后的差距

用一个直观的例子看差距。假设候选里有两个块：

块 X：公司年假按工龄计算，满 1 年 5 天，满 3 年 10 天，满 5 年 15 天。
块 Y：年假未休完的部分，可以顺延到次年 3 月底，逾期作废。

用户问："年假可以顺延吗？"

阶段 块 X 的排名 块 Y 的排名
向量召回（初排） 第 2 名（因为都提到"年假"） 第 4 名
BM25 召回 第 6 名 第 3 名
混合融合后 第 2 名 第 3 名
Rerank 精排后 第 9 名（掉出 Top-5） 第 1 名（正确，胜出）

看到区别了吗？向量检索看到"年假"就兴奋，把块 X 抬得老高；但用户真正问的是"顺延"，只有 rerank 能识别出"顺延"这个意图只有在块 Y 里才被正面回答。重排的价值，就是把"字面上相关"和"实际上相关"区分开。

这就是为什么企业级 RAG 一定要加 rerank 这一层：它能显著减少"答非所问"，让大模型拿到的上下文是"真相关"而不是"表面相关"。

6.6 重排的开销与取舍

诚实地讲，rerank 不是没有代价的。三个取舍要点：

  1. 计算开销：50 次配对打分，一次问答大约额外花 0.1–0.5 秒。对绝大多数企业内部问答（对延迟不敏感）完全可接受；如果做高并发，可以缩小召回数（比如 30）或用更小的 rerank 模型。
  2. 模型选择：bge-reranker-v2-m3 是当下中文开源标杆，需要兼顾英文可加 m3 版本；对部署资源紧张的小团队，bge-reranker-base 更轻。闭源 API 选择：如果允许上云，Cohere Rerank、Voyage rerank 效果也很好，但要注意数据合规。
  3. 什么时候可以不加：如果你的知识库只有几百条问答对、问题类型极其固定，向量检索可能就够用了。rerank 是"质量放大器"，不是"必需件"——数据量大、问题开放、错误代价高时，它才必须上场。

6.7 Rerank 模型对比与选型

除了 BGE-reranker，市面上还有几个主流选择，这里列一张对比表，方便你按预算和场景挑：

模型 类型 中文效果 部署方式 一句话评价
BAAI/bge-reranker-base 开源，本地 良 本地，轻量 资源紧张团队的入门选择
BAAI/bge-reranker-v2-m3 开源，本地 优 本地 中文场景综合首选
jina-reranker-v2 开源，本地 良 本地 多语种，性能不错
Cohere Rerank 3 闭源 API 优 云端 API 效果一流，注意数据出境合规
Voyage rerank-2 闭源 API 优 云端 API 同上，需权衡合规与成本

选型的三条实用标准：

  1. 数据敏感就先看开源：法务、薪酬、客户资料，一律本地部署 bge-reranker-v2-m3，别为了一点精度把数据送出去。
  2. 以实测为准：拿第 9 篇的评测集，把候选模型各自跑一遍，对比 MRR（平均倒数排名）。多花半天实测，好过纠结三个月参数表。
  3. 别忽视速度：rerank 模型的大小直接决定响应时间。并发高、要求秒回的场景，选 base 级；内部工具、能接受 2–3 秒的，选 v2-m3 级。

6.8 重排的替代方案：让 LLM 自己排？

你可能听说过另一种做法：不训练 rerank 模型，而是让大模型直接对候选块排序。把 50 个块编号列出来，问大模型"哪些最相关？按相关度排序"。这种做法在某些场景下效果不错，但它有两个硬伤：

LLM 排序的代价：
① 慢且贵：50 个块全塞进一次调用，输入 token 暴增，成本和延迟都上去了
② 不稳定：大模型排序的"心智"不如专门训练过的 rerank 模型稳，
   偶尔会把不相关的块排到前面，难以复现和评测

相比之下，bge-reranker 是专门为"给文本对打分"训练的模型，速度比 LLM 快一个数量级，打分行为可预期。所以业界的主流共识是：常规场景用专门 rerank 模型；LLM 排序只作为没有合适 rerank 模型时的保底方案。省下的推理成本，拿去调别的环节收益更大。

6.9 重排环节的调优清单

如果你的系统加了 rerank 但效果不明显，按这个清单逐项排查：

排查项 怎么做 常见问题
候选集够不够 确认召回是 Top-50，不是 Top-5 召回太少，精排没有发挥空间
查询是否改写 用了第 7 篇的问题改写吗 口语问题直接进 rerank，打分失真
分数阈值 是否按 Top-1 分数做"无答案"判断 阈值太高误杀、太低漏编
块内容质量 抽查候选块本身干净吗 解析坏掉的块，再排也是垃圾
模型版本 是否用了 bge-reranker-v2-m3 base 级在难问题上略吃力
分数分布 打印一批问题的 rerank 分数分布 全部挤在 0.5 附近说明区分度差

一个反直觉的提醒：rerank 不是加得越多越好。如果你们的用户问题高度同质、知识库很小，rerank 的提升可能只有一两个百分点，而它带来的延迟却是实打实的。先用评测集验证"加 rerank 前后 MRR 的差距"，差距大就加，差距小就先不加——一切以数据为准。

6.10 Rerank 的部署与成本实操

如果你决定上 rerank（多数企业知识库最终都会上），这里给一份务实的部署参考：

部署形态。 bge-reranker 可以通过 sentence-transformers 或 FlagEmbedding 库直接加载运行。生产上建议用独立的推理服务（例如 Flask 包一个 HTTP 接口），和主链路解耦——rerank 挂了不至于拖垮整个问答：

# rerank 服务（简版）
from flask import Flask, request, jsonify
from sentence_transformers import CrossEncoder

app = Flask(__name__)
model = CrossEncoder("BAAI/bge-reranker-v2-m3")

@app.post("/rerank")
def rerank():
    data = request.get_json()
    query, docs = data["query"], data["docs"]
    scores = model.predict([[query, d] for d in docs])
    return jsonify({"scores": scores.tolist()})

批量预排序。 如果你的知识库有大量"标准问题"（如 FAQ 库），可以提前把"每个标准问题 × 相关块"的分数算好缓存，用户问到时直接查缓存。这能把 rerank 的在线开销降到接近零——代价是需要维护缓存与文档的同步。

成本估算。 50 个候选的 rerank 一次调用，在普通 CPU 上大约 0.2–0.8 秒，在 GPU 上更快。如果每天问答量在几千次，这个开销完全可以接受；如果每天几十万次，就需要考虑缓存、缩小候选集或换小模型了。先按需上线，再按量优化，别提前为不存在的并发买单。

6.11 本篇小结

  • 检索分两阶段：召回（快、宽、Top-50）→ 重排（准、严、Top-5）。
  • Embedding 是"分别编码再比方向"，Rerank 是"同框细比"——精度更高但更慢，所以只精排小候选集。
  • 中文场景首选 bge-reranker-v2-m3，开源、可本地部署。
  • 重排分数太低时，说明库里没答案，要触发"承认不知道"机制。

现在，检索这条链路全部打通了。下一步，把这些环节组装成一个完整的问答系统，处理"问题怎么改、上下文怎么拼、答案怎么给引用"——这就是第 7 篇《RAG 问答链路》。
