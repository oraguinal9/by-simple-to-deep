RAG 问答链路：从检索到回答的完整流程

前面的五篇文章，我们像搭积木一样一块块准备好了：文档解析、分块、Embedding、向量库、混合检索、重排序。这一篇，要把所有积木拼成一个能真正问答的系统——也就是完整的 RAG 问答链路。你会看到：问题进来之后，系统在后台悄悄做的那一连串动作，以及为什么每一步都缺不得。

7.1 全景链路：一个问题的一生

用一个生活化的比喻开场。你去政务大厅办事，柜台的办事员（大模型）很热情，但他不知道你家的情况，也没法记住所有政策。你交上问题后，真正专业的系统是这样运转的：

  1. 问题改写：你的问题可能说得含糊，系统先帮你把问题"翻译"成更利于查资料的说法。
  2. 混合检索：系统同时用"关键词"和"语义"两套办法，在政策库里翻找相关材料。
  3. 重排序：翻出一堆材料后，按"哪份最可能解答你的问题"重新排个序，只留最相关的几份。
  4. 拼上下文：把这几份材料整齐地摆到办事员桌上，附上一句"只准用这些材料回答"。
  5. 生成：办事员看完材料，给你一份有凭有据的回答。
  6. 引用：回答末尾标注"本答复依据《XX 政策》第 3 条"，你随时可以回去核对。

流程图画出来就是：

用户问题
   │
   ▼
① 问题改写（Query Rewrite）── 改写：消歧、补全、拆解
   │
   ▼
② 混合检索 ──► BM25 路（关键词）──┐
   │           向量路（语义）  ────┴─► 合并（RRF）→ Top-50
   │
   ▼
③ 重排序（Rerank）── Cross-encoder 逐对打分 → Top-5
   │
   ▼
④ 上下文拼装 ──► Prompt 模板 + 检索到的块 + 元数据
   │
   ▼
⑤ LLM 生成 ──► 基于给定上下文回答
   │
   ▼
⑥ 答案 + 引用来源（文档名、页码、块内容）

7.2 第一步：问题改写（Query Rewrite）

很多人忽略这一步，但它直接影响检索质量。用户的原始问题常常"不适合检索"：

  • 太口语："那个年假的事，公司咋规定的来着？" —— "那个""咋"都是噪声。
  • 有指代："上面那条提到的 4.3 款，和后面冲突吗？" —— "上面那条"是什么？系统不知道。
  • 太宽泛："说说安全制度。" —— 范围太大，检索会返回一堆乱七八糟的块。

问题改写就是用一个小模型（或大模型本身）把问题加工一下：

rewrite_prompt = """你是检索助手。请把用户的提问改写成一个：
1) 简洁的；2) 含有关键专有名词的；3) 便于在知识库中检索的查询。
只输出改写结果，不要解释。

用户提问：{question}"""

query = llm.chat(rewrite_prompt.format(question=raw_question))
# 示例输出："公司的年假政策，特别是年假天数与未休处理规定"

改写不是必需的，但成本极低、收益明显。对口语化严重的内部问答场景，强烈建议加上。高级的改写还能做多路改写（拆成"年假天数"和"年假未休"两个子问题分别检索，再合并结果），覆盖更全面。

7.3 第四步：上下文拼装技巧

检索到的 Top-5 块怎么"喂"给大模型，是有讲究的。拼装的核心目标是：让模型只信上下文、别乱编、还能给出引用。

一个可靠的中文 Prompt 模板长这样（呼应 L11 的提示词设计）：

【系统指令】
你是一个企业知识库问答助手。你的知识完全来自下面提供的参考资料，
绝不允许使用参考资料之外的信息作答。

规则：
1. 只依据参考资料回答，资料里没有的信息，明确回答"资料中未找到"。
2. 回答要简洁、分点，直接给出结论。
3. 每句话末尾用【来源】标注出处：文档名 + 页码。
4. 多个资料互相矛盾时，如实说明矛盾，不要强行调和。

【参考资料】
[来源：员工手册，第 12 页]
{块1 的内容}

[来源：员工手册，第 13 页]
{块2 的内容}

[来源：休假制度 2024 版，第 5 页]
{块3 的内容}

【用户问题】
{改写后的查询}

拼装时的四个实战技巧：

  1. 每块都带元数据标签（来源、页码、标题）——这是"引用"能实现的根基，在第 2 篇我们已经存下了这些信息。
  2. 控制块数：默认 5 块，每块 400 字左右，上下文总量别超模型窗口的 1/4，留出思考空间。
  3. 按相关度排序拼接：最相关的块放最前面。模型对"前面内容"注意力更强，这能提升命中率。
  4. 块之间加分隔符（--- 或编号），避免块边界混淆，让模型分清"这是一份资料结束、另一份开始"。

7.4 "检索不到就承认"的工程实现

这是企业知识库的尊严所在：宁可说"不知道"，也不许编。工程上至少有三道保险：

第一道：Rerank 分数阈值。 在拼上下文之前，检查 Top-1 块的 rerank 分数。低于阈值（如 0.3）就判定"库里无答案"：

if top_score < 0.3:
    return "抱歉，知识库中暂未找到与该问题直接相关的内容。\
您可以换个说法再问，或联系知识库管理员补充资料。"

第二道：Prompt 指令约束。 就是上面模板里的规则 1："资料里没有的信息，明确回答'资料中未找到'"。指令约束不是万能的，但它能把"编造"的概率大幅压下去。

第三道：生成后的忠实度校验。 在答案返回给用户前，用一个小模型（或规则）检查答案的每一句，是不是都"能在参考资料里找到依据"。找不到依据的句子打上标记或直接删掉。这道防线最严，第 9 篇会展开讲。

三道保险，从"进料口"（阈值）到"加工间"（指令）再到"质检口"（校验），层层设卡。

7.5 端到端流程：伪代码

把整个链路浓缩成一份可读的伪代码，你可以照着它搭自己的第一版系统：

def answer_question(user_question: str) -> Answer:
    # ① 问题改写
    query = rewrite(user_question)

    # ② 混合检索：两路并行召回
    vec_hits = vector_search(query, top_k=50)      # 向量路
    bm25_hits = bm25_search(tokenize(query), top_k=50)  # 关键词路
    candidates = rrf_merge(vec_hits, bm25_hits)    # 合并，去重，Top-50

    # ③ 重排序
    ranked = rerank(query, candidates)             # 逐对打分
    top_5 = ranked[:5]
    top_score = ranked[0].score

    # ④ 若检索太弱，直接承认不知道
    if top_score < 0.3:
        return Answer(text="知识库中未找到直接相关内容。",
                      citations=[], no_hit=True)

    # ④ 拼装上下文（带来源标签）
    context = build_context(top_5)

    # ⑤ 生成（用 7.3 的 Prompt 模板）
    final_prompt = RAG_PROMPT.format(context=context, question=query)
    raw_answer = llm.generate(final_prompt)

    # ⑥ 提取引用（让模型输出结构化引用，或事后用规则对齐）
    answer, citations = parse_answer_with_citations(raw_answer)
    return Answer(text=answer, citations=citations)

注意第 ⑥ 步的"引用提取"：让模型在回答时同时输出 JSON 格式的来源标记（比让模型写"见第 12 页"更稳），再用规则解析，实现"引用可点击跳转"。

7.6 引用来源：企业级信任的基石

最后单独说说"引用"，因为它是企业 RAG 和普通"聊天机器人"最本质的区别。

实现引用需要三个环节配合：

  1. 入库时：每个块带上完整的元数据（第 2 篇做过）：文档名、版本、页码、作者、入库时间。
  2. 检索时：块的元数据跟着块一起进上下文（7.3 已做）。
  3. 展示时：前端把模型标注的来源渲染成"第 12 页 >"的可点击链接，点开直接跳到原文。
{
  "answer": "根据员工手册，满 5 年工龄的员工可享受 15 天年假。",
  "citations": [
    {"doc": "员工手册_2024.pdf", "page": 12, "chunk": "满 5 年……15 天年假。"},
    {"doc": "员工手册_2024.pdf", "page": 13, "chunk": "年假申请流程……"}
  ]
}

有了这份 JSON，前端想怎么展示都行。当每一个结论都能追溯到具体文档和页码时，用户才会真正信任这个系统——这也正是知识库相比"直接问大模型"不可替代的价值。

7.7 多轮对话：上下文（History）怎么处理

真实的企业问答很少是"问一句答一句"，大多是聊天式的多轮对话：

用户：年假能休几天？
系统：满 1 年 5 天，满 5 年 15 天……
用户：那我入职刚满两年呢？

第二个问题单独拎出来，"我""那"指代不明，直接检索必然抓瞎。正确的做法是把多轮历史合并成一个"当前问题"再检索：

def resolve_current_question(history, latest_question):
    # 让大模型结合历史对话，把当前问题补全成独立可检索的问题
    prompt = f"""以下是对话历史：
{history}

用户最新提问：{latest_question}

请把最新提问改写成一个"不含指代、可独立检索"的完整问题。
只输出改写结果。"""
    return llm.chat(prompt)

# 示例：
# 历史："年假能休几天？" → "满1年5天，满5年15天。"
# 最新："那我入职刚满两年呢？"
# 改写结果："入职满两年的员工年假有几天？"

几个实操要点：

  • 历史窗口要截断：只保留最近 3–5 轮，太长既费 token 又引入噪声。
  • 历史只用于"改写问题"，不参与检索：检索和上下文拼装用的都是改写后的"独立问题"。
  • 会话隔离：每个用户有独立的会话 ID，历史不要串人——既避免张冠李戴，也符合数据隐私要求。

7.8 多路检索：当一个"问题"其实是一堆问题

用户的一句话里可能藏着多个子问题："年假怎么算？还有没休完的怎么处理？" 单独一个查询向量去检索，可能只覆盖到其中一个。

进阶做法是多路改写（Multi-Query）：把一个问题拆成多个查询，分别检索再合并结果：

queries = llm.chat("把下面问题拆成最多3个独立子查询：\n" + question)
# 示例输出：
# ['年假天数怎么计算', '年假未休完怎么处理', '年假申请流程']

all_candidates = []
for q in queries:
    hits = rrf_merge(vector_search(q), bm25_search(q))
    all_candidates.extend(hits)
deduped = dedupe_by_id(all_candidates)   # 按块 ID 去重
ranked = rerank(question, deduped)       # 用原始问题做精排

好处是覆盖更全，代价是检索次数变多、延迟上升。适合：问题宽泛、答案分散的场景；不适合：问题明确、要求秒回的高并发场景。按需启用，别默认开启。

7.9 系统级健壮性：超时、重试与降级

生产系统不能"一次问崩、全盘皆崩"。问答链路里每个环节都可能失败，要提前设计好应对策略：

环节 可能失败 应对策略
问题改写 模型超时 降级：直接使用原始问题检索
混合检索 向量库/BM25 挂了 降级：只走其中一路
Rerank 模型不可用 降级：跳过重排，用融合排名
生成 大模型超时/限流 重试 1 次 → 返回"服务繁忙，请稍后再试"
引用解析 模型没按格式输出 用规则兜底：从答案中抽取文档名 
def safe_answer(question):
    try:
        q = rewrite(question)          # 失败则 q = question
    except Exception:
        q = question
    try:
        hits = hybrid_search(q)        # 失败则只走向量路
    except Exception:
        hits = vector_search(q)
    ...
    try:
        answer = llm.generate(prompt)  # 失败则返回友好提示
    except Exception:
        return "服务暂时不可用，请稍后再试。"

原则只有一条：任何一环失败，都要有"降级路径"，绝不能让用户看到报错堆栈。企业级系统的稳，就是靠这一层层"安全网"托起来的。

7.10 回答的结构化输出：从"一段话"到"可编程"

企业系统里，问答结果不能只是一段话——前端要渲染、要跳转、要做操作，后端要记录、要分析。所以推荐的实践是：让模型输出结构化 JSON，再用代码解析。

output_schema = """请按以下 JSON 格式回答，不要输出其他内容：
{
  "answer": "对用户问题的最终回答（简洁分点）",
  "confidence": "high|medium|low",          // 检索充分程度
  "citations": [
    {"doc": "文档名", "page": "页码", "snippet": "引用原文片段"}
  ],
  "unanswerable": true|false                 // 资料不足时为 true
}"""

raw = llm.generate(RAG_PROMPT.format(schema=output_schema, ...))
import json
try:
    result = json.loads(raw)                 # 解析为字典
except json.JSONDecodeError:
    result = fallback_parse(raw)             # 模型偶尔不听话，做容错

结构化输出的四个好处：

  1. 引用可编程：citations 数组直接渲染成可点击列表，不必再从大段文字里正则提取。
  2. 前端好做状态：unanswerable=true 时前端展示"未找到资料"的引导卡片，而不是一段尴尬的回答。
  3. 方便评测：第 9 篇的忠实度评测，需要"答案句子"和"引用片段"逐句对应，结构化输出天然提供。
  4. 方便审计：confidence 字段让系统能识别"低置信度回答"，单独标记、重点复核。

容错设计：大模型偶尔不按格式输出（少了括号、多了解释），一定要做 fallback_parse（用正则抽关键字段，或干脆降级为普通文本回答）。宁可让格式偶尔退化为纯文本，也不能让一次解析异常搞垮整个接口。

7.11 本篇小结

完整的 RAG 问答链路六步走：改写 → 混合检索 → 重排 → 拼上下文 → 生成 → 引用。

  • 问题改写：让口语问题更利于检索，成本低收益高。
  • 上下文拼装：带来源标签 + 排序 + 限制数量 + 明确指令，防止乱编。
  • "检索不到就承认"：三道保险——分数阈值、指令约束、忠实度校验。
  • 引用是信任的基石：入库存元数据、检索带元数据、展示可跳转。
