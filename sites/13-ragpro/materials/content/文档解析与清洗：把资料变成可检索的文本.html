文档解析与清洗：把资料变成可检索的文本

在上一篇文章里我们说，企业级知识库的起点是"把资料收拾干净"。这一篇就来做这件最脏、最累、但决定成败的事：文档解析与清洗。

打个比方：你要建一座图书馆，但送来的"书"其实是一箱箱没整理过的纸——有印刷清晰的正规书，有边角发黄的扫描件，有折得皱巴巴还印着页码的复印稿，甚至有几页是表格、几页是照片。你不能直接把这一箱纸扔进书架就让读者"搜索"。图书馆员的第一步，永远是把纸变成字、把字排成行、把行收拾整齐。文档解析干的就是图书馆员的活。

2.1 企业资料都有哪些"脏"形态？

先认清敌人。企业中真实存在的文档，远比我们以为的复杂：

  • PDF：最普遍，也最麻烦。PDF 有两种——文本型 PDF（文字还能被选中复制）和扫描型 PDF（本质是图片，文字全靠"拍"出来的）。
  • Word / PPT：本身有段落结构，但可能混入批注、修订、页眉页脚、文本框。
  • Excel / 表格：信息在行与列里，读出来是一堆数字和文字，顺序和含义都藏在表格结构里。
  • 扫描件 / 图片 / 传真：纯图片，必须 OCR（光学字符识别，把图片里的字"认"出来）。
  • 网页 / HTML：有大量导航、广告、脚本等噪声，正文需要单独抽出来。
  • PDF 里嵌套的图片/流程图：一张架构图，文字识别出来可能是一团乱麻。

记住一句话：在解析之前，任何一份文档都只是"一堆字节"，不是"文本"。解析的目标，就是把它变成一行行干净、有序、机器能读懂的文本。

2.2 解析工具怎么选？

工具的选择取决于"源文档长什么样"。我们按需挑选，没有银弹。下表列出最常用的几个：

工具 擅长 适合场景
pdfplumber（Python 库） 精确提取文本型 PDF，保留坐标、表格结构 印刷清晰的合同、报告、说明书
PyMuPDF（fitz） 速度极快，支持文字、图片、标注提取 批量处理大量 PDF
Unstructured（开源库） 一站式解析 PDF/Word/PPT/HTML/图片，自动识别块 想省事，用统一接口处理多种格式
Apache Tika（Java 工具） 几乎所有格式都能"嚼"，老牌全能选手 需要兼容几十种格式的异构环境
OCR（如 PaddleOCR、Tesseract） 把扫描件/图片里的字认出来 扫描件、照片、传真

一个粗浅的选型口诀：文本型 PDF 用 pdfplumber 或 PyMuPDF；混合格式用 Unstructured；扫描件先走 OCR；全公司什么格式都有，考虑 Tika。 要注意，工具不是万能的，解析结果一定要抽样人工检查——机器读错字、丢段落是家常便饭。

2.3 一个最常用的解析示例：PDF 提取文本

我们看一段真实可用的代码。假设有一份文本型 PDF，用 pdfplumber 把每一页的文字和表格提出来：

import pdfplumber

# 打开 PDF 文件
with pdfplumber.open("产品说明书.pdf") as pdf:
    print(f"总页数：{len(pdf.pages)}")
    all_text = []
    for i, page in enumerate(pdf.pages, start=1):
        text = page.extract_text()          # 提取该页文字
        tables = page.extract_tables()      # 提取该页表格（返回二维列表）
        page_text = f"\n===== 第 {i} 页 =====\n" + (text or "")
        if tables:
            page_text += "\n[表格]\n"
            for row in tables:
                page_text += " | ".join(str(c) for c in row) + "\n"
        all_text.append(page_text)
        print(f"第 {i} 页：提取到 {len(text or '')} 个字符")

clean_text = "\n".join(all_text)
with open("说明书_清洗前.txt", "w", encoding="utf-8") as f:
    f.write(clean_text)
print("提取完成")

这段代码做了三件事：逐页提取文字 → 逐页提取表格 → 拼接成一个带页码标记的文本文件。注意我们刻意在每页开头插入了"第 N 页"标记——这个标记后面会成为"引用来源"的锚点：用户问"这条规定在哪？"系统能回答"在第 12 页"。

2.4 扫描件怎么办：OCR

如果 PDF 里的文字复制不出来，那就是扫描件（图片）。这时提取文字没用，需要 OCR。国内最推荐 PaddleOCR，中文识别效果好、免费开源。

OCR 的基本流程是：PDF 转图片 → 逐张识别 → 拼接文本。代码示意如下：

from paddleocr import PaddleOCR
import fitz  # PyMuPDF

# 1. 把 PDF 每一页渲染成图片
doc = fitz.open("扫描合同.pdf")
ocr = PaddleOCR(use_angle_cls=True, lang="ch")  # 中文识别

full_text = []
for i, page in enumerate(doc, start=1):
    pix = page.get_pixmap(dpi=300)  # 300 DPI，识别更准
    img_path = f"page_{i}.png"
    pix.save(img_path)

    # 2. OCR 识别这一页
    result = ocr.ocr(img_path, cls=True)
    page_text = "\n".join(line[1][0] for line in result[0])
    full_text.append(f"\n===== 第 {i} 页 =====\n{page_text}")

with open("扫描合同_OCR.txt", "w", encoding="utf-8") as f:
    f.write("\n".join(full_text))

几个实操要点：

  • DPI 调到 300：太低识别率骤降，太高文件巨大又拖慢速度。
  • 扫描件一定要人工抽查：印章、手写、模糊字，OCR 都会出错或漏掉。
  • 能搞到源文件就别 OCR：扫描件识别率再高也不如原文，这是"最后手段"。
  • 先小样后全量：先用 3–5 页测试 OCR 效果和耗时，确认满意后再处理整批文档，避免跑了半天才发现参数不对。

如果扫描件里既有印刷体又有手写体（比如填写的申请表），最好把 OCR 的"文字方向检测"打开（对应代码里的 use_angle_cls=True），它能自动纠正拍歪的页面。实在识别不了的手写区域，不要硬扛——在文本里保留一个"[此处为手写内容，未识别]"占位标记，宁可让系统知道"这里缺失"，也不要让错误内容混进知识库。

2.5 清洗：把文本变得更"干净"

解析出来的文本是"能读了"，但还很脏。清洗要处理这几类问题：

（1）去页眉页脚和页码。 每页顶部的公司名、底部的"第 X 页 / 共 X 页"、网站链接，属于噪声。它们会污染分块，让检索系统误以为"公司名"是正文关键词。处理办法：统计高频短行，直接删掉，或按页面边界裁剪。

（2）去掉无意义噪声。 连续空行、特殊符号（如大量 -----、****）、乱码字符（如 锟斤拷 这类编码错误产物）、OCR 产生的孤立单字。用正则清洗：

import re

def clean_text(text: str) -> str:
    # 去掉连续空白行，合并为单个空行
    text = re.sub(r"\n{3,}", "\n\n", text)
    # 去掉页眉页脚里的横线装饰
    text = re.sub(r"-{5,}", "", text)
    # 去掉乱码字符
    text = re.sub(r"[\x00-\x08\x0b\x0c\x0e-\x1f]", "", text)
    # 去掉无意义空格（中文字符之间的空格）
    text = re.sub(r"(?<=[\u4e00-\u9fa5]) (?=[\u4e00-\u9fa5])", "", text)
    return text.strip()

（3）统一编码和换行符。 全角/半角混乱（， 与 ,）、英文引号与中文引号不一致、Windows 换行（\r\n）与 Unix 换行（\n）混用。统一成 UTF-8 编码、统一成 \n，能避免后面很多诡异的 bug。

（4）处理表格。 表格提取出来后，可以转成"可读的句子"再入库。比如 | 姓名 | 电话 | 这种表，可以转成 员工的姓名是张三，电话是 138xxxx。这样检索时用户问"张三的电话"，系统能直接命中，而不必理解表格结构。

2.6 一个完整流程示例：一份混乱 PDF 的"从脏到净"

把以上所有步骤串成一个真实流程，你会更清楚每一步的位置：

【原始输入】一份 2019 年扫描版《员工手册》，共 80 页，
           含页眉"XX 集团机密"、页码、两张组织结构图、若干表格

 ① 判断类型 ──► 扫描型 PDF（文字无法选中）
 ② 渲染图片 ──► PyMuPDF，DPI=300，逐页转 PNG
 ③ OCR 识别 ──► PaddleOCR 中文模型，输出每页文本
 ④ 粗清洗   ──► 去掉"XX集团机密"页眉、页码、横线装饰
 ⑤ 表格还原 ──► 把表格行转成"字段是值"的句子
 ⑥ 图说处理 ──► 组织结构图 OCR 效果差，人工补一段文字说明
 ⑦ 编码统一 ──► UTF-8、统一换行、去空白行
 ⑧ 输出     ──► 一份带页码标记的干净文本，附 JSON 元数据

第 ⑧ 步输出的"干净文本 + 元数据"，才是真正可以进入分块、向量化的原料。顺便说一句，第 ⑥ 步的"图说处理"特别重要但常被忽略：一张图在知识库里的价值，取决于你能不能给它配一句文字说明。

2.7 网页与 HTML 的清洗

企业知识库常常也要抓取内部网页、帮助中心、Wiki。网页比 PDF 好解析，但噪声更多：导航菜单、广告位、页脚、面包屑、脚本标签，全是垃圾。

主流做法是用 trafilatura 或 readability 这类"正文抽取"库——它们能自动识别并剥离噪声，只留下文章主体：

import trafilatura

html = open("help_center.html", encoding="utf-8").read()
# 抽取正文（自动去导航、去广告、去脚本）
content = trafilatura.extract(html, include_links=False, include_tables=True)
print(content[:500])

对内部 Wiki（如 Confluence），更推荐直接走官方 API 导出为结构化文本，比抓网页干净得多。记住一个原则：能用结构化接口（API）就别抓 HTML，能抓 HTML 就别 OCR。解析手段的"成本"和"风险"是从低到高的。

2.8 清洗流程的自动化设计

既然要处理几十万份文档，清洗不能靠手工，得设计成一条可重复执行的流水线。给你一个推荐的工程结构：

pipeline/
├── 1_convert/      # 各种格式 → PDF 或中间格式
├── 2_parse/        # PDF → 文本 + 表格 + 元数据
├── 3_clean/        # 去噪声、去页眉页脚、统一编码
├── 4_validate/     # 抽样检查 + 质量统计（错字率、空块率）
└── 5_output/       # 干净的 .txt + .json 元数据

流水线每一段输出都要可审计：每份文档处理完，生成一行日志——"文件 X：1200 字，含 3 个表格，错字 2 处，可疑块 1 个"。这样出了问题你能快速定位是哪一步干的。

另外强烈建议在清洗阶段做"质量门禁"（Quality Gate）：计算每个块的信息密度（有效汉字占比）和可疑率（乱码/孤立单字比例），低于阈值的块直接标记为"待人工处理"，而不是静默进入知识库。宁可让一份文档"缺失"，也不能让一堆垃圾进入检索。

2.9 Word 与 PPT 的解析细节

除了 PDF，Word 和 PPT 也是企业文档大户，它们的解析有一些"坑"值得单独说。

Word（.docx）：本质是带结构的 XML（可扩展标记语言，一种带标签的文本格式），用 python-docx 能同时拿到段落和表格：

from docx import Document

doc = Document("员工手册.docx")
texts = []
for para in doc.paragraphs:          # 读段落
    if para.text.strip():
        texts.append(para.text)
for table in doc.tables:             # 读表格
    for row in table.rows:
        texts.append(" | ".join(cell.text for cell in row.cells))
print("\n".join(texts)[:500])

要注意的坑：批注、修订痕迹经常残留在文档里，解析前先"接受所有修订并删除批注"；文本框里的内容 python-docx 默认读不到，要额外遍历。

PPT（.pptx）：每张幻灯片有标题和正文，还有备注。对企业知识库，备注往往是隐藏金矿（演讲人把要点写在那里）。用 python-pptx：

from pptx import Presentation

prs = Presentation("产品培训.pptx")
for i, slide in enumerate(prs.slides, start=1):
    title = slide.shapes.title.text if slide.shapes.title else ""
    body = "；".join(
        shape.text for shape in slide.shapes
        if shape.has_text_frame and shape.text.strip()
    )
    notes = slide.notes_slide.notes_text_frame.text if slide.has_notes_slide else ""
    print(f"第{i}页 | 标题：{title} | 正文：{body[:100]} | 备注：{notes[:100]}")

Excel（.xlsx）：一整个工作簿几十个 sheet（工作表），每个 sheet 又有几百行。直接整表转文本会爆炸。推荐按 sheet 拆分处理，把每一行转成"键值对"句子（第 2.5 节的做法），并在块开头保留 sheet 名和表头，这样"查台账"类问题才有线索可循。

2.10 元数据设计：被忽视的宝藏

前面的"黄金原则"里提到过元数据，这里展开说——它是很多知识库"检索对但引用乱"的元凶。

每个块入库时，至少要带这些字段：

{
  "id": "chunk_000123",
  "doc_id": "doc_20240715_012",
  "title": "员工手册_2024版",
  "chapter": "第四章 休假制度",
  "page": 12,
  "author": "人力资源部",
  "created_at": "2024-07-15",
  "permission": "all_employees",
  "chunk_index": 3,
  "chunk_total": 42
}

这些字段的价值：

  • page / chapter：第 7 篇讲引用时，答案要标注"出自第 12 页"，靠的就是它们。
  • permission：权限控制（第 10 篇的坑五）靠它实现——薪酬资料只对 HR 可见。
  • created_at：资料过期检测，"2021 年的制度"和"2024 年的制度"冲突时，系统能提示以新版为准。
  • chunk_index / chunk_total：分块太碎时，可以追溯"这个块属于哪份文档的哪一段"，便于回溯原文。

设计元数据要趁早，因为向量库建好后再补字段，往往要全量重建索引。宁可开始多花半天设计，也别后面返工三天。

2.11 本篇小结

最后给你三条可以长期使用的原则，帮你少踩坑：

  1. "垃圾进，垃圾出"是全流程的铁律。 解析和清洗不做好，后面所有的分块、检索、生成都是在给脏数据做美容。宁可在这一步多花 3 天，也不要让 3 天变成 30 天的返工。
  2. 解析结果必须抽样验收。 抽 5% 的页面人工检查，定一个"可接受标准"（比如每页错字率低于 1%），不合格就换工具、调参数。
  3. 保留元数据。 来源文件名、页码、章节标题、作者、日期，这些"关于文本的文本"要跟着每一段走，它们是后面做引用、做权限、做审计的根基。

到这里，你的资料已经是一份份干净的文本了。下一步，就是把这些"干净但很长"的文本，切成适合检索的小块——这就是下一篇《分块策略》要解决的问题。
