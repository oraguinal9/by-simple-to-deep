Embedding 与向量库选型

前两篇我们把文档变成了"干净文本"，又切成了"能独立回答问题的小块"。现在的问题是：这些文本块，机器怎么"理解"它们的含义，又怎么快速找到和问题最像的那几块？

答案就两个字：向量（Vector）。把文本变成向量，叫 Embedding（嵌入，读作"恩贝丁"）；存向量、查向量的数据库，叫向量库（Vector Database）。这篇文章把这两件事一次讲透，并给出一份适合中文企业知识库的选型建议。

4.1 用生活比喻理解 Embedding

想象你在整理名片。张三、李四、王五的名片，你要按"工作领域"分类，但你没法问名片"你懂不懂金融"。于是你想了个办法：给每张名片打 100 个标签分，比如"金融 0.9、医疗 0.1、法律 0.05……"。整理完，你发现做金融的名片分数相近，做法律的名片分数相近，而金融和法律的名片差很远。

Embedding 就是这件事，只不过标签不是 100 个，而是几百到几千个"看不见的维度"，而且标签不是人想的，是模型学出来的。每个文本块都变成一个"高维坐标点"，含义相近的文本，坐标相近；含义无关的文本，坐标很远。"找相关文本"就变成了"找最近的坐标点"——几何问题。

一个关键直觉：Embedding 追求的是"语义相近 → 向量相近"，而不是"字面相同 → 向量相同"。所以问"年假几天"，系统能找到写着"员工每年可休带薪年假 5 至 15 天"的块，哪怕字面上没有一个"几"字。这就是向量检索相对关键词检索的核心优势。

4.2 怎么选 Embedding 模型

Embedding 模型五花八门，选错是最常见的翻车原因之一。尤其是中文场景，很多人在英文模型上表现不错，换到中文就"反应迟钝"。这里按语言分两类介绍。

中文优先：BGE / m3e / text2vec

模型 特点 一句话点评
BAAI/bge-large-zh-v1.5 智源出品，中文检索榜常年前列，自带"带指令查询"模式 中文企业知识库首选
BAAI/bge-small-zh-v1.5 BGE 的小号版，速度更快、更省资源，精度略低 资源有限或规模超大时用
m3e-base / m3e-large 摩搭社区出品，中英混合，训练数据侧重中文 中文为主、兼顾英文时的不错选择
text2vec-large-chinese 网易有道的开源中文模型 老牌选择，如今略逊于 BGE

英文 / 多语：OpenAI、E5

模型 特点 适用场景
text-embedding-3-small / text-embedding-3-large OpenAI 出品，API 调用，省心但按量付费、数据出境需合规 英文为主、不在意成本与合规
intfloat/multilingual-e5-base 多语种模型，覆盖中文 多语言知识库（如跨国企业内部资料）

选型的三条判断标准

不管选哪个，都用这三条标准衡量：

  1. 中文效果：必须用中文数据集实测，别只看宣传榜。拿 20 条你们行业的典型问题去跑，看检索命中率。
  2. 维度与速度：维度越高越精细但越慢越贵（bge-large 是 1024 维，bge-small 是 512 维）。十万级文档，小模型往往够用。
  3. 部署成本：开源模型可以本地部署（公司内网、数据不出门）；API 模型省运维但每月有账单。企业知识库强烈建议优先本地部署开源中文模型——数据安全往往是硬需求。

使用示例（bge 中文模型，注意加"查询前缀"的官方用法）：

from sentence_transformers import SentenceTransformer
from sentence_transformers.util import cos_sim

# 加载中文 embedding 模型
model = SentenceTransformer("BAAI/bge-large-zh-v1.5")

# 对查询加指令前缀（bge 官方推荐，能明显提升检索效果）
query = "年假有几天？"
query_vec = model.encode("为这个句子生成表示以用于检索相关文章：" + query)

# 文档块不加前缀
doc_vec = model.encode("员工可根据工龄享受每年 5 至 15 天的带薪年假。")

score = cos_sim(query_vec, doc_vec)
print(f"相似度：{score.item():.4f}")   # 数值越接近 1 越相关

4.3 向量库怎么选：主流方案对比

向量算出来了，存哪？这里列五个最常见的方案，各有性格：

方案 类型 优点 缺点 适合谁
Milvus 专业向量数据库 千万级规模、功能全（索引/过滤/多租户）、生态成熟 部署较复杂，重 大企业、海量数据、要正经架构
Qdrant 专业向量数据库 轻量、易用、Rust 写的性能好、文档清晰 比 Milvus 功能略少 中小团队想快速上专业方案
Chroma 轻量级向量库 几行代码就能跑，本地开发极方便 生产环境能力弱 原型验证、学习、小规模
pgvector PostgreSQL 插件 直接复用现有数据库，事务、权限齐全 大并发/极大规模性能有限 已有 PostgreSQL、数据量中等
Elasticsearch 搜索引擎 关键词检索极强，自带 BM25，向量检索也在支持 向量性能不如专业库 需要"关键词 + 向量"一体化的场景

一个非常实用的判断思路：先问自己"我现在有什么、想要多大规模"。 已有 PostgreSQL 就想少加一套系统 → 选 pgvector；从零开始、规模十万级 → 选 Qdrant 或 Milvus；只是本地学习 demo → 用 Chroma；想要"关键词 + 向量"一个系统搞定 → Elasticsearch。别为不存在的千万级需求去上重型武器。

4.4 维度与相似度度量

两个必须理解的基础概念：

维度（Dimensions）

每个文本向量是一个"高维坐标"，维度就是这个坐标的个数。维度高 → 表达能力细 → 但更占存储、计算更慢、效果未必更好。常见值：bge-small 512 维，bge-large 1024 维，text-embedding-3-large 3072 维。选型时记住：选好模型，维度就跟着定了，不用自己纠结；只是要注意建库时维度必须和模型输出一致，换了模型要重建索引。

相似度度量（Similarity Metric）

判断两个向量"像不像"，有三种常用数学度量：

  • 余弦相似度（Cosine）：看两个向量的"方向"是否一致，忽略长度。最常用，对文本语义最友好。
  • 点积（Dot Product）：方向一致且长度都大时分数高。适合已归一化的向量。
  • 欧氏距离（Euclidean）：衡量空间直线距离，值越小越近。文本场景用得少。
余弦相似度：范围 [-1, 1]，1 表示方向完全相同（最相关）
点积：       数值越大越相关（向量长度也参与）
欧氏距离：   数值越小越相关

绝大多数中文文本场景，选"余弦相似度"就对了。选错度量会导致排名怪异，这是新手常踩的坑。

4.5 中文知识库选型建议（可直接抄作业）

综合以上，给你一份针对"企业内部中文知识库"的默认建议：

决策点 推荐 理由
Embedding 模型 BAAI/bge-large-zh-v1.5（本地部署） 中文效果好、开源可私有化、数据不出门
查询指令前缀 记得加"为这个句子生成表示以用于检索相关文章：" bge 官方推荐，白捡的精度提升
相似度度量 余弦相似度 文本语义场景的标准选择
向量库 数据量 < 100 万条：Qdrant；已有 PostgreSQL：pgvector；只是学习：Chroma 匹配你的真实规模，避免过度设计
规模预估 块数 ≈ 文档字数 ÷ 块大小（400 字） 10 万字 ≈ 250 个块，可据此估算硬件

4.6 一个最小可跑的入库示例

把"模型 + 向量库"串起来的最小代码（以 Chroma 为例，最省事）：

from sentence_transformers import SentenceTransformer
import chromadb

# 1. 加载中文 embedding 模型
model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

# 2. 启动 Chroma（本地文件模式）
client = chromadb.PersistentClient(path="./vector_db")
collection = client.get_or_create_collection(
    name="company_kb",
    metadata={"hnsw:space": "cosine"},   # 相似度度量选余弦
)

# 3. 把第 3 篇切好的块 + 元数据一起入库
chunks = [
    {"text": "员工每年可休 5-15 天年假。", "meta": {"来源": "员工手册", "页": "12"}},
    {"text": "年假申请需提前三天在 OA 提交。", "meta": {"来源": "员工手册", "页": "13"}},
]

collection.add(
    documents=[c["text"] for c in chunks],
    metadatas=[c["meta"] for c in chunks],
    ids=[f"chunk_{i}" for i in range(len(chunks))],
    embeddings=model.encode([c["text"] for c in chunks]).tolist(),
)

# 4. 查询
q_vec = model.encode("为这个句子生成表示以用于检索相关文章：年假几天")
results = collection.query(query_embeddings=[q_vec.tolist()], n_results=2)
print(results["documents"])

入库完成后，你的知识库已经有"可搜索的索引"了。但别急着高兴——向量检索有个天生的短板：它不懂关键词、编号、专有名词。下一篇我们就来补上这块短板：混合检索。

4.7 怎么"实测"一个 Embedding 模型

前面反复强调"别只看宣传，要实测"。这里给你一套20 分钟能做完的实测方法，不需要写复杂代码，逻辑清晰可复现。

第一步：准备测试集。 从你的真实业务里挑 10 个典型问题，再为每个问题挑出"正确答案所在的块"和"明显无关的块"各一个。

测试集示例：
问题1："年假有几天？"  → 相关块：员工手册关于年假的段落
                        → 无关块：班车路线说明
问题2："发票怎么开？"  → 相关块：财务制度报销章节
                        → 无关块：年会通知

第二步：计算"相关对"和"无关对"的相似度。 理想情况是：相关对的相似度显著高于无关对。用一段脚本批量算：

from sentence_transformers import SentenceTransformer
from sentence_transformers.util import cos_sim

model = SentenceTransformer("BAAI/bge-large-zh-v1.5")

def score_pairs(model, query, related, unrelated):
    q = model.encode(query)
    r = cos_sim(q, model.encode(related))
    u = cos_sim(q, model.encode(unrelated))
    return float(r), float(u)

r, u = score_pairs(model, "年假有几天？", "员工每年可休年假5-15天。", "班车每半小时一班。")
print(f"相关对相似度：{r:.3f}，无关对相似度：{u:.3f}")
# 好模型的表现：r 明显大于 u（比如 0.6 vs 0.3）

第三步：算"区分度"和"平均排名"。 把所有无关块的相似度都比相关块高的问题数出来——出现一次，说明模型对这个问题理解不到位。10 个问题里，区分度失败超过 2 个，就该换模型或换策略了。

这套方法的价值在于：同一套测试集可以反复用来对比不同的模型。把 bge-small 和 bge-large 都跑一遍，哪个"平均排名"更高就用哪个，用数据做决定。

4.8 本地部署：数据安全与硬件成本

企业知识库的一个硬约束是数据不出门。如果你在金融、医疗、法律行业，或资料包含薪酬、客户信息，Embedding 和生成模型几乎都必须本地部署。这里给出务实的硬件参考：

模型 显存需求（估算） 说明
bge-small-zh-v1.5（512 维） 约 1–2 GB 一台普通办公机就能跑
bge-large-zh-v1.5（1024 维） 约 2–4 GB 推荐，性能/成本均衡
bge-reranker-v2-m3 约 2–4 GB 重排模型，见第 6 篇
生成模型（7B 开源，如 Qwen2.5-7B） 约 8–16 GB 本地生成，够用但需量化

一个典型的全本地配置：一台 16GB 显存的 GPU 服务器（如 RTX 4080/4090），同时跑 bge-large 嵌入 + bge-reranker + 一个量化后的 7B 生成模型，足够支撑一个几十人使用的中小知识库。没有 GPU 的话，CPU 也能跑嵌入模型（只是慢），生成模型建议至少用 32GB 内存的机器。

部署方式上，sentence-transformers 直接支持加载本地模型：

# 下载模型（第一次运行会自动从 Hugging Face 下载）
python -c "
from sentence_transformers import SentenceTransformer
m = SentenceTransformer('BAAI/bge-large-zh-v1.5')
m.save('./models/bge-large-zh')   # 保存到本地，之后离线加载
"

如果公司内网无法访问 Hugging Face（模型托管平台），可以让有外网的同事先下载好整个模型目录，再拷贝到内网服务器加载。先想清楚数据安全约束，再决定本地还是 API——这个决定要放在选型的第一步，而不是最后。

4.9 常见的三个认知误区

最后帮你排掉几个常见的认知雷区：

误区一："维度越高越好。" 不是。高维度意味着更细的语义表达，但也意味着更慢、更贵、更容易过拟合。1024 维的 bge-large 对绝大多数场景绰绰有余，3072 维的模型在十万级文档上纯粹是浪费。选"够用且实测效果最好"的，而不是"数字最大"的。

误区二："同一个模型，Query 和文档用同一个向量就行。" 部分模型（尤其 BGE）官方明确要求：查询要加指令前缀，文档不加（第 4.2 节的代码就是这样）。如果两边都加或都不加，效果会明显下降。这是最容易被忽略的"免费午餐"。

误区三："向量库越专业越好，用最重的。" 对一个 5 万块的内部知识库，Milvus 的分布式能力完全用不上，反而徒增运维负担。用 Chroma 或 pgvector 完全够，先跑通，规模真到了再迁移——向量库迁移是可控的（重新灌数据而已），别为迁移的恐惧而过度设计。

4.10 本篇小结

  • Embedding：把文本变成高维向量，"语义相近 → 向量相近"。中文企业场景首选 bge-large-zh，本地部署更安全。
  • 向量库：Milvus（大而全）、Qdrant（轻而专）、Chroma（原型）、pgvector（复用现有库）、Elasticsearch（检索一体化）。按真实规模选，别过度设计。
  • 两个参数别选错：维度跟着模型走；相似度度量选余弦。
