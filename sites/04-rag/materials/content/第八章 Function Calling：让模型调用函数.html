第八章 Function Calling：让模型调用函数

上一章我们说，Agent 有"工具"这个手脚，能查天气、算账、发邮件。本章就揭开工具机制的核心：Function Calling（函数调用 / 工具调用）——模型到底是怎么"决定调哪个函数、填什么参数"的。

一、核心思想：给模型一份"函数说明书"

Function Calling 的本质，不是让模型去执行代码，而是让模型输出一个结构化的"调用意图"：我要调哪个函数、参数填什么。真正执行代码的，是你写的程序。

要让模型会调函数，你得先把函数介绍给它——就像给新员工发一份"公司有哪些工具、各自怎么用"的说明手册。这份说明用 JSON Schema 描述，包含三要素：

  • name：函数名，如 get_weather；
  • description：这个函数干嘛的、什么时候用（模型靠它判断是否该调）；
  • parameters：参数定义（类型、是否必填、说明），用 JSON Schema 写。

示例——一个"查天气"的函数说明：

{
  "name": "get_weather",
  "description": "查询指定城市当天的天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city":  { "type": "string", "description": "城市名，如 北京" },
      "date":  { "type": "string", "description": "日期，如 2026-08-03" }
    },
    "required": ["city"]
  }
}

你把这份说明，连同用户问题，一起发给支持 Function Calling 的模型。

二、模型返回的不是答案，是"调用意图"

关键点来了：模型不会真的去查天气。它读到你的问题"北京今天天气咋样"，再读到你提供的函数说明，判断"这个问题该调 get_weather，参数是 city=北京"，然后返回一个结构化调用请求：

{
  "name": "get_weather",
  "arguments": { "city": "北京", "date": "2026-08-03" }
}

注意：这只是"意图"，不是天气数据。接下来你的程序接管：

  1. 你的代码解析这个意图，真的去调用天气 API（或读库）；
  2. 拿到结果，比如 {"temp": 28, "cond": "晴"}；
  3. 把这个结果回填给模型，说"这是 get_weather 的返回"；
  4. 模型结合结果，生成自然语言回答："北京今天晴，28℃"。

三、一张图看清完整回合

你 ──问题"北京天气?"+ 函数说明──→ 模型
                                  ↓
                        返回 调用意图(get_weather, {city:北京})
                                  ↓
你的程序 ──真的调天气API──→ 拿到 {temp:28, cond:晴}
                                  ↓
回填结果 ─────────────────→ 模型
                                  ↓
                     生成回答"北京晴 28℃" ──→ 你

这就是"模型出主意，程序动手脚"的分工。模型负责决策（调谁、填啥），程序负责执行（真去查、真去算）。

四、为什么不直接让模型"自己输出 JSON"？

你可能会想：那我让模型直接打印一段 JSON 不就行了？何必用专门的 Function Calling 接口？

区别在于可靠性：

  • 裸让模型输出 JSON，它经常格式飘忽（多逗号、少引号、把解释混进去），你的程序解析十次崩三次；
  • 专门的 Function Calling 接口，模型被训练成严格按 schema 输出结构化调用，参数类型、必填项都被约束，程序解析稳得多。

简单说：Function Calling 是把"让模型调函数"这件容易出错的事，变成了模型被专门训练过的拿手好戏。

五、多轮：模型看结果再决定下一步

真实 Agent 里，一次调用往往不够。模型拿到第一个工具的结果后，可能决定再调第二个工具。

例：用户"北京今天适合穿啥？" 1. 模型调 get_weather → 拿到 28℃ 晴； 2. 模型想：28℃晴，该推荐薄装 → 再调 search_products(category=薄外套, city=北京)； 3. 拿到商品列表 → 综合生成推荐。

这就是多轮工具调用：每轮模型都基于"上一步工具结果"决定"下一步调什么"。Agent 的"思考→行动→观察"循环，底层就是靠 Function Calling 一轮轮串起来的。

六、工程上必须处理的两件事

1. 参数校验

模型偶尔会填错参数（比如 city 填成数字）。你的程序在真正调函数前，要按 JSON Schema 校验参数，不对就提示模型重填，而不是直接崩。

2. 函数执行失败

天气 API 挂了、数据库连不上——函数可能报错。要把错误信息也回填给模型，让它决定"重试 / 换工具 / 老实告诉用户失败"，而不是让整个 Agent 卡死。

七、一个常见误区

"开了 Function Calling，模型就自动会用我的系统了。"

不对。 模型只知道你明确告诉它的那些函数。你没登记的函数，它根本不知道存在。所以工具清单（函数说明）的质量，直接决定 Agent 的能力边界——这也是为什么"给模型写清楚每个工具的用途和参数"如此重要。

八、本章小结

  • Function Calling = 让模型输出结构化调用意图（调哪个函数 + 参数），真正执行的是你的程序。
  • 使用前提：用 JSON Schema 给模型写函数说明（name/description/parameters），它靠 description 判断何时该调。
  • 模型返回意图 → 你的程序执行函数 → 回填结果 → 模型生成回答。分工：模型决策，程序动手。
  • 比"裸让模型输出 JSON"可靠得多（格式受 schema 约束）。
  • 多轮调用串起 Agent 的"思考→行动→观察"循环。
  • 工程必做：参数校验 + 执行失败处理；模型只知你登记过的函数，工具清单质量决定能力边界。

  4. B. description
