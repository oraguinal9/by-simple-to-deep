第六章 RAG 实战问题与优化：重排序与混合检索

前几章我们已经跑通了一个"能用"的 RAG：切块 → Embedding → 向量检索 top-k → 拼提示词 → 生成。但现实中，"能跑"和"答得准"之间，隔着一整套优化。

本章直面 RAG 最常见的痛点，并给出可落地的优化手段。记住一句贯穿全篇的话：

���索质量决定 RAG 的上限，生成只是把上限兑现出来。

一、RAG 最常见的三大痛点

痛点 1：检索召回不到正确答案

用户问 A，但 top-k 里根本没有包含答案的那块资料。后面生成再聪明也是"巧妇难为无米之炊"。 - 可能原因：切块太大/太小、embedding 模型不匹配、查询表述和资料表述差异大。

痛点 2：检索召回了，但正确答案"排得太靠后"

top-k 里其实有正确资料，但它排在第 8 位，而我们只取前 3 送进提示词——正确资料被截断丢弃。 - 这说明"粗排"不够准，需要"精排"补一刀。

痛点 3：答非所问 / 被无关资料带偏

检索到了一堆沾边但不核心的资料，模型抓错重点。 - 需要更精准的排序，或先对资料做质量过滤。

下面三把"优化武器"逐一拆解。

二、武器 1：查询改写（让问题和资料"说同一种话"）

前面说过，向量检索比的是"语义方向"。但如果用户问题写得很口语、很简略，而资料写得很书面，二者方向可能偏掉。

解决方法：查询改写（Query Rewriting）——先用一个小模型把用户问题"翻译"成更适合检索的表述。例如：

  • 原问题："猫掉毛能吃鸡不？"
  • 改写后："猫咪脱毛期间是否可以食用鸡肉 宠物护理"

改写后再去检索，命中率显著提升。进阶还有 HyDE（假设性文档嵌入）：让模型先"假设性"写一段它心目中的答案，再用这段答案去检索——因为答案和资料同属"资料语体"，反而比原问题更容易对齐。

三、武器 2：重排序 Rerank（先粗召，再精排）

这是性价比最高的一招，一定要掌握。

思路分两步： 1. 粗召（召回）：用向量检索先捞出较多候选，比如 top-20（宁可多捞，别漏）； 2. 精排（rerank）：用一个专门的重排序模型（cross-encoder 类，如 bge-reranker），对"问题 + 每块资料"成对打分，重新排序，取最前面的 top-3~5 送进提示词。

为什么有效？因为： - 向量检索是"问题和资料各自变向量再比距离"，二者没真正"对照"过； - rerank 模型是同时看到问题和资料，判断"这段到底回答没回答这个问题"，精度高得多。

代价是 rerank 比向量检索慢一点（要逐对计算），所以通常只对在粗召的几十个候选上跑，性能可接受。

一句话：向量检索负责"广撒网"，rerank 负责"去粗取精"。两者配合，是工业级 RAG 的标配。

四、武器 3：混合检索（关键词 + 向量）

纯向量检索有个软肋：专名、编号、精确短语它反而容易漏。比如用户搜"订单号 SO-2026-8832 的退款状态"，向量检索可能觉得"订单号"这种无意义字符串不重要，结果漏掉。但关键词匹配（如 BM25）恰恰擅长精确命中这些字面串。

混合检索（Hybrid Search） = 向量检索 + 关键词检索（BM25）并行，再把两边结果融合（比如 RRF 倒数排名融合）：

用户问题
  ├─→ 向量检索  → 候选集 A（擅长语义/同义）
  └─→ BM25 检索 → 候选集 B（擅长专名/精确词）
            ↓ 融合排序
       最终 top-k

这样"猫主子掉毛"（语义）和"SO-2026-8832"（精确）都能稳稳命中。

五、元数据过滤���先缩小范围再检索

很多时候，检索前就能用元数据把范围砍小。比如用户问"《报销制度》里差旅标准"，与其在全库百万块里找，不如先过滤 source == 报销制度，再在子集里做向量检索——又快又准，还避免跨文档干扰。

元数据过滤特别适合：按部门、按时间、按文档类型、按权限隔离。

六、怎么知道"优化见效了"：评估 RAG

优化不能靠"感觉"，要能量化。最实用的两个指标：

  • 检索召回率（Recall@k）：标准答案应该引用的资料块，有没有出现在 top-k 里？覆盖率越高越好。
  • 回答相关性 / 忠实度：生成的答案，是否真的基于资料、有没有编造？可用 LLM 当评委（LLM-as-judge）打分，或人工抽检。

建议做法：攒一批真实问答对（问题 + 标准应引用的资料 + 标准答案要点），每次改了切块/embedding/rerank 后重跑，看指标变化。这就是 RAG 的"回归测试"。

七、RAG 调试清单（遇事不决照着查）

回答不好时，按顺序排查：

  1. 资料里到底有没有答案？（没有就去补知识库，别怪模型）
  2. 检索召回了吗？ 打印 top-k，看正确答案块在不在、排第几。
  3. 切块合理吗？ 答案被切散了？块太大噪声多？调大小/重叠。
  4. embedding 模型适合中文吗？ 换中文优调模型试试。
  5. 加查询改写 / rerank / 混合检索 任一，看召回是否提升。
  6. 提示词对吗？ 有没有"只依据资料、没有就说查不到"的约束？资料矛盾处理了吗？
  7. 生成本身烂？ 换更强模型或调温度/系统指令。

80% 的 RAG 问题出在 1~5（检索侧），不在生成。先修检索，再动生成。

八、本章小结

  • 检索质量决定 RAG 上限，生成只是兑现上限。
  • 三大痛点：召回不到、排太靠后、被无关带偏。
  • 查询改写 / HyDE：让问题和资料"说同一种语体"，提升对齐。
  • Rerank（重排序）：向量粗召 top-N + rerank 精排 top-k，工业级标配，性价比最高。
  • 混合检索：向量（语义）+ BM25（精确/专名）融合，专治"订单号类"查询。
  • 元数据过滤：先缩小范围再检索，更快更准。
  • 用召回率 + 忠实度量化评估；遇事按"调试清单"从检索侧往上查。

九、小练习

  1. 用户问"订单 SO-2026-8832 的退款到哪了"，纯向量检索可能为什么漏？混合检索怎么补？
  2. 为什么说"先向量粗召 top-20，再 rerank 取 top-3"通常比"直接向量取 top-3"更好？
  3. 给你一个 RAG 系统，回答总答非所问。你打开日志发现：正确答案块其实在 top-20 里、但排第 15，而系统只取了前 3。问题出在哪一步？该加什么优化？
