第九章 ReAct：让 Agent 边想边做

前两章讲了 Agent 有工具（第七章）、以及工具怎么被调用（第八章 Function Calling）。但还有一个核心问题没解决：

面对"订北京的高铁，再订接机车，最后发短信告诉我"这种多步骤目标，模型怎么知道先干啥、后干啥、中途结果怎么用？

本章介绍 Agent 领域最经典的一种"做事方法"——ReAct。

一、什么是 ReAct

ReAct = Reasoning（推理） + Acting（行动）。它的核心思想极其朴素：

让模型把"心里话"说出来，再据此行动，再看结果，再想下一步——想和做交替进行。

具体每一步，Agent 会产生三种东西：

  • Thought（思考）：模型自己嘀咕"我现在该干嘛、为什么"。比如"我得先查北京天气，才能决定带不带伞"。
  • Action（行动）：基于思考，决定调哪个工具、传什么参数（就是上一章的 Function Calling）。
  • Observation（观察）：工具返回的结果。比如"北京 28℃ 晴"。

然后拿着 Observation，进入下一轮 Thought → Action → Observation……直到 Thought 判断"事办完了"，输出最终答案。

二、一个具体推演

任务："北京今天适合穿啥？顺便看看要不要带伞。"

Thought:   用户想知道穿着建议，得先知道北京今天天气。
Action:    get_weather(city=北京, date=今天)
Observation: { temp: 28, cond: "晴" }
Thought:   28℃ 晴天，偏热，不需要厚衣也不需要伞；可以推荐轻薄透气的衣服。
Action:    search_products(category="夏装", city="北京")
Observation: [T恤, 短裤, 凉鞋 ...]
Thought:   信息足够了，可以综合天气和商品给建议。
Answer:    北京今天 28℃ 晴，建议穿 T 恤短裤等夏装，不用带伞；给您找到了几款……

看见了吗？模型不是"一口气答完"，而是每步先想清楚再动手，手上的结果又喂给下一步的思考。这就是"边想边做"。

三、为什么 ReAct 这么好用

1. 把"推理"显式化，可追踪可纠错

模型把 Thought 写出来了，你就能看到它为什么这么决策。哪步想歪了，你能定位、能干预。对比"黑箱一口气给答案"，ReAct 透明得多。

2. 把"长任务"拆成"短决策"

复杂任务不用一次想透，而是走一步看一步。每步只解决"当下该调哪个工具"，压力小、不易错。

3. 观察结果能纠正偏差

如果 Action 返回"查无此城市"，下一轮 Thought 就能意识到"是不是城市名写错了"，换成正确写法。错误在循环中被自然消化，而不是一错到底。

四、ReAct 和 Function Calling 是什么关系

容易混淆，其实层次不同：

  • Function Calling 是"怎么调一个函数"的机制（第八章）；
  • ReAct 是"按什么节奏组织多步任务"的方法（本章）。

ReAct 的每一个 Action，底层就是一次 Function Calling。换句话说：ReAct 是上层思维框架，Function Calling 是它调动工具的具体手段。 两者是"战略"与"战术"的关系。

五、进阶：Plan-and-Execute（先计划再执行）

ReAct 是"走一步看一步"，适合步骤不长的任务。但当任务很长（比如"调研一个行业并写报告"），纯 ReAct 容易在中途"迷失方向"。

进阶做法是 Plan-and-Execute： 1. 先规划（Plan）：模型先一次性列出大致步骤清单（如：①搜行业规模 ②搜头部公司 ③搜政策 ④汇总）； 2. 再逐步执行（Execute）：每一步用 ReAct 式的小循环去完成。

好处是有全局蓝图，不会走岔。许多成熟 Agent 框架会混合这两种思路。

六、记忆（Memory）：让 Agent 跨步骤"记事"

多步任务里，Agent 常需要"记住前面发生过什么"。比如第一步查到的天气，第三步还要用。这就需要记忆机制：

  • 短期记忆：把本轮对话历史（包括之前的 Thought/Action/Observation）保留在上下文里，模型自然能看到；
  • 长期记忆：跨多轮、跨会话记住用户信息（常借助我们前面学的 RAG——把历史存进知识库，需要时检索）。

所以你又会看到：Agent 的记忆，常常也是靠 RAG 实现的。RAG 和 Agent 在这条线上再次交汇。

七、ReAct 的风险与对策

ReAct 强大，但也有典型毛病：

  • 死循环：Thought 反复横跳，Action 一直重复（比如不停查天气）。对策：设最大步数上限，超了就停并回报。
  • 幻觉式 Action：模型编造一个根本没登记过的函数名。对策：执行前校验函数名是否在工具清单内，不在就驳回。
  • 步数爆炸烧钱：每步都要调一次模型。对策：简单任务别上 ReAct；或用 Plan-and-Execute 减少无效试探。

八、本章小结

  • ReAct = 推理 + 行动，让模型交替产生 Thought（思考）→ Action（调用工具）→ Observation（看结果），循环到任务完成。
  • 价值：推理显式化可追踪、长任务拆成短决策、Observation 能自然纠错。
  • ReAct 是"战略"（组织多步），Function Calling 是"战术"（调单个函数）；ReAct 的每个 Action 底层就是一次 FC。
  • 进阶 Plan-and-Execute：先列全局步骤，再逐步 ReAct 执行，防长任务迷失。
  • 记忆靠保留对话历史（短期）+ RAG 检索（长期）；Agent 记忆常与 RAG 交汇。
  • 风险：死循环（设步数上限）、幻觉函数名（校验清单）、烧钱（简单任务不上 ReAct）。
