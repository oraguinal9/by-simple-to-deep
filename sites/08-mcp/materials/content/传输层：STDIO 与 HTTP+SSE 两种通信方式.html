传输层：STDIO 与 HTTP+SSE 两种通信方式

MCP 规定 Client 和 Server 之间用 JSON-RPC 2.0 格式传消息。但具体这些消息通过什么「管道」传，有两种官方支持的传输方式：STDIO（标准输入输出） 和 HTTP + SSE（Server-Sent Events）。这一章讲清两者的区别、适用场景和底层原理。

一、先理解「传输层」管什么

不管用哪种传输，消息的内容（JSON-RPC）是一样的。传输层只负责一件事：把这些 JSON 字符串可靠地从 A 送到 B。

类比：你写信的内容不变，但可以选择「让邮差当面递」（STDIO，本地）还是「走快递网络」（HTTP+SSE，远程）。

二、STDIO 模式（本地、子进程）

原理

STDIO 适合 Server 跑在你自己电脑上 的场景。Host 启动时，直接把 Server 当作一个子进程拉起来，然后通过操作系统的「标准输入（stdin）/ 标准输出（stdout）」跟它说话。

Host 进程
  └─ 启动子进程：文件系统 MCP Server
        Host 写消息 → Server 的 stdin
        Server 写消息 → Host 的 stdout
  • Host 往 Server 的 stdin 写一行 JSON（一条请求）；
  • Server 从 stdin 读，处理，往自己的 stdout 写回一行 JSON（响应）；
  • Host 从 Server 的 stdout 读响应。

注意是逐行的：一条消息 = 一行 JSON（以换行符分隔）。

优点

  • 零网络配置：不用开端口、不用管 IP、不用 HTTPS；
  • 天然隔离：子进程崩了不影响 Host；
  • 安全默认好：Server 只在你本机跑，数据不出电脑；
  • 简单：适合「我电脑上的文件 / 本地数据库」这类场景。

缺点 / 限制

  • Server 必须和 Host 同一台机器（子进程嘛）；
  • 一个 Server 进程通常只服务一个 Client（1 对 1）。

典型场景

文件系统访问、本地 SQLite、本机 shell、读取本地配置——凡是「能力在本地、不想出网」的，都用 STDIO。

三、HTTP + SSE 模式（远程、跨网络）

原理

当 Server 跑在另一台服务器（比如云上的 SaaS），就不能用子进程了，得走网络。MCP 的远程传输用两套 HTTP 机制配合：

Client (Host 内)                        Server (远程)
     │                                        │
     │  POST /mcp  (发 JSON-RPC 请求)  ──────▶│
     │                                        │
     │  ◀────────  SSE 长连接 (Server 推响应/事件)
     │            GET /sse                    │
  • 客户端 → 服务端：用普通 POST 把 JSON-RPC 请求发过去；
  • 服务端 → 客户端：用 SSE（Server-Sent Events） 建立一条长连接，服务端有结果了就顺着这条连接推回来。

SSE 是浏览器/HTTP 原生支持的「服务端单向推送」机制（比 WebSocket 简单，只能服务端推、客户端收）。

优点

  • 跨机器：Server 可以部署在任何能访问的服务器上；
  • 多客户端共享：一个远程 Server 可被多个 Host 连；
  • 适合 SaaS：比如「云端知识库 MCP」「团队共享的数据库 MCP」。

缺点 / 限制

  • 要处理网络、认证、HTTPS、跨域；
  • 部署复杂度高；
  • 数据出网，需要考虑隐私和权限。

典型场景

团队共享的工具、云端 API 封装、需要被很多人同时用的能力。

四、两种模式怎么选

维度 STDIO HTTP+SSE
Server 位置 本机子进程 远程服务器
网络配置 无 需端口/域名/证书
安全默认 高（不出网） 需自行加固
共享性 单人 可多人
适合 本地文件、本地库 SaaS、团队工具

经验：先从 STDIO 开始。绝大多数个人场景（读文件、跑本地脚本、查本地库）STDIO 就够了，省去一堆部署麻烦。等真要「让别人也能用这个能力」，再上 HTTP+SSE。

五、消息格式本身（两种模式相同）

无论 STDIO 还是 HTTP+SSE，消息体都是 JSON-RPC 2.0。例如 Client 问 Server「你会什么」：

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

Server 回：

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {"name": "read_file", "description": "读取文件", "input_schema": {...}}
    ]
  }
}

STDIO 把这段 JSON 写成一行喂给 stdin；HTTP+SSE 把它放进 POST 的 body。内容一模一样，只是「信封」不同。

六、常见坑

  • STDIO 下 Server 不能往 stdout 打日志（会污染协议流）——日志要写到 stderr 或文件；
  • SSE 连接要保持：断了要重连，否则收不到推送；
  • 两种模式别混用：一个 Server 要么 STDIO 要么 HTTP，客户端按它的声明连。

七、本章小结

  • MCP 传输层只负责「把 JSON-RPC 消息可靠送达」，内容两种模式一致；
  • STDIO：本地子进程，经 stdin/stdout 逐行传，零网络配置、安全默认好，适合本机能力；
  • HTTP+SSE：远程部署，POST 发请求 + SSE 收推送，支持多人共享，但要管网络/认证/证书；
  • 选型原则：个人本地优先 STDIO，团队/云端再上 HTTP+SSE；
  • 坑点：STDIO 的 Server 日志要走 stderr；SSE 要处理重连。
