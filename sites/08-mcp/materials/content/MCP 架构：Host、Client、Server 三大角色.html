MCP 架构：Host、Client、Server 三大角色

前面三章打好了基础。这一章我们正式进入 MCP 的世界，搞清楚它那套体系里到底有哪几个角色、各自干什么。理解了架构，后面讲传输、讲原语、讲开发就都有了落脚点。

一、三个核心角色

MCP 把一次「模型用工具」的完整链路，拆成了三个明确分工的角色：

┌─────────────────────────────────────────────┐
│  Host（宿主应用）                              │
│   例如：Claude Desktop、Cursor、你的 AI App     │
│   · 承载一次对话                              │
│   · 内部集成了一个大模型                       │
│   · 决定「要不要调工具、调哪个」              │
│                                              │
│   ┌──────────────┐      ┌──────────────┐     │
│   │ MCP Client   │◀────▶│ MCP Server   │     │
│   │ (协议客户端) │ 协议  │ (能力提供方) │     │
│   └──────────────┘      └──────────────┘     │
│        1:1                    1:N            │
│   每个 Server 对应           一个 Client 可   │
│   一个 Client               连接多个 Server   │
└─────────────────────────────────────────────┘

1. Host（宿主）

Host 是你实际打开用的那个应用。它负责： - 维护你和模型的对话； - 内部跑一个大模型（或接入一个）； - 在合适的时机，通过 MCP 让模型用上外部工具； - 把工具结果呈现给你，必要时弹出权限确认。

典型 Host：Claude Desktop、Cursor、VS Code 插件、你自己写的 AI 聊天程序。

2. Client（客户端）

Client 是 Host 内部的一个组件，住在 Host 进程里。它的唯一职责是：跟某一个 MCP Server 说协议话。

关键点：一个 Client 只连一个 Server（1 对 1）。如果你的 Host 同时接了「文件系统 Server」和「GitHub Server」，那 Host 内部就有两个 Client，各管一个 Server。

Client 干的活： - 启动 / 连接 Server； - 问 Server「你会什么」（能力发现）； - 把模型的调用请求转发给 Server； - 把 Server 的返回转回给 Host / 模型。

3. Server（服务端）

Server 是能力的提供方。它知道某个具体领域怎么干活： - 文件系统 Server：懂怎么读、写、列目录； - GitHub Server：懂怎么调 GitHub API； - 数据库 Server：懂怎么连库、跑 SQL。

Server 把自己的能力，按 MCP 规定的格式「声明」出来，等 Client 来调用。它不知道也不会直接碰模型——它只跟 Client 对话。

二、一次请求在三角色间怎么流动

用「读文件」为例，把数据流画出来：

[你] 帮我读 notes.txt
  │
  ▼
[Host] 把你的话 + 已知能力 交给 模型
  │
  ▼
[模型] 返回意图：调 read_file(path="notes.txt")
  │
  ▼
[Host] 通过 [Client A] 把意图发给 [文件系统 Server]
  │
  ▼
[Server] 真去读文件，返回内容
  │
  ▼
[Client A] 把内容回传给 [Host]
  │
  ▼
[Host] 把内容塞回对话，让模型生成回答
  │
  ▼
[你] 看到：notes.txt 的第一行是……

注意 Host 是中枢：模型在 Host 里，Client 在 Host 里，Server 在外面。Host 把「模型的意图」翻译给 Client，再把「Server 的结果」喂给模型。

三、为什么是「1 个 Client 对 1 个 Server」

这是 MCP 设计里很讲究的一点。好处：

  • 隔离：某个 Server 崩了，不影响其他 Server（各自独立进程 / 连接）；
  • 清晰的生命周期：一个 Server 的启动、关闭，只对应一个 Client；
  • 权限边界清晰：每个 Server 的授权可以单独管理（「允许这个文件 Server 读 Desktop，但那个数据库 Server 只能查」）。

所以当你看到「Host 连接了 5 个 MCP Server」时，背后就是 Host 里起了 5 个 Client，各连一个。

四、Host 和「模型」的关系要分清

新手容易把 Host 和模型混为一谈。记住：

  • 模型是那个「思考、生成文本」的引擎，它不认识 MCP；
  • Host 是应用，它既包着模型，又管着一堆 Client；
  • MCP 发生在 Host（经 Client）↔ Server 之间，不经过模型。

换句话说：MCP 是「应用和外部能力」之间的协议，模型只是这个应用里的一个被服务的对象。这也是为什么同一个 MCP Server，既能被 Claude Desktop 用、也能被 Cursor 用、还能被你自研的 App 用——因为协议在应用层，不在模型层。

五、本地 Server vs 远程 Server

Server 可以跑在两种地方：

类型 跑在哪 传输方式 例子
本地 Server 你的电脑上（子进程） STDIO（标准输入输出） 文件系统、本地数据库
远程 Server 另一台服务器 HTTP + SSE 云上的 SaaS 能力

两者对 Host/Client 来说用法一样，区别只在「怎么传消息」（下一章讲）。MCP 把这种差异也屏蔽了，所以应用层代码不用管 Server 在本地还是云端。

六、本章小结

  • MCP 三角色：Host（宿主应用，含模型）／ Client（协议客户端，1 对 1 连 Server）／ Server（能力提供方）；
  • 一个 Host 内有 N 个 Client，每个 Client 只连一个 Server；
  • 数据流中枢是 Host：模型出意图 → Host 经 Client 发 Server → Server 执行 → 结果回 Host → 喂模型作答；
  • MCP 发生在 Host↔Server（经 Client）之间，模型本身不认识 MCP；
  • 同一 Server 可被任意 Host 复用，因为协议在应用层；
  • Server 可本地（STDIO）可远程（HTTP+SSE），对应用透明。

下一章我们讲传输层：消息具体通过什么通道在 Client 和 Server 之间流动（STDIO 与 HTTP+SSE），这是部署 MCP 时第一个要拍板的事。

小练习：你常用的某个 AI 工具（比如某个 IDE 插件），试着判断：谁是 Host？它内部大概有几个 Client？连的 Server 可能在本地还是远程？
