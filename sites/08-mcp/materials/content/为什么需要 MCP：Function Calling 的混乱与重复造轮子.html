为什么需要 MCP：Function Calling 的混乱与重复造轮子

上一章我们说，MCP 出现之前，模型接工具是「各玩各的」。这一章我们把这件事拆开看：到底痛在哪、MCP 又是怎么逐个解决的。

一、痛点一：每个模型厂商的格式都不统一

这是最表层的痛。三家主流模型的「工具定义」，长得完全不一样。

OpenAI 风格

{
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_weather",
      "description": "查询某城市天气",
      "parameters": {
        "type": "object",
        "properties": {
          "city": {"type": "string", "description": "城市名"}
        },
        "required": ["city"]
      }
    }
  }]
}

Anthropic 风格

{
  "tools": [{
    "name": "get_weather",
    "description": "查询某城市天气",
    "input_schema": {
      "type": "object",
      "properties": {
        "city": {"type": "string", "description": "城市名"}
      },
      "required": ["city"]
    }
  }]
}

看出区别了吗？同样的「查天气」，一个叫 function，一个叫 input_schema；返回结构也不同。这意味着：你为 GPT 写的工具描述，搬到 Claude 上得改一遍字段名。模型多了、工具多了，这种改写是指数级的工作量。

MCP 的解决：协议规定了一套统一的「能力声明格式」。Server 用 MCP 标准告诉客户端「我会什么」，客户端再翻译成自家模型能懂的格式。工具作者完全不用关心下游是哪个模型。

二、痛点二：每个应用都得自己造一遍对接代码

假设你是个开发者，想做一个「AI 助理」，它能： - 读你电脑上的文件； - 查你的 GitHub； - 发消息到 Slack； - 跑你公司的数据库查询。

在没有标准的情况下，你得：

  1. 为「文件」写一套对接（怎么列目录、怎么读、怎么处理权限）；
  2. 为「GitHub」写一套（调 REST API、处理 token）；
  3. 为「Slack」「数据库」各写一套；
  4. 把每一套都接到你选的那个模型上（再写一遍适配）；
  5. 如果哪天你想换成另一个更强的模型，第 4 步推倒重来。

这就是「重复造轮子」。更糟的是，别人已经写过的 GitHub 对接，你用不了，因为你们的「接口约定」不一样，得自己再写。

MCP 的解决：文件系统、GitHub、Slack、数据库的对接，各由专人写成一个个 MCP Server（官方和社区已经有一大堆现成的）。你作为应用开发者，只要实现对 MCP 协议的支持，就能「插上」所有这些 Server。你写 1 次协议对接，获得 N 个能力。

三、痛点三：工具一多，模型就「选不准」

即使你把所有工具都接上了，还有个现实问题：给模型的工具清单太长，它会瞎调。

模型本质是「在 prompt 里挑一个最合适的工具」。当工具从 5 个涨到 500 个，噪声急剧上升： - 它可能在不需要时硬调一个工具； - 它可能调错参数； - 它可能在该用 A 的时候用了名字像的 B。

MCP 的解决（部分）：MCP 把「工具」「资源」「提示词」分成了不同原语（详见第六章），并且 Server 可以按需暴露、可以分页、可以有清晰的 description。再加上客户端的「能力路由」设计，能有效降低模型的选择负担。这不是 MCP 单独能根治的，但它提供了结构化的基础。

四、痛点四：安全与权限一片混乱

「让模型调工具」最危险的地方是权限。一个能读文件的模型，会不会偷偷读你的密码文件？一个能发 Slack 的模型，会不会乱发消息？

在早期各自为战的方案里，每个应用自己定义「模型能做什么、不能做什么」，没有统一的安全模型。有的干脆「全放开」，有的临时加个确认弹窗，质量参差。

MCP 的解决：协议把「谁有权限」这件事上升为一等公民。Server 声明自己能做什么，客户端/用户负责授权（比如「允许模型读 Desktop 目录，但不允许写」）。而且 MCP 强烈建议危险操作要 humans in the loop（人在回路） —— 真要删文件、真要发消息，先弹窗让你确认。这把安全从「各应用自觉」变成了「协议层约定」。

五、痛点五：无法组合与复用

真实任务往往是组合拳：「读 GitHub 上这个 issue → 查相关数据库 → 总结成 Slack 消息」。在没有标准时，这种跨系统的编排得你手写一整条 pipeline，换一个场景又得重写。

MCP 的解决：因为所有 Server 都说同一种语言，客户端可以同时连接多个 Server，并把它们编进同一次对话。模型自己就能决定「先调 GitHub Server 拿 issue，再调 Database Server 查数据」。组合能力变成「插上更多 Server」，而不是「再写一套代码」。

六、把五个痛点串起来

痛点 没有标准时 MCP 之后
格式不统一 每模型一套 统一能力声明
重复对接 每应用重写 Server 写一次，处处可用
工具太多选不准 prompt 噪声爆炸 结构化原语 + 路由
安全混乱 各应用自觉 协议层授权 + 人在回路
无法组合 手写 pipeline 多 Server 并行接入

这正是为什么 MCP 值得存在：它把「模型用工具」这件本该是基础设施的事，做成了标准件。

七、本章小结

  • 模型接工具的混乱来自五方面：格式不统一、重复对接、选不准、安全乱、难组合；
  • MCP 用「统一能力声明 + Server 生态 + 结构化原语 + 协议层授权 + 多 Server 并发」逐一对应解决；
  • 核心收益是解耦与复用：工具作者、应用作者、模型厂商各司其职；
  • 但要清醒：MCP 不是银弹，模型「选不准工具」「乱调」的问题需要客户端路由 + 良好 prompt 配合，协议只提供地基。

下一章，我们回到最底层，看「工具调用」这件事在模型内部到底是怎么发生的——这是理解 MCP 之前必须打好的基础。
