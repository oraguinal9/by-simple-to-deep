第九章 部署上线：从权重到 API 服务

微调、量化都搞定了，模型躺在硬盘里。怎么让它真正"接客"——被你的 App、网站、脚本调用？这就是部署。

部署在解决什么？

训练时模型在 GPU 上慢慢学；部署时模型要 7×24 小时、低延迟、高并发地回答问题。目标从"学好"变成"服务好"。一条典型的链路：

用户请求 → 你的服务程序 → 加载模型(权重+LoRA) → 推理引擎生成回答 → 返回

两种形态

  1. 本地/内网调用：脚本直接 from transformers import ... 加载模型跑。适合实验、一次性处理。
  2. 在线 API 服务：起一个 HTTP 服务，对外提供 /chat 接口，多个客户端随时来问。这是生产常态。

本章聚焦 API 服务。

推理引擎：别用最慢的那个

模型"怎么跑"极大影响速度和显存。直接用原生 transformers 生成也能跑，但吞吐低。生产常用专门优化过的引擎：

  • vLLM：高吞吐、PagedAttention 显存管理，几乎是大模型 API 服务的标配。
  • llama.cpp：C++ 实现，跨平台、对量化（尤其 4-bit GGUF）支持极好，适合边缘/消费级显卡。
  • TensorRT-LLM / Ollama / LMStudio：各有侧重，Ollama 对"个人本地一键起服务"最友好。

打个比方：权重是发动机，推理引擎是整车厂——同样的发动机，装进不同的车，速度和油耗天差地别。

加载 LoRA：底座 + 适配

部署微调成果时，通常是：

  1. 加载底座模型（可先量化到 INT4/NF4 省显存）；
  2. 叠加 LoRA 权重（几 MB 的那个文件）；
  3. 合并或动态挂载后提供服务。

很多框架支持"一个底座挂多个 LoRA，按请求动态切换"，这正是第二章说的 PEFT 多任务优势在部署端的兑现。

API 长什么样？

对外通常暴露一个和 OpenAI 兼容的接口，方便现有生态直接对接：

POST /v1/chat/completions
{
  "model": "my-finetuned-7b",
  "messages": [{"role": "user", "content": "你们的退货政策？"}]
}

返回流式或非流式的回答文本。用 OpenAI 兼容格式的好处：你写的客户端、LangChain 等工具几乎不用改就能接上。

上线前要检查的清单

  • 显存够不够：模型 + 推理引擎开销，留出余量（量化是常用解法，见第八章）。
  • 并发与队列：多人同时问怎么办？引擎一般有批处理（batching）和排队。
  • 最大长度：限制输入/输出 token，防超长请求拖垮服务。
  • 超时与降级：模型卡住要有超时；重要场景准备兜底话术。
  • 安全：要不要鉴权（API Key）？要不要过滤危险请求？

容器化：一键复现环境

把"模型 + 引擎 + 依赖"打包进 Docker 镜像，能在任意机器一键起服务，避免"在我机器上能跑"的玄学。生产部署几乎必做。

本章小结

  • 部署目标：把"会学的模型"变成"能 7×24 服务用户的 API"。
  • 选对推理引擎（vLLM/llama.cpp/Ollama）事半功倍。
  • 部署 = 底座（可量化）+ 叠加 LoRA，支持多适配动态切换。
  • 用 OpenAI 兼容接口，生态无缝对接；上线前查显存/并发/安全。

小练习

  1. 你训好一个退货客服 LoRA。部署时为什么要"先加载 4-bit 底座，再叠加 LoRA"，而不是只存一个合并后的完整模型？
  2. 为什么用 OpenAI 兼容的 API 格式，对后续接工具链更省事？
