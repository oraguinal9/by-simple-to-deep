实战路线：用 Dify 做一个完整的业务应用

最后一章，把前 9 章的能力串起来，完整走一遍「用 Dify 做一个真实业务应用」的全流程。我们以「公司智能客服」为例——一个既需要知识库、又需要工具、还需要工作流编排的典型场景。

需求定义：先想清楚再动手

场景：公司内部客服，员工会问三类问题： 1. 制度类（报销、请假、采购流程）——需要知识库； 2. 订单/工单类（查自己的订单状态）——需要工具（查数据库）； 3. 闲聊/寒暄——直接聊就行。

目标：一个入口，自动分流，准确回答制度问题，能查真实订单状态，还显得「专业友好」。

边界划分（用 L1 的决策思维）： - 制度类 → 知识库（资料可更新，不用改应用）； - 订单类 → 工具调用（查真实数据）； - 闲聊 → 模型自由发挥（不用特殊处理）。

架构设计：这个应用长什么样

用户提问
  ↓
工作流（入口）
  ├─ LLM 分类节点：制度类 / 订单类 / 闲聊
  │
  ├─ 制度类 → 知识检索节点 → 拼上下文 → LLM 生成（带引用）→ 结束
  ├─ 订单类 → 代码节点（查订单状态）→ LLM 组织回答 → 结束
  └─ 闲聊 → LLM 直接回答 → 结束

设计要点： - 用工作流保证流程可控（第 3 章）； - 制度类走知识库（第 4 章）； - 订单类用代码节点模拟查库（也可以换成 HTTP 节点查真实 API）； - 分类用便宜小模型，生成用强模型（第 8 章的成本思路）。

第一步：准备知识库

上传制度文档：《员工手册》《报销制度》《请假制度》《采购流程》。

  • 分段：按段落切，500 字左右；
  • 索引：配好 Embedding 模型；
  • 检索：混合检索 + Rerank（有就开）。

在知识库里建几条典型的问答对（问题-答案模式），比如「报销多久到账」直接命中标准答案，省 token 又准确。

第二步：搭建工作流

按架构图逐步搭：

  1. 开始节点：定义输入 user_message；
  2. LLM 分类节点：提示词让它输出 制度 / 订单 / 闲聊 三类，小模型即可；
  3. 条件分支：按分类走三条路；
  4. 制度分支：知识检索节点（选知识库，TopK=3）→ LLM 生成节点（系统提示词：「只依据资料回答，附引用」）；
  5. 订单分支：代码节点模拟查订单（返回订单状态）→ LLM 组织回答；
  6. 闲聊分支：LLM 直接友好回答；
  7. 结束节点：输出最终回答。

代码节点模拟查订单： python def main(order_id: str) -> dict: orders = {"ORD-001": "已发货", "ORD-002": "审核中", "ORD-003": "已完成"} return {"status": orders.get(order_id, "未找到该订单")}

第三步：调试与迭代

用一批测试问题逐类验证：

测试输入 期望行为
报销流程是什么？ 走制度分支，带引用回答
我的 ORD-001 到哪了？ 走订单分支，返回真实状态
你好呀 走闲聊分支，友好回复
请假要提前几天？ 走制度分支，准确回答

调试点： - 分类不准 → 优化分类节点的提示词（加 few-shot 示例）； - 检索不准 → 调 TopK/阈值； - 回答太啰嗦 → 生成节点提示词加「简洁」约束。

一次只改一处，改完重测全部用例——这是第 6 章的调试流程。

第四步：完善体验

  • 对话开场白：欢迎语 + 建议问题（「报销流程」「订单查询」）；
  • 会话变量：用户说了订单号后记下来，之后直接问「它到哪了」也能答（第 7 章）；
  • 温度：制度类生成节点温度调低（0.1），闲聊节点可以高一点（0.7）。

第五步：发布上线

按第 9 章三步走：

  1. 内部验证：发布 WebApp 链接，给同事试用一周，收集真实问题；
  2. 看日志：分析哪类问题回答差、哪类没人问，据此迭代；
  3. 正式集成：嵌入公司 OA（iframe）或接 API 进 IM 机器人。

上线后的持续运营

应用上线只是开始，持续的循环是：

收集真实用户问题
  → 分析日志（失败案例、高频问题）
  → 更新知识库（新政策、补充 FAQ）
  → 优化提示词（调规则、加示例）
  → 重新发布
  → 再收集……

关键认知：AI 应用是「养」出来的。知识库要常更新（政策变了就传新文档），提示词要常调（发现回答差就改规则）。平台的价值之一就是让这个循环足够快——改知识库、改提示词、重新发布，都只要几分钟。

复盘：这个项目用到了哪些能力

回看整个项目，你把这一阶段学的都用上了：

能力 用到哪
工作流编排（第3章） 整体流程
知识库（第4章） 制度问答
Agent/工具（第5章） 订单查询（代码节点）
提示词（第6章） 分类/生成节点的提示词
变量与对话（第7章） 会话变量记订单号
模型管理（第8章） 分类小模型 + 生成大模型
发布（第9章） WebApp → iframe → API

再往后走：能力升级方向

这个应用「够用」了，但还有升级空间：

  • 接真实数据：代码节点换成 HTTP 节点，连真实订单系统；
  • 加人机协同：复杂投诉转人工（加条件分支 + 通知）；
  • 多轮表单：用会话变量实现「逐步收集信息」的流程；
  • 数据看板：接日志做回答质量评分，用数据驱动迭代。

FAQ：实战中最常被问的问题

Q：这个项目到底该用工作流还是 Agent？ A：主流程用工作流（分类分流是固定逻辑），订单查询用代码/HTTP 节点实现「准工具」。只有「用户意图无法预判」的部分才考虑 Agent。默认先工作流，遇到灵活需求再局部用 Agent。

Q：分类节点用大模型是不是浪费？ A：是。分类是简单任务，用便宜小模型足够。把「贵模型」留给「生成回答」这种真正需要能力的地方——这是成本优化的第一课。

Q：代码节点里能查数据库吗？ A：能。代码节点可以连数据库（需在环境变量配连接串），或用 HTTP 节点调后端 API。生产环境更推荐 HTTP 节点（解耦、可审计），代码节点适合快速原型。

Q：知识库检索不到订单数据怎么办？ A：订单数据是动态的，不该进知识库。知识库放「静态制度」，动态数据走工具/API——这是很多初学者会混淆的地方。

Q：应用上线后怎么衡量效果？ A：三个数：回答满意率（人工打分）、知识命中率（引用来源使用情况）、用户留存（回头用的人多不多）。用数据说话，别凭感觉。
