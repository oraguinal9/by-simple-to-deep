应用发布：API、嵌入与分享

应用做好、调试满意后，最后一步是「发布」——让用户能用上。Dify 提供三种发布方式：WebApp 分享、网页嵌入、API 接入。这一章讲清每种方式怎么用、适合什么场景。

发布前：别忘了「发布」动作

Dify 的编排界面有「草稿（Draft）」和「已发布（Published）」两个状态：

  • 草稿：你正在编辑的版本，只有你能预览；
  • 已发布：对外可访问的版本。

每次改完要手动点「发布」，新版本才生效。这是平台帮你做的「上线审批」——防止把半成品发出去。

方式一：WebApp 分享链接（最快）

做法：应用 →「发布」→ 生成一个网页链接，发给用户即可。

特点： - 零开发，最快让用户用上； - Dify 托管页面（聊天界面、表单界面都有）； - 可设置访问密码、白名单。

适合：内部工具、给少量用户试用、快速验证产品想法。

方式二：嵌入网页（一行代码）

做法：Dify 生成一段 <iframe> 代码，贴进你的官网/系统页面：

<iframe src="https://your-dify/app/xxx" width="100%" height="600" style="border:none"></iframe>

特点： - 用户不用离开你的网站； - 样式受 iframe 限制（界面是 Dify 的）； - 适合「在现有网站里加个 AI 助手」的场景。

进阶：Dify 提供「WebApp 嵌入」的多种形态（浮动按钮、iframe、自定义 CSS），可以调整到和你的站点风格接近。

方式三：API 接入（最强大）

做法：应用发布后获得一个 API Endpoint + API Key，你的后端代码直接调用。

Dify 提供两种 API 风格：

1. Chat Messages API（聊天助手专用）：

curl -X POST 'https://your-dify/v1/chat-messages' \
  -H 'Authorization: Bearer app-xxxxx' \
  -H 'Content-Type: application/json' \
  -d '{
    "inputs": {},
    "query": "报销流程是什么？",
    "response_mode": "blocking",
    "user": "user-123"
  }'

2. Workflow Run API（工作流专用）：调用工作流，传开始节点定义的输入，拿结束节点的输出。

特点： - 完全集成进你自己的业务系统（APP、小程序、后台）； - 可以传 user 参数做用户隔离、传 conversation_id 做会话管理； - 按调用计费、有日志、可监控。

适合：真正的产品集成，把 AI 能力嵌进现有业务流程。

三种方式怎么选

给一个决策参考：

场景 推荐
快速试用/内部 WebApp 链接
官网加助手 嵌入 iframe
接进 APP/小程序/后台 API
还没想清楚 先 WebApp 验证，再决定

铁律：先发布一个最便宜的版本（WebApp）让用户用起来，验证价值后再投入做 API 集成——别一上来就做最重的。

API 接入的工程细节

如果你走 API 路线，这些细节很关键：

1. 用户隔离：每个用户传唯一 user 值，会话和日志才能按用户区分；

2. 会话管理：保存返回的 conversation_id，下次提问带上，对话才有记忆；

3. 错误处理：处理超时、限流（429）、模型错误等异常，给用户友好提示；

4. 安全：API Key 只在服务端保存，绝不放进前端代码（会被人抓走白嫖你的额度）。

5. 流式输出：response_mode: streaming 支持流式返回，用户能看到「打字机」效果，体验更好。

日志与监控：发布后的眼睛

Dify 内置了完整的日志系统，每个应用的每次调用都有记录：

  • 输入输出：用户问了什么、模型答了什么；
  • 元数据：用了哪个模型、token 消耗、耗时；
  • 评分：可以人工给回答打分，沉淀数据用于优化提示词。

发布后一定要养成看日志的习惯：哪类问题回答差、哪个模型太慢太贵、哪些用户用得最多——数据会告诉你下一步优化什么。

一个完整的发布案例

把第 4 章的「公司制度问答助手」发布上线：

1. 内部试用：生成 WebApp 链接发给 5 个同事，收集反馈
2. 反馈分析：同事说「回答太啰嗦」「想嵌入 OA」
3. 优化：调系统提示词（更简洁）、加访问白名单
4. 嵌入 OA：生成 iframe 嵌入办公系统
5. 后续扩展：产品化后改用 API 接入，接进 APP

这就是真实的发布路径：先验证 → 再优化 → 再扩展。平台让每一步都只要几分钟。

发布后的运营：别「发完就完事」

应用发布只是「开始被用」，后面的运营决定它好不好：

1. 日志周报：每周看一次日志统计——回答数、失败率、平均耗时、token 成本趋势；

2. 失败案例分析：挑出「用户重复问 / 回答被踩」的对话，逐个分析是检索问题还是提示词问题；

3. 知识库保鲜：业务变化时及时更新文档；高频问题沉淀成问答对；

4. 版本迭代节奏：每次发布记录「改了什么、数据上有什么变化」，形成版本史，别乱改一气。

一句话：发布是起点不是终点。一个「有人持续看日志、每周迭代」的应用，和一个「发布就没人管」的应用，半年后质量天差地别。

安全与合规速查

发布到公网前，过一遍安全清单：

  • [ ] API Key 只在服务端，没进前端代码
  • [ ] WebApp 有访问控制（密码/白名单）
  • [ ] 用户输入有长度/频率限制（防滥用烧钱）
  • [ ] 日志不记录敏感个人信息
  • [ ] 知识库内容合规（不泄露机密/他人隐私）
  • [ ] 有成本预算告警

安全不是发布后才想的事——发布前过一遍清单，能避免「上线即翻车」。

小练习

  1. 把第 2 章的聊天助手发布成 WebApp，用手机打开链接试一下访问体验。
  2. 用 iframe 把它嵌进一个本地 HTML 页面，调整宽度高度看效果。
  3. 调用一次 Chat Messages API（用 curl 或 Postman），体验 API 调用与参数传递。
  4. 进阶：给 API 调用实现「保存 conversation_id 实现多轮对话」的逻辑，模拟真实业务集成。
  5. 进阶：用发布后的日志数据，挑 3 条「回答不佳」的对话，分析原因并改一版提示词重新发布。

发布后应用就能「被用」了。最后一章，把所有能力组合起来——实战路线：用 Dify 做一个完整的业务应用。
