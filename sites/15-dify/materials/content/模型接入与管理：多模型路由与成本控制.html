模型接入与管理：多模型路由与成本控制

做 AI 应用绕不开「模型」这个核心成本。Dify 的价值之一是统一管理多个模型：接一个模型能跑，接十个模型也能管。这一章讲模型的接入、路由与成本控制。

Dify 的模型管理架构

Dify 的「模型供应商（Model Provider）」概念：

模型供应商（OpenAI / DeepSeek / 通义 / Ollama / 本地模型……）
  ├─ 大语言模型（LLM）：对话、生成
  ├─ 文本向量模型（Embedding）：知识库索引
  ├─ 重排序模型（Rerank）：检索精排
  └─ 其他（图像、语音……）

一个供应商可配置多个模型实例（如 DeepSeek 下配 chat 和 reasoner）。应用可以随时切换用哪个模型，不用改代码。

接入流程：三步

  1. 设置 → 模型供应商 → 添加：选择供应商（OpenAI、DeepSeek、通义、智谱、Ollama、硅基流动等）；
  2. 填写凭证：API Key（云端）或本地服务地址（Ollama）；
  3. 验证：点「测试」，显示成功即可用。

推荐组合（学习用）： - 主对话模型：DeepSeek（便宜）或通义/智谱（国产稳定）； - Embedding 模型：同供应商的向量模型； - Rerank 模型：BAAI/bge-reranker 等（经 API 或本地）。

应用里的模型配置

每个应用可以配置「自己的模型」，不强制全局统一：

  • 编排界面右侧：选择应用用的模型和参数（温度、max tokens）；
  • 按节点配置：工作流里每个 LLM 节点可以独立选模型——比如分类用便宜小模型，生成用贵的大模型；
  • Agent 模式：选一个主模型负责思考和工具调用。

这是多模型路由的基础：不同任务用不同模型，成本和质量都能兼顾。

成本控制：精打细算的艺术

模型调用是按 token 计费的，Dify 提供多个省钱手段：

1. 任务-模型匹配

任务 推荐模型 理由
简单分类 小模型（如 DeepSeek chat） 便宜够用
复杂推理 大模型（如推理模型） 能力要求高
检索向量化 专用 Embedding 模型 便宜稳定
精排 Rerank 模型 一次几百 token，开销小

2. 控制输入长度

  • 上下文裁剪：工作流里只传必要的字段，别把无关内容塞给模型；
  • 历史压缩：长对话用总结代替原始历史（第 7 章讲过）；
  • 检索限制：知识库 TopK 不要贪多（3~5 段够用），每段都是钱。

3. 缓存与复用

  • 相同问题的答案可以缓存（Dify 支持缓存节点），减少重复调用；
  • 高频问题用「知识库问答模式」直接命中标准答案，不走 LLM。

4. 监控成本

Dify 的日志/统计面板能看到每次调用的 token 数和费用。每周看一次成本报表，找出「又贵又没用」的调用优化掉。

模型能力对比与选择

选模型前先明确三个维度：

维度 说明
能力 复杂推理用强模型，简单任务用小模型
速度 生产环境注意响应延迟，小模型更快
价格 成本敏感场景优先性价比模型

给新手的建议：先默认用一款性价比模型（如 DeepSeek）跑通，遇到「能力不够」的具体问题再针对性换强模型——别一开始就上最贵的。

本地模型：省钱与隐私的选项

如果数据敏感或想省 API 费，可以在 Dify 接本地模型（Ollama，L10 讲过）：

设置 → 模型供应商 → Ollama
Base URL：http://host.docker.internal:11434
模型名：qwen2.5:7b 等

优点：免费、离线、数据不出内网。 代价：需要 GPU 才快，效果通常不如云端大模型。

推荐策略：简单任务用本地小模型，复杂任务用云端大模型——两者在 Dify 里可以同时接入，按节点/应用自由切换。

模型出问题怎么办：排障清单

Q：应用报「模型不存在/未配置」？ A：检查应用编排界面右侧的模型选择和供应商凭证是否有效。

Q：回答速度很慢？ A：模型太大/太远，或输入太长。换小模型、裁剪上下文、换更近的服务商。

Q：某供应商偶尔超时？ A：Dify 支持「模型冗余」——配两个供应商，主用失败自动切换（部分版本支持）。也可以手动在节点间切。

Q：知识库向量化失败？ A：Embedding 模型没配或额度不够。确认供应商的「文本向量模型」已配置。

模型选型决策清单

面对「用哪个模型」的纠结，用这张清单快速决策：

1. 任务需要多强的推理能力？
   简单分类/抽取 → 小模型（省 90% 成本）
   复杂推理/长文 → 大模型或推理模型

2. 数据能出内网吗？
   能 → 云端 API 最省事
   不能（合规/机密） → 本地模型（Ollama/vLLM）

3. 对延迟的要求？
   秒级响应 → 小模型 / 就近服务商
   可接受慢 → 大模型

4. 预算敏感吗？
   敏感 → 性价比模型起步，跑通再升级
   不敏感 → 直接上好模型

铁律：永远「够用就好」——先用便宜的跑通，遇到具体问题再升级。别一上来就选最贵最强的。

成本优化的进阶技巧

除了「任务匹配模型」，还有几个进阶省钱法：

1. 缓存高频答案 相同问题的回答可以走缓存节点，第二次起不调模型。适合 FAQ 型应用，成本接近零。

2. 知识库问答模式代替 LLM 命中「问题-答案」对时直接返回标准答案，不经过生成模型。这是「最省」的路径。

3. 提示词压缩 系统提示词精简、few-shot 示例精选（3 个够用别放 10 个）、工具描述控制长度——每条输入都在烧钱。

4. 用量预警 Dify 的统计面板设周/月目标，超了就告警。成本失控往往发生在「没人看」的时候。

小练习

  1. 在 Dify 里接入 2 个不同的模型供应商（如 DeepSeek + 通义，或云端 + 本地 Ollama）。
  2. 给同一个应用切换不同模型，对比回答质量和速度差异。
  3. 在工作流里实现「简单问题用便宜模型，复杂问题用贵模型」的路由（用条件分支）。
  4. 进阶：跑一轮完整对话后，去日志面板统计 token 消耗，算一算如果每天 1000 次调用，月成本是多少。
  5. 进阶：给应用开「缓存节点」，对同一个问题连续问两次，对比第二次是否省了模型调用。
