工作流编排：让应用按你的逻辑走

聊天助手适合「一问一答」，但真实业务往往需要固定流程：先判断用户意图，再决定走哪条路，可能还要查知识库、调外部 API。这一章讲 Dify 的工作流（Workflow）——把 AI 应用从「自由发挥」变成「按你的逻辑走」。

工作流 vs 聊天助手

先搞清楚区别：

聊天助手 工作流
流程 模型自由发挥 你编排的固定流程
控制力 靠提示词约束 每个节点精确控制
适合 开放对话 明确流程的任务
例子 陪聊、头脑风暴 客服工单分类、内容审核流水线

关键认知：流程越明确，越该用工作流。工作流让「模型的自由发挥」被限制在你设计的轨道里，输出更可控、更稳定。

工作流的核心概念：节点

工作流由节点（Node）组成。Dify 提供了一批内置节点：

节点 作用
开始 流程入口，定义输入变量
LLM 调用大模型生成
知识检索 查知识库，RAG 能力
条件分支（IF/ELSE） 按条件走不同路径
代码（Code） 写 Python/JS 处理数据
HTTP 请求 调用外部 API
变量聚合器 把多个结果合并
模板转换 用模板拼字符串
结束 流程出口，定义输出

理解节点的关键：每个节点有「输入」和「输出」，节点之间用线连起来，前一个节点的输出可以传给后一个节点。这就像一个可视化的「函数管道」。

搭建第一个工作流：客服工单分类

从一个经典例子开始，我们要做「客服工单分类器」：

开始
 ├─ 输入：用户留言
 ↓
LLM 节点：判断问题类型（售后/售前/其他）
 ↓
条件分支
 ├─ 售后 → 结束（输出「转接售后」）
 ├─ 售前 → 结束（输出「转接销售」）
 └─ 其他 → LLM 节点：生成通用回答 → 结束

搭建步骤：

  1. 创建应用时选「工作流」类型；
  2. 「开始」节点加一个输入变量 user_message（字符串）；
  3. 加 LLM 节点，提示词里引用 {{user_message}}，让它输出分类结果；
  4. 加条件分支节点，按 LLM 输出的分类走不同路径；
  5. 每个分支加「结束」节点，输出不同内容；
  6. 右上角「预览」输入一条留言试跑。

跑通后你会发现：流程的每一步都是确定的——这就是工作流「可控」的意义。

变量传递：工作流的血液

节点之间靠变量流动数据。变量在 Dify 里用 {{变量名}} 引用，来源可以是：

  • 开始节点定义的输入；
  • 前一个节点的输出（在节点配置里选择）。

一个典型的传递链：

开始.user_message
  → LLM(参考 {{开始.user_message}} 生成分类)
  → 条件分支(看 {{LLM.text}} 的值)
  → 结束(输出 {{LLM.text}})

调试技巧：预览时点开每个节点，能看到它的实际输入输出——这就是工作流的「断点调试」，找问题非常方便。

条件分支：让流程「聪明」起来

条件分支是工作流最常用的逻辑节点。它按条件把流程分成多条路：

如果 {{分类}} 包含「售后」 → 走售后路径
否则如果 {{分类}} 包含「售前」 → 走售前路径
否则 → 走通用路径

条件支持：等于、包含、开头是、正则匹配、数值比较等。条件分支让同一个工作流面对不同情况做出不同反应——这是「智能感」的重要来源。

代码节点与 HTTP 节点：打通外部世界

两个「连接真实世界」的节点：

代码节点：写一小段 Python/JS，处理数据。比如把 LLM 输出的 JSON 字符串解析成对象、格式化日期、清洗文本。

# 代码节点示例：去掉多余空格
def main(user_message: str) -> dict:
    cleaned = " ".join(user_message.split())
    return {"cleaned": cleaned}

HTTP 请求节点：调用外部 API。比如查库存、发通知、调天气接口。这让 AI 应用能真正「干活」而不是只说话。

工作流设计原则

几个实战经验：

  1. 能少则少：不是节点越多越好，能用 3 个节点解决就别用 5 个，复杂 = 难维护；
  2. 提示词要精确：LLM 节点是「不稳定点」，提示词写清楚输入输出格式，后续节点才能依赖它；
  3. 关键路径设兜底：条件分支记得加「否则」兜底，防止模型输出意外分类时无路可走；
  4. 善用代码节点做格式保证：别让模型「保证输出 JSON」，让代码节点解析并兜底。

工作流的常见翻车现场

新手搭工作流最容易踩这几个坑：

坑 1：LLM 节点输出格式不稳定 模型说好的输出 JSON，偶尔多写一句话，下游节点直接解析失败。解法：把「输出格式」写进提示词 + 用代码节点兜底解析。

坑 2：条件分支条件写错变量 分支比较的变量引用错了节点输出，流程永远只走一条路。解法：预览时点开节点看实际值，确认变量名对得上。

坑 3：节点之间没有「线」连上 搭了节点忘了连线，数据根本不流动。解法：流程跑通后，观察是否有节点「没被调用」（日志里能看到）。

坑 4：结束节点只放在一条分支 有的分支走到头没有结束节点，流程卡住或返回空。解法：每个分支都必须有结束节点。

坑 5：循环依赖 节点 A 的输出要 B，B 的输出又要 A——直接报错。解法：设计时避免回环，需要循环用「迭代节点」等专门能力。

工作流 vs 代码：怎么选

你可能会想：工作流这么好用，是不是所有流程都该用它？做个对比：

工作流（Dify） 代码实现
上手门槛 低（拖拽） 高（写码）
可控性 可视化、直观 完全可控
复杂逻辑 节点多了难维护 代码更擅长
调试 可视化看中间值 断点调试
适合 常规业务流 算法级复杂逻辑

建议：80% 的业务流程用工作流，遇到「工作流表达不了」的（复杂算法、深层循环）再考虑代码节点或外部服务。

小练习

  1. 搭一个「客服工单分类」工作流，跑通 3 种不同类型的输入。
  2. 给工作流加一个 HTTP 请求节点（可以调用一个公开 API，如天气接口），把结果拼进回答。
  3. 故意让 LLM 节点输出一个意外的分类值，验证你的「否则」兜底分支是否生效。
  4. 进阶：用代码节点把 LLM 输出的 JSON 解析后，再传给结束节点，体会「模型输出不可靠 → 代码兜底」的思路。
  5. 进阶：故意搭一个「漏了结束节点的分支」的工作流，观察报错，加深对「分支必须收口」的理解。
